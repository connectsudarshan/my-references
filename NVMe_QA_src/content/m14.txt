# Module 14: Multi-Controller, Multipath & Virtualization

@@ 14.01 | Basic | Concept | fig=multictrl | tags=multi-controller,dual-port,cntlid,cmic,subsystem
Q: What does a dual-port, multi-controller NVMe SSD look like, and what is shared between its controllers?
SHORT: One NVM subsystem holds one shared pool of media and namespaces, and exposes it through two or more controllers. On a dual-port PCIe SSD each port has its own link and its own controller, with a distinct 16-bit CNTLID. Everything a host can touch directly (BAR0 registers, queues, interrupts, features) is per controller. The data, the namespaces, the FTL and the NQN are shared. CMIC in Identify Controller says the drive is multi-port or multi-controller.
DEEP:
- **Per controller:** its own PCIe function and BAR0 (CAP, CC, CSTS, doorbells), admin queue and I/O queues, MSI-X table, Set Features state (Arbitration, Power Management, Number of Queues and Async Event Configuration have controller scope, Base 2.3 Figure 403, but note 7 there says different Power Management settings on controllers of one domain give an unspecified domain power state), Async Event Request queue and its controller-scoped log pages.
- **Per subsystem:** the NAND and FTL, the namespaces and their contents (a shared namespace has the same NSID in every controller that can reach it, Base 2.3, 2.4.1), the subsystem NQN, reservation state per namespace, and the NVM Subsystem Reset domain.
- **Identity:** CNTLID (Identify Controller bytes 79:78) is unique only inside one subsystem. The pair (subsystem NQN, CNTLID) names a controller. CMIC (byte 76) has bit 0 multiple ports (MPORTS), bit 1 multiple controllers (MCTRS), bit 2 function type (set for an SR-IOV virtual function) and bit 3 ANA reporting (ANARS).
- **Typical dual-port drive:** a U.2 or U.3 form factor that can present two PCIe links, often two x2 links, to two hosts or two root ports of one host. Each host runs its own driver instance on its own controller. Each controller maps to PCI Function 0 of its own port, and each port has its own Fundamental Reset (Base 2.3, 2.4.1).
- **Multi-controller is not the same as multi-port:** a single-port drive can still expose several controllers, for example one per SR-IOV virtual function (questions later in this module).
- **What to read:**

```
nvme id-ctrl /dev/nvme0 | grep -E "cntlid|cmic|subnqn"
nvme list-ctrl /dev/nvme0        # CNS 13h: all controllers in the subsystem
nvme list-subsys                 # host view: which paths belong to which subsystem
```
- **What the diagram shows:** two hosts, two ports and two controllers on top of one shared namespace and ANA state per controller.
FOLLOW:
- Can host B see the queues host A created? => No. Queues, doorbells and CC/CSTS belong to one controller. Hosts interact only through shared namespaces and subsystem-wide state.
- Is CNTLID unique across drives? => No. It is unique only within an NVM subsystem, so two drives can both have CNTLID 0.
PITFALL: Validating a dual-port drive by running the same test on each port one after another. The bugs live in concurrent cross-port traffic, resets and reservations.

@@ 14.02 | Basic | Concept | tags=ana,states,alua,path-status,anatt
Q: What is Asymmetric Namespace Access (ANA), and what are the ANA states?
SHORT: ANA lets a multi-controller subsystem tell the host how good each path to a namespace is right now, like SCSI ALUA. Namespaces are grouped into ANA groups, and each controller reports one state per group: Optimized, Non-optimized, Inaccessible, Persistent Loss or Change. The host reads them from the ANA log page and prefers Optimized paths. A command sent down a bad path fails with a path related status (SCT 3). Only Optimized is mandatory to report.
DEEP:
| State | Value | Meaning | Host behavior |
|---|---|---|---|
| Optimized | 01h | Full-performance path | Use it |
| Non-optimized | 02h | Works, but slower or more expensive | Use only if no Optimized path |
| Inaccessible | 03h | Controller alive, cannot reach user data of this group now, may recover | Use another path, re-check for at least ANATT if none is usable |
| Persistent Loss | 04h | Persistently inaccessible, shall not move to any other state | Do not use, detach the namespaces if Namespace Management exists |
| Change | 0Fh | Transitioning between states | Wait a short time, then retry on the same controller for at least ANATT (spread the retries), or use another Optimized or Non-Optimized path |

- **State is per (controller, ANA group):** the same namespace can be Optimized through controller 0 and Inaccessible through controller 1.
- **Error statuses:** a command to a namespace in the wrong state completes with SCT 3 and SC 01h (Asymmetric Access Persistent Loss), 02h (Asymmetric Access Inaccessible) or 03h (Asymmetric Access Transition), which Linux names status 301h, 302h and 303h. For 01h and 02h the command should not be resubmitted to the same controller. For 03h it should be retried after the transition (Base 2.3, Figure 107, 8.1.1.6 to 8.1.1.8). A few commands are exempt while a group is in these states (8.1.1.10).
- **ANATT:** Identify Controller byte 342 reports ANA Transition Time in seconds: the maximum time for a transition between states, or for reporting Change. It is nonzero whenever ANA is supported (Base 2.3, Figure 328).
- **What is mandatory:** a subsystem with ANA has every controller set CMIC bit 3 (ANARS) and ANACAP bit 0 (RANAOS), because reporting Optimized is required. ANACAP (byte 343) bits 1 to 4 advertise the optional states: 1 Non-Optimized, 2 Inaccessible, 3 Persistent Loss, 4 Change. Every attached namespace must sit in an ANA group with a non-zero ANAGRPID, and the controller must support the ANA log page and the ANA Change notice (Base 2.3, 8.1.1.1).
- **Side effects:** while Inaccessible or Persistent Loss, capacity fields such as NUSE and NVMCAP in Identify Namespace read 0, so take them from a path that is Optimized or Non-Optimized.
- **Why not just use a controller failure signal:** ANA says "the controller is fine but this path is not," for example a firmware update, a mirrored-cache failover or an array controller taking over.
- **On a plain dual-port SSD** ANA is often not implemented at all (CMIC bit 3 clear, symmetric access). If it is, both controllers usually report Optimized for every group, so it stays dormant until a fault or vendor feature changes it.
FOLLOW:
- Is ANA required for multipath? => No. Without ANA the host treats all paths as equal. ANA is optional and advertised by CMIC bit 3 and the ANACAP field.
- What does the host do on Persistent Loss? => It stops using that controller for the group, and Base 2.3 says the state shall not transition to any other state, so no recovery is expected. If Namespace Management is supported the namespaces should be detached (8.1.2.3).
PITFALL: Treating Inaccessible as a dead drive. The controller is alive and answering admin commands, so a reset is the wrong reaction.

@@ 14.03 | Basic | Concept | tags=nvme-mi,bmc,smbus,mctp,out-of-band
Q: What is NVMe-MI, and why does an SSD need a management interface outside the normal queues?
SHORT: NVMe Management Interface (NVMe-MI) lets a BMC or enclosure controller monitor and manage an SSD without the host OS. It runs over SMBus or I2C, or over MCTP carried on SMBus or on PCIe vendor-defined messages. It reads health, temperature and vital product data, and can send some admin commands. It keeps working when the host is down, the driver is hung or the controller is disabled.
DEEP:
| Path | Transport | Typical use |
|---|---|---|
| Basic Management Command | SMBus block read, 7-bit address 6Ah, no MCTP | Tiny fixed health block for simple BMCs |
| NVMe-MI over MCTP | MCTP over SMBus/I2C, or MCTP over PCIe VDMs | Full command set, from a BMC |
| In-band tunnel | NVMe-MI Send and Receive admin commands (1Dh Send and 1Eh Receive; Base 2.3, 5.2.19 and 5.2.18) | Host software using the MI command set |

- **Roles:** the BMC is the management controller, the SSD contains a management endpoint. MCTP message type 04h carries NVMe-MI.
- **What it does:** subsystem health poll, read MI data structures (port and controller information), configuration get and set, VPD read and write, and tunneled admin commands (a limited set) and PCIe register access.
- **Why outside the queues:** a fleet needs temperature, wear and fault data from a drive that has no working host, and an enclosure needs to know a slot's drive is present before any OS boots.
- **Base 2.3 scope:** the Base spec only defines the MI Send and Receive opcodes, OACS bit 6 (NVMe-MI Send Receive Supported) and the NVMe-MI Commands Supported and Effects log (13h). Everything else about MI is in the NVMe-MI spec.
- **Independent of NVMe state:** MI can answer while CC.EN is 0. Access that needs the PCIe link fails with a dedicated "PCIe inaccessible" MI status when the link is down.
- **Validation relevance:** the SSD's management firmware shares resources with the I/O path. Heavy MI polling must not perturb I/O latency, and MI must survive resets, power states and hangs.
FOLLOW:
- Is MI over PCIe VDM out of band? => It bypasses the NVMe queues (so it is logically out of band) but rides the same PCIe link, so it needs the link up. SMBus MI does not.
- Which tools speak MI on Linux? => libnvme has an MI layer that talks MCTP (with nvme-cli front ends on recent builds), and BMC stacks such as OpenBMC carry their own.
PITFALL: Assuming NVMe-MI is one interface. The SMBus Basic Management Command, MI over MCTP and the in-band MI Send/Receive commands have different reach, format and failure behavior.
VERIFY: Not in Base 2.3, so check the NVMe-MI Specification for the 6Ah address, MCTP message type 04h, the SMBus/PCIe VDM binding, the MI-over-CC.EN behavior and which admin commands are allowed through the MI tunnel. Also check the nvme-cli/libnvme MI support on your build.

@@ 14.04 | Intermediate | Concept | tags=linux,native-multipath,iopolicy,head-device,list-subsys
Q: How does Linux native NVMe multipath present and use multiple paths?
SHORT: With nvme_core.multipath enabled, the driver merges every controller in one subsystem that exposes the same shared namespace into one head block device, such as /dev/nvme0n1. The per-path nodes (nvme0c0n1, nvme0c1n1) are hidden. Each I/O picks a path by ANA state and I/O policy (numa, round-robin, or queue-depth on newer kernels), preferring Optimized paths. On a path error it requeues the I/O on another path.
DEEP:
- **Naming:** head node `nvme<subsys>n<ns>`, hidden per-path nodes `nvme<subsys>c<ctrl>n<ns>`. Without multipath, every controller shows its own `nvme<ctrl>n<ns>` and one shared namespace appears twice.
- **When paths merge:** same subsystem NQN, namespace flagged shared, and matching identifiers (NGUID, EUI-64, UUID). If the IDs do not match, the driver logs an error and refuses the merge.
- **Policy:** `cat /sys/class/nvme-subsystem/nvme-subsys0/iopolicy`. `numa` (default) sends I/O to the path nearest the submitting CPU's node, `round-robin` alternates, `queue-depth` picks the path with the fewest outstanding requests. All only choose among Optimized paths, falling back to Non-optimized only when none is Optimized.
- **Per-path state:** `/sys/class/nvme/nvme0/nvme0c0n1/ana_state` and `ana_grpid` show what the driver last learned from the ANA log.
- **Host view:**

```
nvme list-subsys
cat /sys/module/nvme_core/parameters/multipath
```
- **Setting:** `multipath` is a module parameter you set at boot or module load, and it cannot be flipped at run time.
- **Testing consequence:** fio against the head node measures the combined multipath behavior. To exercise one path, take the others away (ANA Inaccessible, controller reset, disconnect) or load nvme_core with multipath=N.
FOLLOW:
- Two drives report the same NGUID. What happens? => Only IDs within one subsystem merge. Identical NGUIDs on different subsystems are a firmware or manufacturing defect, and the driver may reject or mishandle them.
- Does numa policy spread load across both ports? => Not necessarily. A single-node host sends everything to one Optimized path, so use round-robin or queue-depth to load both.
PITFALL: Running a throughput test on a dual-port drive and concluding the second port is unused. With the numa policy on a single-node host that is the expected behavior.
VERIFY: Linux driver behavior, not spec text (Base 2.3 does not cover host OS policy): which kernel version introduced the queue-depth policy, and the exact sysfs path of the per-path ana_state attribute on your kernel.

@@ 14.05 | Intermediate | Concept | tags=ana,log-page,change-count,aen,rgo
Q: How is the ANA log page laid out, and how does the host learn that an ANA state changed?
SHORT: The ANA log page (Log Identifier 0Ch) starts with a 16-byte header holding a change count and the number of group descriptors, then one descriptor per ANA group: 32 bytes of group ID, NSID count, group change count and state, followed by the NSID list. It is per controller. A state change triggers an Async Event, notice type ANA Change, if the host enabled it, and the host re-reads the log.
DEEP:
| Offset | Size | Field |
|---|---|---|
| 0 | 8 | Change Count of the log |
| 8 | 2 | Number of ANA Group Descriptors |
| 10 | 6 | Reserved |
| 16 | 32 + 4 x NNSID | First descriptor, then the next, back to back |

- **Descriptor:** bytes 0-3 ANAGRPID, 4-7 number of NSID values, 8-15 group Change Count, byte 16 state (low 4 bits), 17-31 reserved, then the 32-bit NSIDs from byte 32 (Base 2.3, Figures 227 and 228). Descriptors come in ascending group ID order and NSIDs in ascending NSID order.
- **Per controller:** each controller reports its own view, so the host reads the log from every controller in the subsystem. A group appears only if it has a namespace attached to that controller, so a controller with no namespaces returns zero descriptors.
- **Return Groups Only:** RGO is bit 8 of CDW10, bit 0 of the log specific field (Figure 226). The controller returns each descriptor with the NSID count cleared to 0 and no NSID list, which shortens the read when there are many namespaces.
- **Partial reads:** if the log's Index Offset Supported bit is set in the LID Supported and Effects log, the host can set OT in CDW14 and pass a descriptor index instead of a byte offset in LPOL/LPOU (index 1 is descriptor 0), which avoids byte arithmetic on variable-size descriptors.
- **Notification:** Set Features, Async Event Configuration (FID 0Bh) enables the ANA Change notice (bit 11; OAES bit 11 says the controller supports it). The controller then completes an Async Event Request with type 2 (notice), info 03h, and log page ID 0Ch, so CQE DW0 reads 000C0302h. After reporting a Notice event the controller masks further events of that type until the host clears it by reading the ANA log with RAE cleared (Base 2.3, 5.2.2, Figure 154).
- **Also reactive:** Linux re-reads the log after an I/O fails with an ANA error status, and again on reconnect and reset.
- **Change count:** the 64-bit header count starts at 0 after a Controller Level Reset and increments every time the log contents change, whether or not an event was sent, so a host can detect a change it missed by comparing counts. It rolls over to 0. The per-group count starts at 1 after the reset, rolls over to 1, and 0 means the controller does not report one (then re-examine that descriptor).
- **Multi-read consistency:** if the host reads the log in several Get Log Page commands, it should re-read the header and compare the Change Count. A mismatch means the data is inconsistent and the read must be repeated.
- **When the notice is sent:** on an ANA Group ID change, on a failed state transition, and on entry to Optimized, Non-Optimized, Inaccessible or Persistent Loss, unless the entry results from a namespace attach (Base 2.3, 8.1.1.9). Attach, detach and delete changes are reported by the namespace attribute notices instead. Entry to Change is not in the list.
FOLLOW:
- Why does a host need a separate read per controller? => The state is per (controller, group). Controller 0's log says nothing certain about controller 1's view.
- What if the AEN is masked or never enabled? => Correct hosts still learn from failing I/O statuses and periodic re-reads, but recovery is slower. A validator should test both.
PITFALL: Reading the log once at connect time and caching it. States change, and stale Optimized states send I/O down a path that fails.

@@ 14.06 | Intermediate | Concept | tags=reservations,registrants,holder,types,write-exclusive
Q: How do NVMe reservations work, and what do the six reservation types allow?
SHORT: A reservation lets hosts share a namespace safely. Each host registers a 64-bit key with the namespace, and one registrant can acquire a reservation of a chosen type, becoming the holder. The six types (write exclusive or exclusive access, each in plain, registrants-only, and all-registrants forms) decide who can read and write. A non-permitted command completes with Reservation Conflict, status 83h.
DEEP:
| Type | Value | Holder | Other registrants | Non-registrants |
|---|---|---|---|---|
| Write Exclusive | 1 | R/W | Read only | Read only |
| Exclusive Access | 2 | R/W | None | None |
| Write Exclusive, Registrants Only | 3 | R/W | R/W | Read only |
| Exclusive Access, Registrants Only | 4 | R/W | R/W | None |
| Write Exclusive, All Registrants | 5 | R/W (each registrant is a holder) | R/W | Read only |
| Exclusive Access, All Registrants | 6 | R/W (each registrant is a holder) | R/W | None |

- **Objects:** a registrant is a host (identified by its Host Identifier), a key is 64 bits, and a namespace has at most one reservation at a time. The table is Base 2.3 Figure 702.
- **Which commands conflict (Figure 703):** the write group is Flush, Format NVM, Sanitize, Capacity Management, Namespace Management and Attachment, Security Send, and the I/O command set's Write and Copy destination commands. The read group is Security Receive plus Read and Copy source. Identify, Get Log Page, Get/Set Features and the rest are always allowed. So a Flush from a non-holder registrant fails under Write Exclusive and Exclusive Access, and from a non-registrant under every type.
- **Timing:** the check happens when the controller starts processing a command. A command that passed is never aborted later for a new reservation (Base 2.3, 8.1.24).
- **Scope:** the reservation belongs to the namespace, so it applies to every controller that has the namespace attached, which is what makes it work for dual-port and dual-host drives.
- **Registrants-only types:** the holder is one host, but every registrant is allowed the same access, which suits a cluster.
- **All-registrants types:** there is no single holder, and the reservation ends when the last registrant unregisters or on Release or Clear (Base 2.3, 8.1.24.4).
- **Use:** cluster managers use reservations to fence a failed node so it cannot write after the cluster moved on (questions 14.09, 14.11 and 14.17).
- **Capability:** Identify Controller ONCS bit 5 (RESERVS) says reservations exist, and Identify Namespace RESCAP says what a namespace supports: bit 0 PTPLS, bits 1 to 6 the six types in value order, bit 7 IEKS (Figure 335). Without support the four reservation commands fail with Invalid Command Opcode.
FOLLOW:
- Does a Read to a Write Exclusive namespace from a non-holder work? => Yes, reads are allowed. Only modifying commands conflict.
- Is reservation state per controller or per namespace? => Reservation state is per namespace. Registration is per host: controllers with the same Host ID count as one registrant, so registering through one covers the others (Base 2.3, 8.1.24.3).
PITFALL: Assuming a reservation is a lock that prevents the holder's own race conditions. It only arbitrates access between hosts and does nothing about ordering within one host.
VERIFY: Which NVM Command Set commands (Write, Write Zeroes, Write Uncorrectable, Dataset Management, Copy, Verify, Compare) fall in the read or write group. Base 2.3 Figure 703 only says "I/O Command Set specific", so check the NVM Command Set Specification.

@@ 14.07 | Intermediate | Numeric | tags=ana,log-page,size,mdts,numd
Q: How big can the ANA log page get, and why can that matter for a driver?
SHORT: Size = 16-byte header + 32 bytes per group descriptor + 4 bytes per NSID listed. A drive with 128 ANA groups and 1024 namespaces reports up to 16 + 128 x 32 + 1024 x 4 = 8208 bytes. Linux sizes its buffer from the Identify Controller limits and disables ANA if that exceeds the maximum transfer size, so a log 16 bytes over a limit like 8 KiB makes it log an error and turn multipath ANA off.
DEEP:
1. Header: 16 bytes (change count 8, group count 2, reserved 6).
2. Worst-case descriptors: NANAGRPID (Identify Controller bytes 351:348) groups x 32 bytes = 128 x 32 = 4096 bytes.
3. Worst-case NSID lists: each namespace appears once, so the maximum is the maximum number of namespaces x 4 bytes = 1024 x 4 = 4096 bytes.
4. Total: 16 + 4096 + 4096 = 8208 bytes.
5. Get Log Page NUMD (zero-based dword count) for the full read: 8208 / 4 - 1 = 2051.
6. Small example: 2 groups and 3 NSIDs total = 16 + 2 x 32 + 3 x 4 = 92 bytes, which matches the decode in question 14.10.

- **Linux check:** the driver computes header + NANAGRPID x 32 + max namespaces x 4 and compares it to its maximum transfer size derived from MDTS. If larger it logs "ANA log page size ... larger than MDTS" and disables ANA support. A drive with MDTS = 1 and a 4 KiB minimum page, 8192 bytes, would fail at 8208.
- **Max namespaces:** newer kernels use MNAN (bytes 543:540). Base 2.3 (Figure 328) requires a controller with ANA to report MNAN non-zero and not above NN, and the kernel refuses ANA otherwise.
- **Validation checks:**
  - Advertised NANAGRPID and namespace limits are consistent with the largest log the drive returns.
  - Partial reads (NUMD smaller than the log, non-zero log page offset) return the correct slice.
  - Sum of NNSID across descriptors matches the number of attached namespaces, and no NSID appears twice.
FOLLOW:
- How does a host read a log of unknown size safely? => Read the 16-byte header first for the group count, then compute the size, or read the maximum computed from Identify Controller.
- Does RGO reduce the size a lot? => Yes. With Return Groups Only the size is 16 + 32 x groups, no NSID lists, so 4112 bytes for 128 groups.
PITFALL: Testing ANA only with two namespaces. Tables near the limits are where transfer size, MDTS and buffer bugs live.
VERIFY: The exact Linux message text and MNAN handling on your kernel. Base 2.3 (Figure 328) defines MDTS for any command that moves data between host memory and the controller but does not name Get Log Page, so confirm your drive applies it to log reads.

@@ 14.08 | Intermediate | Concept | tags=nvme-mi,health-poll,ccs,basic-management,bmc
Q: What does the NVMe-MI health poll return, and how would a BMC use it and the Basic Management Command?
SHORT: The NVM Subsystem Health Status Poll returns an 8-byte structure: subsystem status, SMART warnings, composite temperature, percentage of life used, and a 16-bit Composite Controller Status of sticky change flags. The BMC polls it, alerts on the flags and clears them. The older SMBus Basic Management Command returns an even smaller block (temperature, warnings, life used) without MCTP, for simple BMCs.
DEEP:
- **Health poll structure:** NSS (NVM Subsystem Status), SW (SMART warnings), CTEMP (composite temperature), PDLU (percentage drive life used), CCS (2 bytes), 2 reserved bytes.
- **CCS bits:** flag events that happened since the last clear, for example Ready (bit 0), Controller Fatal Status (bit 1), Shutdown Status (bit 2), NVM Subsystem Reset Occurred (bit 4), Namespace Attribute Changed (bit 6), Firmware Activated (bit 7), Composite Temperature change (bit 9), Percentage Used (bit 10), Available Spare (bit 11), Critical Warning (bit 12).
- **Clearing:** the poll has a clear option that resets the CCS flags after they are read, so a BMC does not see the same event twice. A Configuration Set can also clear selected bits.
- **Basic Management Command:** an SMBus block read at command 00h returns a length byte, status flags, SMART warnings, composite temperature, percentage drive life used and a PEC byte. Command 08h returns vendor ID and serial number.
- **Other MI commands:** Read NVMe-MI Data Structure (opcode 00h), Configuration Get and Set (04h and 03h), and further commands such as controller health poll, VPD read and write and reset.
- **Validation cross-checks:** compare MI temperature, life used and warnings with in-band SMART (Get Log Page 02h) at the same instant. They should agree within the sensor update interval. A mismatch shows two separate firmware sources of truth.
- **Response status:** the MI response header carries a status, where 00h is success, 04h invalid parameter and 21h PCIe inaccessible.
FOLLOW:
- Why sticky flags rather than levels? => A BMC polling every few seconds could miss a short event, so the flag latches it until read.
- What does the BMC see if the PCIe link is down? => Health polls that the management endpoint can answer without the link still work, and PCIe-dependent MI commands return "PCIe inaccessible".
PITFALL: Treating the Basic Management Command temperature as identical to SMART. Its encoding has special values for no data and sensor failure that a naive parser reads as temperatures.
VERIFY: Basic Management Command byte encodings (SMART warnings polarity, temperature special values, status flag bits, the length byte value, what command 08h returns), all MI opcodes beyond 00h, 01h, 03h and 04h, and CCS bit positions in the NVMe-MI spec.

@@ 14.09 | Advanced | Concept | tags=reservations,register,acquire,release,preempt,ptpl,notification
Q: Walk through the reservation commands and their actions, including preempt, PTPL and the notifications.
SHORT: Reservation Register (0Dh) adds, removes or replaces a host's key. Acquire (11h) takes the reservation, or preempts or preempts-and-aborts another host's registration. Release (15h) releases the reservation or clears everything. Report (0Eh) returns the registrants, holder and type. Preempted hosts learn through a reservation notification log page (80h). Persist Through Power Loss (PTPL) decides whether state survives a power cycle.
DEEP:
| Command | Opcode | Actions | Data |
|---|---|---|---|
| Reservation Register | 0Dh | 0 Register, 1 Unregister, 2 Replace | Current key and new key |
| Reservation Acquire | 11h | 0 Acquire, 1 Preempt, 2 Preempt and Abort | Current key and preempt key |
| Reservation Release | 15h | 0 Release, 1 Clear | Current key |
| Reservation Report | 0Eh | none | returns a status structure |

- **CDW10 fields:** Register has CPTPL in bits 31:30, IEKEY in bit 3 and RREGA in bits 2:0. Acquire has RTYPE in bits 15:8, IEKEY in bit 3 and RACQA in bits 2:0. Release has RTYPE in bits 15:8, IEKEY in bit 3 and RRELA in bits 2:0 (Base 2.3, Figures 603, 607, 610).
- **Ignore Existing Key:** only Register honors IEKEY, where it skips the current-key check for Unregister and Replace. Acquire and Release with IEKEY set fail with Invalid Field in Command (7.5 to 7.7). RESCAP bit 7 (IEKS) says the namespace uses the 1.3-or-later behavior.
- **Preempt:** the acquirer, a registrant sending its own key, names a preempt key (PRKEY). If PRKEY matches the holder, then in one atomic step the other registrants with that key are unregistered, the reservation is released and a new one of the command's RTYPE is created for the acquirer. If PRKEY names a non-holder registrant, only registrants with that key are removed. PRKEY 0 is Invalid Field, except with the All Registrants types, where it removes every other registrant and takes over. A holder may preempt itself to change type (8.1.24.7).
- **Preempt and Abort:** as preempt, and afterwards all controllers of the preempted hosts are asked to abort commands being processed for that NSID. The Acquire completes only after each of them has aborted or otherwise completed, so its completion is the fence. The abort itself is best effort. It is the fencing primitive.
- **Clear:** the release action that removes the reservation and every registration. Only a registrant may use it, and it needs its key.
- **Report:** returns a header with a 32-bit generation counter (incremented by a successful Register, Release with Clear, Preempt or Preempt and Abort), reservation type, number of registrants (REGSTRNT, called number of registered controllers before 2.3) and PTPL state. Then comes one entry per registrant: CNTLID (FFFFh if no controller of this subsystem), a holder flag (AHHR), host ID and key. CDW11 bit 0 (EDS) selects the extended form with 128-bit host IDs, which must match the Host ID size in use or the command fails with Host Identifier Inconsistent Format (7.8).
- **Notifications:** a Reservation Notification log page (80h) lists Registration Preempted (01h), Reservation Released (02h) and Reservation Preempted (03h). The controller signals it with an async event (type 6, info 00h), and Set Features FID 82h masks each kind per namespace (bit 1 registration preempted, bit 2 released, bit 3 preempted). Preempt sends Registration Preempted to the removed hosts, a type change sends Reservation Released to the remaining registrants, and Clear sends Reservation Preempted to the removed hosts (8.1.24.7, 8.1.24.8).
- **PTPL:** set through the CPTPL bits of Register or through FID 83h. CPTPL is 00b no change, 10b clear, 11b set. With PTPL on, reservations and registrants survive power loss. Without it, a power loss clears them.
- **CLI:** `nvme resv-register`, `resv-acquire`, `resv-release`, `resv-report`.
FOLLOW:
- Does a controller reset drop registrations? => No. Reservations and registrations persist across all Controller Level Resets and all NVM Subsystem Resets. Only a power loss clears them, unless PTPL is set (Base 2.3, 8.1.24.2). One catch: registrations made under Host ID 0h do not survive a Controller Level Reset, because that host counts as a new one afterwards (5.2.26.1.32).

Q: A Linux host reserves a namespace through nvme0 and things work, but the same writes fail with Reservation Conflict when multipath uses nvme1. What went wrong?
SHORT: The subsystem tells hosts apart by Host Identifier, not by controller. If nvme0 and nvme1 have different Host IDs (on PCIe the default is 0h, meaning not associated with any other controller), nvme1 is a different host and a non-registrant, so its writes get Reservation Conflict, status 83h. It is not a path error, so multipath does not fail over. Give all of one host's controllers the same non-zero Host ID before registering.
DEEP:
- **Symptom:** the failure appears only when the path changes, for example after failover or with a different iopolicy. 83h is a generic status, not SCT 3, so Linux does not treat it as a path error and returns it to the application.
- **Evidence:**
  - `nvme resv-report /dev/nvme0n1 --eds` lists registrants with CNTLID, holder flag, host ID and key. If nvme1's Host ID differs from the registrant's, nvme1 is not that host, however the keys match.
  - `nvme get-feature /dev/nvme0 -f 0x81 -l 16` and the same for nvme1 shows the Host Identifier feature (FID 81h). A 128-bit ID needs EXHID, CDW11 bit 0, and every controller in the subsystem must use the same size (Host Identifier Inconsistent Format otherwise).
  - The Reservation Conflict shows in the CQE (SCT 0, SC 83h). Linux maps it to a reservation-conflict block error (BLK_STS_RESV_CONFLICT), not a path error.
- **Host ID rules (Base 2.3, 5.2.26.1.32, 8.1.24):** 0h means the host is not associated with any other controller, so two controllers at 0h are two hosts. A controller may require a non-zero ID for reservations (CTRATT bit 18, RHII) and otherwise supports 0h, or fails reservation commands with Host Identifier Not Initialized (27h). The feature is not saved and returns to 0h after a reset (Figure 403), so it must be set again every time. Once non-zero, another Set Features gets Command Sequence Error. Registrations made under 0h stay with 0h if the ID is set later.
- **Linux and Host ID:** fabrics controllers send HOSTID in Connect (mandatory and 128-bit over fabrics), but the in-tree PCIe driver code does not appear to issue Set Features 81h itself, so on a dual-port PCIe SSD a script or udev rule has to set it on each controller (`nvme set-feature -f 0x81`, 16-byte buffer, extended bit in CDW11).
- **Why the design works this way:** in a cluster, node A's two paths must be one host, or a node would fence itself when it switches paths. Different hosts must get different IDs, or fencing does nothing.
- **Fix:** same non-zero Host ID on every controller of one host, set again after each reset, then register once and acquire once. Registering through the second controller again is allowed only with the same key. A different key from the same host fails with Reservation Conflict (8.1.24.3).
- **Test angle:** a drive should treat two controllers with the same Host ID as one host, so a registration through either covers both, and treat a different Host ID as another host. A drive that treats the two paths of one host as strangers fails multi-path clusters.
FOLLOW:
- Would Reservation Conflict retry on another path? => No. The host driver sees a generic status, not a path status, so it completes the I/O with an error. A retry would conflict again with the same key state.
- How does the Host ID relate to the Host NQN? => They are separate. Host NQN identifies a host to a fabrics target. Host ID is a Set Features value used for reservations and other host-scoped tracking.
PITFALL: Setting the Host ID on only one controller, or after registering, and blaming the SSD when I/O on the other path conflicts. Registrations made under Host ID 0h do not move to the new ID.
VERIFY: How PCIe controllers get their Host ID on your Linux kernel (a driver or udev behavior, not Base 2.3 text).

|---|---|---|
| CC.EN 1 to 0 | Controller A | None, B's queues and I/O continue |
| Function Level Reset of A's function | Controller A | None |

| NSSR (write 4E564D65h, "NVMe", to NSSR at offset 20h; needs CAP.NSSRS) | Whole subsystem | Controller Level Reset on B, link may drop, CSTS.NSSRO set |

Q: How does the Virtualization Management command assign resources to secondary controllers, and in what order do you bring a VF up?
SHORT: Virtualization Management (admin opcode 1Ch) acts on a controller ID with an action and resource type. Actions: Primary Flexible Allocation (01h), Secondary Offline (07h), Secondary Assign (08h) and Secondary Online (09h). Resource type 0 is VQ (queue resources) and 1 is VI (interrupt resources). The primary assigns VQ and VI counts to each secondary, then brings it Online. Identify (CNS 14h and 15h) reports what exists and what is assigned.
DEEP:
- **Identify Primary Controller Capabilities (CNS 14h):** whether VQ and VI are supported (CRT bits 0 and 1), total flexible resources (VQFRT, VIFRT), how many are assigned to secondaries (VQRFA, VIRFA), how many the primary currently holds (VQRFAP, VIRFAP), the primary's private resources (VQPRT, VIPRT), the maximum for one secondary (VQFRSM, VIFRSM) and the preferred granularity (VQGRAN, VIGRAN).
- **Identify Secondary Controller List (CNS 15h):** up to 127 entries of 32 bytes for controller IDs from CDW10 CNTID upward. Each has the secondary and primary controller ID, the Online bit, the VF number and the VQ and VI counts currently assigned (NVQ, NVI).
- **Command fields:** CDW10 carries the action (bits 3:0), the resource type (10:8) and the target CNTLID (31:16). CDW11 carries the number of resources, NR (15:0). CQE DW0 returns NRM, the number actually modified, which may be smaller or larger than requested (Base 2.3, 5.3.6). OACS bit 7 (VMS) advertises the command.
- **Bring-up order:**
  1. Identify primary capabilities. Plan totals against limits.
  2. Optionally give the primary flexible resources (action 01h). It persists and takes effect after the next Controller Level Reset other than a Controller Reset.
  3. Enable the VFs at the PCIe level (`echo N > sriov_numvfs`) so the functions exist. Secondaries are Offline, and read CSTS.CFS = 1, until brought Online.
  4. With the secondary Offline, assign VQ resources (action 08h, RT 0, NR) and VI resources (action 08h, RT 1, NR). The minimum is 2 VQ (admin plus one I/O queue pair) and a VI for vector 0.
  5. Reset the secondary (a VF Function Level Reset), so the MSI-X table size reflects the new VI count.
  6. Bring the secondary Online (action 09h), which needs the primary enabled. Its controller now accepts CC.EN and the VF driver can initialize it (Base 2.3, 8.2.6.3).
- **Errors:** command-specific statuses are Invalid Controller Identifier (1Fh, bad CNTLID), Invalid Secondary Controller State (20h, assigning while not Offline, or Online without a configured secondary or an enabled primary), Invalid Number of Controller Resources (21h, NR above VQFRT or VQFRSM) and Invalid Resource Identifier (22h, NR above the remaining free resources).
- **Resets:** if the primary is disabled, reset or shut down, every secondary goes Offline implicitly, and going Offline removes its flexible resources, so they must be assigned again (8.2.6.3).
- **Linux:**

```
nvme primary-ctrl-caps /dev/nvme0
nvme list-secondary /dev/nvme0
nvme virt-mgmt /dev/nvme0 -c 1 -r 0 -a 8 -n 4    # assign 4 VQ to CNTLID 1
```
- **PCIe side:** see the PCIe page, SR-IOV module, for the VF mechanics. NVMe adds the queue and vector budget on top.
FOLLOW:
- Can you resize a VF's queues while it is Online? => Take it Offline, reassign, bring it Online. Expect a live controller to reject the change with Invalid Secondary Controller State.
- Does a VF need its own namespaces? => It needs namespaces attached with Namespace Attachment. Private namespaces isolate tenants, shared ones let several controllers see the same data.
PITFALL: Enabling VFs and expecting I/O. An unassigned or Offline secondary cannot create queues, so the VF's driver fails at initialization.
VERIFY: The nvme-cli virt-mgmt option letters and the sriov_numvfs sequence on your kernel, which are tool behavior and not Base 2.3 text.

Q: How would you design a validation plan for path failover on a dual-port SSD?
SHORT: Build a fault matrix (graceful ANA change, controller reset, PCIe link drop, silent hang, NSSR, both paths down and back) and run each under verified fio load with two hosts or two controllers. Measure application errors, longest I/O stall, failover and failback time and data integrity. Define pass criteria per fault class, capture host logs, ANA logs and analyzer traces on both ports, and automate it as a loop with randomized timing.
DEEP:
| Fault | Injection | Expected host reaction | Pass criteria |
|---|---|---|---|
| ANA state flip (Optimized to Inaccessible) | Vendor or debug command | ANA Change event, reroute | Zero app errors, stall in milliseconds |
| Controller disable/reset | CC.EN=0 or sysfs `reset_controller` | Requeue, resume after reset | Zero app errors, stall bounded by reset time |
| PCIe link down on one port | Slot or PERST# control, interposer | Controller dead, failover | Zero app errors, stall bounded by detection |
| Silent hang | Firmware knob stops completions | I/O timeout, then reset | Stall about the timeout, then continues |
| NSSR | Register write | Both controllers reset | Recovery, no corruption |
| All paths down, one returns | Sequential faults | Queue while no path, resume | No error within the queue window |
| Failback | Restore state | Traffic returns to Optimized | Path used again, no flap |

- **Evidence:** kernel nvme tracepoints, `nvme list-subsys` sampled fast, dmesg timestamps, ANA log snapshots, analyzer capture on both ports with a shared time marker.
- **Randomize:** fault time relative to command boundaries, queue depth, write size, and whether a Flush or a large write is in flight.
- **Compliance checks:** path errors carry DNR = 0 (Linux does not fail over when DNR is set), ANA statuses match the log, and Change state ends within ANATT.
- **Automation:** a state-machine harness that arms an injector, runs the workload, applies a fault, waits for a settle window, checks invariants (no miscompare, no unexpected error, bounded stall) and stores artifacts on failure.
FOLLOW:
- How do you decide the stall limit? => From the host's timeouts and the product requirement, for example one I/O timeout (30 s default on Linux) for silent hangs, and far less for graceful and link-down cases.
- Why test with two hosts, not just two controllers on one? => Two hosts have separate Host IDs, separate reservation identities and separate reset behavior, which is what a real dual-port deployment stresses.
PITFALL: Testing failover only when the workload is idle. Failover with writes in flight, a Flush queued or GC running is where data-integrity bugs surface.
VERIFY: Linux default timeouts and retry counts on your kernel, and whether path errors with DNR set skip failover in that version.

@@ 14.16 | Principal | Debug | tags=failover,timeout,anatt,stall,dmesg,root-cause
Q: After you disable one port of a dual-port SSD under load, application I/O freezes for about 30 to 60 seconds before continuing on the other path. Is it a bug, and how do you root-cause it?
SHORT: It can be correct behavior. Failover speed depends on how the failure is detected. A link that drops or a controller that reads all ones is caught in milliseconds, but a controller that silently stops completing commands is caught only by the I/O timeout, 30 seconds by default on Linux, and possibly twice with an Abort attempt. So classify the failure regime first from timestamps, then decide whether the drive should have signaled a path error.
DEEP:
Three regimes explain most freezes:
1. **Loud failure:** link down or the controller registers read all ones. The driver notices at the next poll or timeout check, resets the controller, cancels in-flight requests with Command Aborted By Host (SCT 3 Path Related, SC 71h, i.e. status 371h), and multipath reroutes them. Freeze: typically a few seconds at most.
2. **Silent hang:** the link is up, but the controller stops posting CQEs. Nothing tells the host until the I/O timeout fires (30 s), after which the driver sends Abort and waits again, or resets. Freeze: about one to two timeout periods.
3. **Stuck transition:** a group sits in ANA Change state past ANATT. Linux logs "ANATT timeout, resetting controller" at about twice the reported ANATT, then reroutes.

- **Method:**
  - Line up timestamps: fault injection time, last completion, first timeout message in dmesg, reset, first completion on the other path.
  - Look at dmesg for the wording of the timeout, the abort and the reset ("I/O ... timeout, aborting", "controller is down", "ANATT timeout").
  - Read CSTS and the PCIe link state on the failed port at the freeze midpoint. All ones means a dead link or function.
  - Capture the surviving controller's ANA log. If the fault injection changed the ANA state on the good side, the ANA Change event should have reduced the stall.
  - Analyzer: does the failing port still ack TLPs but never complete commands (silent hang), or is the link gone?
- **Decision:** if the drive can know it cannot serve a controller, it should complete with a path-related status or set CSTS.CFS, not stay silent. A firmware fix means detecting the internal fault and failing fast. A host-side tuning (`nvme_core.io_timeout`) trades stall time for false timeouts when GC or throttling delays completions.
FOLLOW:
- The freeze is exactly 60 seconds every time. What does that suggest? => Two 30-second timeouts in sequence: the I/O timed out, an Abort was tried, and only the second timeout reset the controller.
- Multipath is on, but the I/O froze rather than rerouting immediately. Why? => Failover happens when a request completes with a path error or is cancelled, so until then it sits in the hung controller's queue.
PITFALL: Reporting the freeze as a drive defect when the injection method made a silent hang. Check what the fault looked like to the host before assigning blame.
VERIFY: Linux abort and reset flow in nvme_timeout on your kernel version (single or double timeout), and the exact dmesg strings.

@@ 14.17 | Principal | Cross-layer | tags=fencing,preempt-abort,stale-write,split-brain,reservations,data-integrity
Q: How would you build a test that proves a failed-over write cannot land late and overwrite newer data, and how do reservations fit?
SHORT: The hazard is a write still executing on the failed path after the host retried it on the other, so the old data overwrites the newer data. NVMe gives no ordering across controllers. The test stalls a write on controller A, fences A (controller reset, or reservation Preempt and Abort from B), lets B write newer data, releases the stall, and asserts the LBA still holds the newer sequence number.
DEEP:
- **Sequence:** W1(seq n) goes to LBA L through A and is delayed inside the drive. The host times out and fails W1 over to B, then the application writes W2(seq n+1) to L through B. A recovers and executes W1 late. If it lands, L holds n, stale data with no error.
- **Fences:** (a) reset A so its outstanding commands are discarded, confirmed by CSTS.RDY dropping. (b) If A is unreachable or belongs to another host, B (as a registrant) issues Reservation Acquire with Preempt and Abort against A's key. A's registration is removed, commands from A are aborted, and A's later writes get Reservation Conflict.
- **Setup:** two hosts or two controllers with different Host IDs, a shared namespace, a reservation type that blocks writes from non-registrants (for example 4, Exclusive Access Registrants Only), keys registered for both.
- **Making the stall:** a firmware or debug knob to hold one controller's commands mid-flight. Sleeping in the host cannot do it, because the command must be inside the drive.
- **Data model:** every write carries LBA, global sequence number, writer ID and CRC. The host keeps a shadow of the newest acknowledged sequence per LBA.
- **Assertions:**
  1. After fencing, A's write gets no success that alters media, or its effect precedes W2.
  2. A read of L through both controllers returns seq n+1.
  3. Reservation Report shows A removed, generation incremented, and A's controller has a Registration Preempted notification pending.
  4. A control run without the fence documents whether the drive can misorder, which is allowed by the spec, so it is a hazard to report and not a failure.
- **Scale:** loop with random delays between the stall and the fence, many LBAs and sizes, and Flush in the mix. Search the whole range for stale sequence numbers after each run.
FOLLOW:
- Does Preempt and Abort guarantee A's commands are gone? => It requests it, but a command past the point of no return may still complete. The test asserts the final data order, not that no command ran.
- Why not just wait longer before retrying? => A hung controller gives no bound. Without a fence, any delay is only a guess.
PITFALL: Testing fencing on an idle namespace. The race needs a command in flight inside the drive at the moment of the fence.
VERIFY: What the spec requires of Preempt and Abort for commands already in progress, and which reservation types block writes from unregistered or preempted hosts.
