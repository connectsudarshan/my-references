# Module 9 — Config Space & Enumeration

@@ 9.01 | Basic | Concept | fig=cfgspace | tags=config-space,type0,type1,header,layout
Q: How is PCIe configuration space laid out, and how do Type 0 and Type 1 headers differ?
SHORT: Every function has its own configuration space of up to 4 KB. The first 256 bytes are the legacy PCI-compatible region: a 64-byte header (Type 0 for endpoints, Type 1 for bridges and root or switch ports) followed by capability structures. Offsets 100h to FFFh hold the PCIe extended capabilities. It is the only thing software can reach before any BAR is assigned.
DEEP:
| Offset | Content |
|---|---|
| 00h-3Fh | Standard header, Type 0 or Type 1 (Header Type at 0Eh, bits 6:0) |
| 40h-FFh | Capability structures, linked from the pointer at 34h |
| 100h-FFFh | Extended capability structures, linked from 100h |

- **Per function:** a multi-function device has one 4 KB space per function. Function 0 is mandatory.
- **Access paths:** CfgRd/CfgWr TLPs generated by the root complex, the memory-mapped ECAM window that hides them behind ordinary loads and stores, and the legacy x86 ports CF8h/CFCh, which reach only the first 256 bytes.
- **Where it lives:** in registers inside the device, with attributes such as read-only, read-write, write-1-to-clear and sticky. It is not stored in host memory.

| Offset | Type 0 (endpoint) | Type 1 (bridge or port) |
|---|---|---|
| 00h-0Fh | IDs, Command, Status, Revision, Class Code, Header Type, BIST | Same |
| 10h-17h | BAR0, BAR1 | BAR0, BAR1 |
| 18h-27h | BAR2 to BAR5 | Primary, Secondary and Subordinate bus numbers, I/O, Memory and Prefetchable Base/Limit, Secondary Status |
| 28h-33h | Subsystem IDs (2Ch), Expansion ROM BAR (30h) | Prefetchable and I/O upper address bits |
| 34h-3Fh | Capabilities Pointer, Interrupt Line and Pin | Capabilities Pointer, Expansion ROM (38h), Interrupt Line and Pin, Bridge Control (3Eh) |
FOLLOW:
- Can the legacy CF8h/CFCh mechanism read an extended capability? => No. It reaches only 256 bytes, so extended capabilities need ECAM or an equivalent memory-mapped mechanism.
- How does software know which header layout to parse? => Read Header Type at 0Eh and mask bit 7 (the multi-function flag). 00h is Type 0, 01h is Type 1.
PITFALL: Treating the 4 KB as one space per device. It is per function, and each function can have a different capability chain.
VERIFY: Type 1 field offsets against the header figure in the PCIe Base Specification (or PCI-to-PCI Bridge Architecture Specification).

@@ 9.02 | Basic | Concept | tags=vendor-id,device-id,class-code,header-type,multifunction,nvme
Q: Which config space fields identify a function, and what is the Class Code of an NVMe SSD?
SHORT: Vendor ID (00h) and Device ID (02h) name the silicon, Revision ID (08h) the stepping, and the three-byte Class Code (09h to 0Bh) says what kind of function it is. For NVMe it is base class 01h (mass storage), sub-class 08h (non-volatile memory), programming interface 02h (NVM Express), so 010802h. Header Type (0Eh) holds the layout in bits 6:0 and the multi-function flag in bit 7. A Vendor ID of FFFFh means nothing answered.
DEEP:
- **Vendor ID:** assigned by the PCI-SIG. FFFFh is reserved as invalid, which is why an empty slot reads as all ones.
- **Device ID and Revision ID:** vendor-assigned. Drivers and quirk tables key on the pair, and firmware validation keys on Revision to tell steppings apart.
- **Subsystem Vendor ID and Subsystem ID (Type 0, at 2Ch and 2Eh):** identify the board or OEM that used the chip, so the same controller can have different quirks per SSD model.
- **Class Code layout:** offset 0Bh base class, 0Ah sub-class, 09h programming interface. lspci prints `Non-Volatile memory controller (prog-if 02 [NVM Express])`.
- **Header Type bit 7:** if set, the device has more than one function and the enumerator must probe the other function numbers. If clear, only function 0 exists.
- **Driver binding:** Linux `nvme` matches on the class code 010802h with a wildcard entry, plus specific Vendor/Device entries for quirks. Windows lists `CC_010802` in the hardware ID and binds its in-box NVMe driver by that.
FOLLOW:
- What do SR-IOV virtual functions return for Vendor ID? => FFFFh. Their identity comes from the physical function's SR-IOV capability (VF Device ID), and the OS treats them specially.
- Why is Vendor ID read first during enumeration? => It is the cheapest presence test. Anything except a valid ID means no function there (or not ready yet, see Configuration Request Retry Status).
PITFALL: Matching on Device ID alone in a test script. The same Device ID can ship with different firmware and Subsystem IDs, and behavior can differ per OEM model.
VERIFY: Programming interface values for NVMe (02h NVM Express, 01h NVMHCI, and any newer value for administrative controllers) in the PCI-SIG class code list and the NVMe over PCIe Transport specification.

@@ 9.03 | Basic | Concept | tags=command,status,mse,bme,intx,write-1-to-clear
Q: What do the Command and Status registers control, and which bits matter for an NVMe SSD?
SHORT: Command (04h) enables the function's behavior. Memory Space Enable turns on BAR decoding, Bus Master Enable lets the function issue memory requests (DMA and MSI/MSI-X writes), and Interrupt Disable blocks INTx. Status (06h) reports state: the Capabilities List bit says a capability chain exists, Interrupt Status shows pending INTx, and the error bits are write-1-to-clear. Both reset to disabled, so software must enable them.
DEEP:
| Register | Bit | Name | Meaning |
|---|---|---|---|
| Command | 0 | I/O Space Enable | Decode I/O BARs |
| Command | 1 | Memory Space Enable | Decode memory BARs. Off means MMIO is not claimed |
| Command | 2 | Bus Master Enable | Function may issue memory and I/O requests |
| Command | 6, 8 | Parity Error Response, SERR# Enable | Error reporting controls |
| Command | 10 | Interrupt Disable | Suppress INTx only. No effect on MSI/MSI-X |
| Status | 3 | Interrupt Status | Reflects INTx state |
| Status | 4 | Capabilities List | Pointer at 34h is valid |
| Status | 8, 11-15 | Master Data Parity Error, Signaled and Received Target Abort, Received Master Abort, Signaled System Error, Detected Parity Error | Sticky error flags, write 1 to clear |

- **Bus Master Enable on an SSD:** an NVMe controller fetches queue entries and moves data by DMA, and its MSI-X interrupts are memory writes too. With BME clear, nothing leaves the device, so the host sees a controller that looks fine on MMIO but never completes commands.
- **Bridges:** on a Type 1 header, Memory Space Enable gates forwarding downstream and Bus Master Enable gates forwarding of upstream requests.
- **Layout trap:** Command is the low half and Status the high half of the DWORD at 04h.
FOLLOW:
- Who sets Bus Master Enable, the BIOS or the OS driver? => Usually the OS, via `pci_set_master()` in Linux, when the driver enables the device. Firmware sets it only when it uses the device, for example to boot from it.
- Does Interrupt Disable stop MSI-X? => No. It only masks INTx. Drivers often set it anyway when they enable MSI-X.
PITFALL: A 32-bit read-modify-write to offset 04h writes back the Status half. Any error bit that was read as 1 is written as 1 and cleared, so you lose evidence. Use 16-bit accesses (`setpci ... COMMAND=...`).
VERIFY: Bit positions against the Command and Status register figures in the Base Specification.

@@ 9.04 | Intermediate | Concept | tags=bar,prefetchable,64-bit,io-space
Q: Explain Base Address Registers: memory versus I/O, 32-bit versus 64-bit, and the prefetchable bit.
SHORT: A BAR tells software how much address space the function needs, and receives the base address software assigns. Bit 0 says memory (0) or I/O (1). For memory BARs, bits 2:1 select 32-bit (00b) or 64-bit (10b, which consumes two consecutive BAR slots), and bit 3 is Prefetchable. Sizes are powers of two and the base must be naturally aligned. A Type 0 header has six slots, a Type 1 header two.
DEEP:
| Field | Memory BAR | I/O BAR |
|---|---|---|
| Bit 0 | 0 | 1 |
| Bits 2:1 | Type: 00b 32-bit, 10b 64-bit | Bit 1 reserved |
| Bit 3 | Prefetchable | part of address (bits 31:2) |
| Address | Bits 31:4 | Bits 31:2 |

- **64-bit BAR:** the low dword sits in slot N and the high dword in slot N+1. A Type 0 header holds at most three of them.
- **Prefetchable:** reads have no side effects and the data can be merged, read ahead or write-combined. The host may map it write-combining, and bridges may place it in the prefetchable window, which is 64-bit capable.
- **Non-prefetchable:** register spaces with side effects, like NVMe controller registers and doorbells. They must be uncached and unmerged, and behind a bridge they must sit in the non-prefetchable window, which is 32-bit only, so below 4 GB.
- **I/O BARs:** legacy. PCIe endpoints such as NVMe SSDs do not need them, and lspci shows `I/O-` in Control.
- **Address meaning:** the BAR holds a bus address. The CPU physical address of the same range can differ if the host bridge translates. `lspci` and `/proc/iomem` show the two views.
FOLLOW:
- Why do NVMe controller registers usually sit in a 64-bit non-prefetchable BAR? => They are register space with side effects, so no prefetching or merging, and 64-bit lets firmware place them anywhere the bridge windows allow.
- What is the ROM BAR? => A separate dword (30h in Type 0) for an option ROM, decoded only when its enable bit is set and Memory Space Enable is on.
PITFALL: Treating prefetchable as a performance hint. It changes which bridge window the BAR lands in and how the CPU may map it, and mismatching it breaks ordering assumptions.

@@ 9.05 | Intermediate | Numeric | tags=bar,sizing,probing,64-bit,worked-example
Q: How does software size a BAR? Work the numbers for a 16 KB 64-bit NVMe BAR0 and a 256 MB prefetchable BAR.
SHORT: Write all ones to the BAR, read it back, and mask off the low type bits (4 for memory, 2 for I/O). The bits the device hardwires to zero are the size bits. Invert what remains and add 1 to get the size. FFFFC000h reads back as 16 KB. A 64-bit BAR needs both dwords probed and 64-bit arithmetic. Do it with decoding disabled and restore the original value afterwards.
DEEP:
1. Save the original BAR value and clear Memory Space Enable (and I/O Space Enable) in Command.
2. Write FFFFFFFFh. Read it back.
3. The low bits tell the type. For memory, mask the low 4 bits (`& ~0xF`). For I/O, mask the low 2.
4. Size = (~masked_value) + 1, computed in the BAR's width.
5. Restore the original value and re-enable decoding.

**Example 1, 32-bit memory:** read back FFFFC000h. Invert gives 00003FFFh, plus 1 is 4000h = 16 KB.

**Example 2, NVMe BAR0 (64-bit, non-prefetchable):** write FFFFFFFFh to BAR0 and BAR1. BAR0 reads FFFFC004h (low nibble 4h: type 10b, prefetchable 0) and BAR1 reads FFFFFFFFh. Combined and masked it is FFFFFFFF_FFFFC000h. Inverted it is 3FFFh, plus 1 is 4000h = 16 KB.

**Example 3, 256 MB prefetchable 64-bit (for example a CMB):** BAR2 reads F000000Ch (type 10b, prefetchable 1), BAR3 reads FFFFFFFFh. Masked: FFFFFFFF_F0000000h. Inverted: 0FFFFFFFh, plus 1 is 10000000h = 256 MB.

- **Edge case:** for a BAR of 4 GB or more the low dword reads back as only the type bits (for example 0000000Ch). 32-bit arithmetic would overflow, so always use 64-bit math on 64-bit BARs.
- **Alignment:** the lowest writable address bit equals the size, so the base must be a multiple of the size. A 256 MB BAR sits on a 256 MB boundary.
FOLLOW:
- What does a BAR that reads back 0 after the all-ones write mean? => It is not implemented (hardwired to zero), so skip it.
- What if the readback is FFFFFFFFh in full? => That is not a 4 GB BAR. It means nothing answered (device gone or link down), so treat it as an error and re-read the Vendor ID.
PITFALL: Sizing a live device without disabling decode. The temporary all-ones base can overlap other resources, and if the sequence is interrupted the BAR is left at a bogus address.
VERIFY: Minimum BAR sizes that the Base Specification allows for memory and I/O BARs.

@@ 9.06 | Intermediate | Concept | tags=bridge,bus-number,windows,routing,type1
Q: What do bus numbers and the memory, prefetchable and I/O windows in a Type 1 header do?
SHORT: Every bridge, root port and switch port describes what lies beneath it. Primary, Secondary and Subordinate Bus Number give the bus range that ID-routed TLPs, such as configuration requests and completions, are forwarded into. The I/O, Memory and Prefetchable Base/Limit pairs give the address ranges that address-routed TLPs are forwarded into. Anything else that arrives from below goes upstream.
DEEP:
- **Bus numbers (18h to 1Ah):** Primary is the bus on the upstream side, Secondary is the bus directly below, Subordinate is the highest bus number anywhere below. A request for bus B goes down if Secondary <= B <= Subordinate.
- **Memory window (20h/22h):** 16-bit Base and Limit hold address bits 31:20, so granularity is 1 MB, 32-bit, non-prefetchable.
- **Prefetchable window (24h/26h):** same 1 MB granularity, with upper 32 bits at 28h and 2Ch, so 64-bit capable.
- **I/O window (1Ch/1Dh):** 4 KB granularity, upper 16 bits at 30h and 32h. Most PCIe endpoints need none.
- **Closed window:** Base above Limit disables it.
- **Direction:** a TLP whose address falls inside a window goes downstream. A TLP that does not, such as DMA to host memory or an MSI write, is forwarded upstream if the bridge's Bus Master Enable is set. Address ranges of sibling ports allow peer-to-peer inside a switch, unless ACS redirects it.

Decoding example: Memory Base = E3B0h and Limit = E3B0h. Base address = E3B0h << 16 = E3B00000h, and the limit address = E3B00000h | FFFFFh = E3BFFFFFh, so a 1 MB window.
FOLLOW:
- Why is the smallest window 1 MB even for a 16 KB BAR? => The Base/Limit registers only hold bits 31:20, so software rounds up, and bridge windows waste address space.
- What does Secondary Bus Reset (Bridge Control) do? => It drives a hot reset on the link below, resetting everything downstream without a power cycle.
PITFALL: Forgetting that Bus Master Enable on a bridge controls upstream forwarding. An SSD can be perfectly configured while a bridge above it with BME clear silently blocks its DMA and MSI writes.
VERIFY: Granularity and register offsets for the I/O window and the reserved bits in the Base/Limit registers.

@@ 9.07 | Intermediate | Concept | tags=capabilities,linked-list,pm,msi,msix,pcie-cap
Q: How does the capability linked list work, and which capabilities does an NVMe SSD expose?
SHORT: If Status bit 4 is set, the byte at offset 34h points to the first capability. Each capability starts with a Capability ID byte and a Next Pointer byte, and the list ends with a next pointer of 00h. Well-known IDs are Power Management 01h, MSI 05h, PCI Express 10h and MSI-X 11h. An NVMe SSD typically shows PM, MSI, PCI Express and MSI-X, with AER in the extended list.
DEEP:
1. Check Status bit 4 (Capabilities List).
2. Read the Capabilities Pointer at 34h. Mask the low two bits, since capabilities are dword aligned.
3. At that offset, read byte 0 (ID) and byte 1 (Next Pointer).
4. Move to Next Pointer and repeat until it is 00h.

| ID | Capability |
|---|---|
| 01h | Power Management |
| 05h | MSI |
| 09h | Vendor Specific |
| 10h | PCI Express |
| 11h | MSI-X |

- **Order is arbitrary:** capabilities may appear anywhere in 40h to FFh. A typical SSD chain is 40h, 50h, 70h, b0h, each pointing to the next.
- **Loop guard:** a broken chain can loop. A robust tool bounds the walk (a 256-byte space can hold at most about 48 capabilities) and rejects pointers below 40h.
- **PCI Express capability location:** it must live in the first 256 bytes, and everything about the PCIe link is reached through it (see the overview question later in this module).
- **Register-level detail:** PM, MSI and MSI-X internals belong to the power management and interrupt modules.
FOLLOW:
- Does the same list logic apply to the Type 1 header? => Yes. The pointer is at 34h in both headers.
- What does `lspci` print for the chain? => `Capabilities: [40] Power Management version 3`, `[50] MSI: ...`, `[70] Express ...`, `[b0] MSI-X: ...`. The number in brackets is the offset.
PITFALL: Assuming a capability sits at a fixed offset. Offsets differ per vendor and per firmware version, so always walk the list.
VERIFY: Capability ID values (01h, 05h, 09h, 10h, 11h) and the bit position of Status.Capabilities List against the PCI Code and ID Assignment Specification and the Base Specification.

@@ 9.08 | Intermediate | Concept | tags=extended-capabilities,aer,sriov,ats,dsn,l1-substates
Q: How is the extended capability list organized, and which extended capabilities matter for SSD validation?
SHORT: Extended capabilities start at offset 100h. Each begins with a 32-bit header: a 16-bit Capability ID, a 4-bit Version and a 12-bit Next Capability Offset, which is dword aligned and 0 at the end of the chain. Common ones are AER, Device Serial Number, SR-IOV, ATS, Secondary PCI Express, L1 PM Substates, Latency Tolerance Reporting, and the Physical Layer and Lane Margining capabilities at Gen4 and above.
DEEP:
- **Header layout:** bits 15:0 ID, bits 19:16 Version, bits 31:20 Next offset. The first is always at 100h, next pointers are at least 100h, and 0 ends the chain.
- **Version matters:** the same ID with a higher version has more registers, so read the version before you parse.
- **No extended capabilities:** the dword at 100h reads as zero. If it reads all ones on a device that is otherwise alive, the platform is probably not reaching the extended space (ECAM problem).

| ID | Capability | Why an SSD validator cares |
|---|---|---|
| 0001h | Advanced Error Reporting | Error status, masks, header log |
| 0003h | Device Serial Number | Identify a unit across resets |
| 000Eh | ARI | Function numbering above 7 |
| 000Fh | ATS | Address translation for DMA |
| 0010h | SR-IOV | Virtual functions on enterprise SSDs |
| 0018h | Latency Tolerance Reporting | Power state gating |
| 0019h | Secondary PCI Express | Gen3+ lane equalization status |
| 001Eh | L1 PM Substates | L1.1 and L1.2 |
| 0026h | Physical Layer 16.0 GT/s | Gen4 eq status |
| 0027h | Lane Margining at the Receiver | Margin tests |

- **Where they go:** register-level details for errors, power and virtualization are in later modules. Here the point is to find them.
FOLLOW:
- How do you find a specific extended capability? => Walk the chain from 100h comparing IDs, as `setpci ECAP_AER` and `lspci -vvv` do.
- What about the Vendor-Specific Extended Capability and DVSEC? => Both give vendors their own structures with a standard header. The DVSEC carries a vendor ID and a DVSEC ID, and is how CXL exposes its structures.
PITFALL: Copying the ID table from memory into a tool. Verify against the spec revision and handle unknown IDs by skipping them, not by aborting the walk.
VERIFY: All extended capability ID values and versions in this table against the PCI Code and ID Assignment Specification and the Base Specification, including the IDs added after 5.0.

@@ 9.09 | Intermediate | Debug | tags=lspci,setpci,linux,windows,tools,sysfs
Q: How do you read and interpret config space in practice on Linux and Windows? Interpret this `lspci` snippet.
SHORT: On Linux run `lspci -vvv -s <BDF>` as root for decoded output, `lspci -xxxx` for the raw 4 KB, and `setpci` to read or write single registers. Read the Control and Status lines for enables, the Region lines for BAR addresses and sizes, then LnkCap against LnkSta for link state. On Windows use Device Manager (Resources and Details tabs), WinDbg `!pci`, or vendor and third-party PCI dump utilities.
DEEP:
```
3b:00.0 Non-Volatile memory controller (prog-if 02 [NVM Express])
    Control: I/O- Mem+ BusMaster+ ... DisINTx+
    Status: Cap+ ... INTx-
    Region 0: Memory at e3b00000 (64-bit, non-prefetchable) [size=16K]
    Capabilities: [70] Express Endpoint
        LnkCap: Speed 16GT/s, Width x4
        LnkSta: Speed 8GT/s (downgraded), Width x4
    Capabilities: [b0] MSI-X: Enable+ Count=129 Masked-
        Vector table: BAR=0 offset=00002000
```
- **Reading it:** the driver has enabled Mem and BusMaster. DisINTx+ means INTx is off and MSI-X is in use (Enable+, 129 vectors, table in BAR0 at 2000h). BAR0 is 16 KB.
- **The problem:** LnkSta is 8 GT/s but LnkCap is 16 GT/s. Check the other end: read the root port's LnkCap first, because a Gen3 slot makes this normal. Then check the target speed in Link Control 2 and equalization status in Link Status 2 and the Secondary PCI Express capability (see the link modules).
- **Commands:**
  - `lspci -nn -tv` shows the tree with IDs, `-D` adds the domain.
  - `lspci -xxx -s 3b:00.0` dumps 256 bytes, `-xxxx` dumps 4096.
  - `setpci -s 3b:00.0 COMMAND` reads Command, `COMMAND=0004:0004` sets Bus Master, and `CAP_EXP+10.w` reads Link Control.
  - `/sys/bus/pci/devices/0000:3b:00.0/config` is the raw file, and `resource0` is BAR0.
- **Windows:** Device Manager, Details, "Location paths" and "Hardware Ids" (with `CC_010802`), Resources for memory range and IRQ, `!pci` in kernel debugging.
FOLLOW:
- Why does `lspci` show `<access denied>` for capability details? => Non-root users can read only the first 64 bytes through sysfs. Run as root.
- Is it safe to run `setpci` writes on a live SSD? => Only on registers you understand. Writing Command or Link Control while the driver runs can hang the device or the link.
PITFALL: Reading LnkSta as if it described the whole path. Each end reports its own, and downgraded compares only against that device's own LnkCap.
VERIFY: `setpci` symbolic names such as `CAP_EXP` and `ECAP_AER` for your pciutils version, and the WinDbg `!pci` flags for your debugger version.

@@ 9.10 | Advanced | Concept | tags=pcie-capability,mps,mrrs,device-control,link-control
Q: What is in the PCI Express capability structure, and which registers must enumeration software program?
SHORT: The PCI Express capability (ID 10h) holds the PCIe-specific controls: the device and port type, Device Capabilities and Control (Max Payload Size, Max Read Request Size, Relaxed Ordering Enable, Extended Tag Field Enable), Link Capabilities, Control and Status, and the second-generation Device, Link and Slot registers. Software programs MPS and MRRS to be consistent across the hierarchy and leaves Link Control mostly to link management.
DEEP:
| Offset in capability | Register |
|---|---|
| 02h | PCI Express Capabilities (version, device/port type) |
| 04h, 08h, 0Ah | Device Capabilities, Control, Status |
| 0Ch, 10h, 12h | Link Capabilities, Control, Status |
| 24h, 28h, 2Ah | Device Capabilities 2, Control 2, Status 2 |
| 2Ch, 30h, 32h | Link Capabilities 2, Control 2, Status 2 |

- **Device Control:** Max Payload Size (bits 7:5), Enable Relaxed Ordering (bit 4), Extended Tag Field Enable (bit 8), Max Read Request Size (bits 14:12), error reporting enables, Initiate FLR.
- **MPS encoding:** 000b is 128 B, 001b 256 B, then 512 B, 1024 B, 2048 B, 4096 B. A TLP payload above the receiver's MPS is a Malformed TLP.
- **MRRS:** limits the size of read requests a device issues. An NVMe SSD reads host memory for commands, PRP lists and write data, so its MRRS affects write performance.
- **Link registers:** Link Capabilities gives max speed and width and ASPM support, Link Control holds ASPM Control, Retrain Link and Common Clock Configuration, and Link Status holds Current Link Speed, Negotiated Link Width, Link Training and Data Link Layer Link Active. Details were covered in the LTSSM and equalization modules.
- **Control 2:** Completion Timeout value, ARI Forwarding Enable, and Target Link Speed in Link Control 2.
- **Port-only registers:** Slot and Root registers exist only for ports that need them.
FOLLOW:
- Who decides the MPS for a path? => Enumeration software, which sets each device's MPS to at most what every device it may talk to accepts, usually the minimum along the path.
- Where do you see Relaxed Ordering used? => The device sets an attribute bit in memory write TLPs if Enable Relaxed Ordering is on. Its effect is covered in the ordering module.
PITFALL: Assuming a larger MPS on the SSD than on the root complex is harmless. Its writes exceed the receiver's limit and are dropped as Malformed TLPs, which can look like a data corruption bug.
VERIFY: Register offsets and bit positions within Device Capabilities, Control and Control 2 against the PCI Express Capability Structure figure in the Base Specification.

@@ 9.11 | Advanced | Numeric | tags=ecam,mcfg,addressing,ari
Q: How does ECAM map bus, device, function and register into a memory address, and how large is it?
SHORT: The address is base + (bus << 20) + (device << 15) + (function << 12) + register offset. That gives 4 KB per function, 1 MB per bus (32 devices x 8 functions x 4 KB) and 256 MB for 256 buses in one segment. The base comes from the ACPI MCFG table. Example: 03:1C.2 register 10h with base C0000000h is C03E2010h. With ARI the device and function bits form one 8-bit function number.
DEEP:
1. Fields: bus is 8 bits (27:20), device is 5 bits (19:15), function is 3 bits (14:12), and the register is 12 bits (11:0).
2. Example 1, bus 03h, device 1Ch, function 2, register 10h (BAR0), base C0000000h:
   - 03h << 20 = 00300000h
   - 1Ch << 15 = 000E0000h
   - 2 << 12 = 00002000h
   - Sum with 10h: 003E2010h, so address C03E2010h.
3. Example 2, 3B:00.0 register 100h (first extended capability), base E0000000h: 3Bh << 20 = 03B00000h, so address E3B00100h.
4. Sizes: 4 KB x 8 x 32 = 1 MB per bus. 1 MB x 256 buses = 256 MB per segment. If firmware limits the range to 64 buses, it reserves 64 MB.

- **Segments:** MCFG has one entry per PCI segment (domain), each with a base, segment number and bus range. `lspci` shows the domain as the leading `0000:`.
- **ARI:** bits 19:12 become an 8-bit function number. For example function 45h on bus 3Bh, register 10h gives E3B45010h.
- **Access rules:** map it uncached, use naturally aligned 1, 2 or 4 byte accesses that do not cross a dword, and expect the root complex to turn each into one CfgRd or CfgWr TLP.
- **Linux log:** `PCI: MMCONFIG for domain 0000 [bus 00-ff] at [mem 0xe0000000-0xefffffff]` shows the range.
FOLLOW:
- What does ECAM cost in address space? => Up to 256 MB of address space for a full 256-bus segment (usually placed below 4 GB, though the MCFG base can be higher), which is why firmware trims the bus range on some platforms.
- What if the ECAM region is not mapped or wrong? => Reads return all ones, extended capabilities vanish while the first 256 bytes may still work through CF8h/CFCh.
PITFALL: Forgetting the segment. Two devices on different segments can have the same bus/device/function, so a tool must key on the full domain:bus:device.function.
VERIFY: MCFG table format and the requirement for the uncached mapping in the ACPI and PCI Firmware specifications.

@@ 9.12 | Advanced | Concept | tags=cfgrd,cfgwr,type0,type1,ari,routing
Q: What are Type 0 and Type 1 configuration requests, how does a bridge convert one into the other, and what does ARI change?
SHORT: Configuration requests are single-dword non-posted TLPs routed by bus, device and function. A Type 0 request (CfgRd0 or CfgWr0) is for a function on the link it arrives on. A Type 1 request (CfgRd1 or CfgWr1) is for something below a bridge. A bridge receiving Type 1 for its Secondary bus converts it to Type 0, and forwards it unchanged if the bus is deeper. ARI turns device and function into one 8-bit function number.
DEEP:
- **TLP format:** 3 DW header, Fmt/Type CfgRd0 = 000 00100b, CfgWr0 = 010 00100b, CfgRd1 = 000 00101b, CfgWr1 = 010 00101b. The target is in DW2 (bus 31:24, device 23:19, function 18:16, register number in the low bits) with a length of 1 DW.
- **Completions:** a read returns CplD, a write returns Cpl. Unsupported Request means nothing decoded it, and CRS means it is not ready (see the reset readiness question).
- **Bridge decision on receiving Type 1 from upstream:**
  1. Bus equals Secondary: convert to Type 0 and send down.
  2. Bus in Secondary+1 to Subordinate: forward as Type 1.
  3. Otherwise: not for this port, complete with UR (or ignore).
- **Type 0 arriving at a bridge:** it is for the bridge's own config space.
- **One device per link:** a PCIe downstream port forwards only device 0 to the link partner, so a non-ARI enumerator scanning devices 1 to 31 below a root or switch port gets UR. Bus 0 and the internal bus of a switch do hold several devices.
- **ARI (Alternative Routing-ID Interpretation):** the 8 bits of device and function form a function number, so one device can have up to 256 functions. A downstream port needs ARI Forwarding Enabled in Device Control 2. Functions are found by following the ARI capability's Next Function Number chain. SR-IOV uses it for many virtual functions.
FOLLOW:
- Which config request does the root complex use for a device directly below a root port? => Type 0 if the bus equals the root port's Secondary bus, Type 1 if the target is deeper.
- Why is ARI needed for SR-IOV SSDs? => Eight functions are too few for many virtual functions, so ARI provides up to 256 per bus without extra bus numbers.
PITFALL: Assuming a Type 1 request changes at each hop. It stays Type 1 until the bridge whose Secondary bus is the target.
VERIFY: Fmt/Type encodings, the UR versus drop behavior for out-of-range Type 1 requests, and the device-number handling with ARI Forwarding in the Base Specification.

@@ 9.13 | Principal | Scenario | tags=enumeration,depth-first,bus-numbers,windows,mps,hotplug
Q: Walk through how software enumerates a root port, a switch and two NVMe SSDs, including the bus numbers and windows it programs.
SHORT: Enumeration is a depth-first scan. At each bridge software assigns a Secondary bus number, scans below it, and only then knows the Subordinate number to program. Endpoints get their BARs sized. On the way back up each bridge's memory window is set to cover its children. Finally software programs MPS across the hierarchy and enables Command bits. In this example the buses are numbered 1 to 4 and each SSD port gets a 1 MB window.
DEEP:
Topology: Root port RP (00:1C.0), a switch upstream port USP (bus 1), a switch internal bus 2 with downstream ports DSP-A (02:01.0) and DSP-B (02:02.0), and SSD1 and SSD2, each a 16 KB 64-bit non-prefetchable BAR0.
1. RP: Primary 0, Secondary 1, Subordinate temporarily FFh. Scan bus 1.
2. USP: Primary 1, Secondary 2, Subordinate FFh. Scan bus 2.
3. DSP-A: Primary 2, Secondary 3, Subordinate FFh. SSD1 at 03:00.0: size BAR0 (16 KB). DSP-A Subordinate = 3.
4. DSP-B: Primary 2, Secondary 4, SSD2 at 04:00.0. Subordinate = 4.
5. Back up: USP Subordinate = 4, and RP Subordinate = 4. (A hot-plug reserve would raise them.)
6. Windows: each SSD needs 16 KB, but a bridge window rounds to 1 MB, so DSP-A gets 1 MB, DSP-B 1 MB, USP 2 MB and RP 2 MB. For example the RP window E0000000h to E01FFFFFh, DSP-A E0000000h, DSP-B E0100000h, giving SSD1 BAR0 at E0000000h and SSD2 at E0100000h.
7. Configure: MPS and MRRS across the tree, ARI Forwarding where devices support it, Interrupt Line, then Memory Space Enable and Bus Master Enable, starting from the endpoints and going up.

- **Why depth-first:** the Subordinate number is only known after the scan below finishes.
- **Packing:** allocate the largest BARs first, since each must be naturally aligned. 64-bit non-prefetchable BARs must sit below 4 GB, since bridge memory windows are 32-bit.
- **Hot-plug:** firmware reserves extra bus numbers and window space on hot-plug bridges (Linux `pci=hpbussize=`, `hpmemsize=`), or a later hot-add has nowhere to go.
- **Failure modes:** Above 4G Decoding off with large prefetchable BARs, or too few bus numbers in a deep switch tree.
FOLLOW:
- Which MPS do you choose? => The largest value every device on the path supports, so no receiver sees an oversize payload. Linux offers `pci=pcie_bus_safe` and `pcie_bus_perf`.
- Who does this, BIOS or OS? => Usually both. The BIOS enumerates to boot, and the OS either trusts it or reassigns (`pci=realloc`).
PITFALL: Setting Subordinate to the current bus before scanning below. Type 1 requests to devices deeper in the tree are never forwarded, and downstream devices look missing.
VERIFY: Linux boot parameter names (`hpbussize`, `hpmemsize`, `realloc`, `pcie_bus_safe`, `pcie_bus_perf`) for your kernel version.

@@ 9.14 | Advanced | Trap | tags=crs,reset,readiness,100ms,vendor-id
Q: You read the Vendor ID 20 ms after reset and get FFFFh or 0001h. Is the SSD dead?
SHORT: Not necessarily. After a reset a device may not be ready, so it answers configuration requests with Configuration Request Retry Status (CRS). If CRS Software Visibility is enabled, the root complex returns 0001h for a Vendor ID read to say retry later. FFFFh means nobody answered, which can mean a dead link. Software should wait at least 100 ms after reset, then retry, and only after about 1 s of failure treat it as broken.
DEEP:
- **CRS:** a completion status a device returns for a configuration request while it is initializing. Without software visibility, the root complex retries in hardware. With CRS Software Visibility Enable in Root Control, a read of the 2-byte Vendor ID returns 0001h and software polls.
- **Timing rules (spec-sensitive):**
  - Software waits 100 ms after a reset before the first configuration request. For links above 5 GT/s it counts from link-up (Data Link Layer Link Active), not from the end of reset.
  - A device must be able to finish a first configuration request with success or CRS within about 1 s.
  - Functional Level Reset has a similar 100 ms budget.
- **Read what came back:** 0001h from a Vendor ID read means CRS. FFFFh means UR or no response: no device, link down or a broken route.
- **Three readiness levels for NVMe:** the link is up, then config space answers, then MMIO registers and CSTS.RDY come ready. CSTS.RDY has its own timeout (CAP.TO), independent of the PCIe rules.
- **Why SSDs matter:** an SSD firmware boot after an unsafe power loss can rebuild metadata, taking much longer than a clean boot. Firmware that returns nothing instead of CRS, or a BIOS that gives up early, shows up as a missing drive that a later rescan finds.
- **Measure it:** loop on Vendor ID reads from PERST# deassertion and log CRS count and time to the first valid read across temperature and power-loss states.
FOLLOW:
- Does the endpoint have to return CRS? => It is allowed to while not ready. A device that returns neither CRS nor completions within the limit is out of spec.
- Can you rescan later? => Yes: `echo 1 > /sys/bus/pci/rescan`. If the device appears, the fault is readiness timing rather than link or hardware.
PITFALL: Declaring failure at the first FFFFh. The right test distinguishes CRS, UR and link-down using the completion status, the root port link status and a deadline.
VERIFY: The 100 ms and 1 s values, the Data Link Layer Link Active based timing for greater than 5 GT/s, the FLR timing and the CRS Software Visibility bits in the Base Specification.

@@ 9.15 | Advanced | Cross-layer | tags=nvme,bar0,cmb,capabilities,doorbell,msix
Q: How do NVMe controller registers map onto PCIe BAR0, what capabilities does an NVMe SSD expose, and how does a CMB affect BAR sizing?
SHORT: NVMe controller registers (CAP, VS, INTMS, INTMC, CC, CSTS, AQA, ASQ, ACQ and more) are memory-mapped from the start of a 64-bit non-prefetchable BAR0, with doorbells at offset 1000h. Its size is the register block plus the doorbells, rounded up to a power of two and at least 16 KB. A CMB adds a separate memory region in a BAR named by its Base Indicator Register, which can force a large prefetchable BAR and Above 4G Decoding.
DEEP:
| BAR0 offset | Register |
|---|---|
| 00h | CAP (Controller Capabilities, 8 bytes) |
| 08h | VS (Version) |
| 0Ch, 10h | INTMS, INTMC |
| 14h, 1Ch | CC, CSTS |
| 24h, 28h, 30h | AQA, ASQ, ACQ |
| 38h, 3Ch | CMBLOC, CMBSZ |
| 1000h | Doorbells |

- **Doorbell footprint:** one submission tail and one completion head doorbell per queue, each `4 << CAP.DSTRD` bytes. With DSTRD = 0 that is 8 bytes per queue pair.
- **BAR0 size example:** admin plus 128 I/O queue pairs = 129 pairs x 8 B = 1032 B. 4096 + 1032 = 5128 B, so a 16 KB BAR. For 65,535 I/O queue pairs: 4096 + 65,536 x 8 = 528,384 B, which rounds up to 1 MB.
- **Capabilities usually seen:** Power Management, MSI, PCI Express and MSI-X, plus AER in the extended list, and sometimes SR-IOV, DSN, L1 PM Substates and vendor structures.
- **MSI-X table and PBA:** they may share BAR0 after the doorbells or live in another BAR (check lspci `Vector table: BAR=`). Doorbell pages and MSI-X tables should not share a 4 KB page.
- **CMB:** the Controller Memory Buffer is on-SSD memory the host can use for queues or data, located by CMBLOC and sized by CMBSZ. A 256 MB CMB needs a 256 MB, naturally aligned BAR.
- **Resource failure:** if firmware cannot place that BAR (window too small, or Above 4G Decoding disabled for a 64-bit prefetchable BAR), the kernel logs `BAR n: no space for [mem size ...]` and the controller may not probe at all.
FOLLOW:
- Why do doorbells start at 1000h? => The specification places the doorbell array right after the 4 KB controller register block, so it starts at 1000h and grows with the number of queues.
- Where do you see BAR0 in `lspci`? => `Region 0: Memory at ... (64-bit, non-prefetchable) [size=16K]`.
PITFALL: Assuming the BAR0 size shows the number of queues. It only bounds the doorbell area, and the actual queue count comes from CAP, Set Features, and the interrupt vectors available.
VERIFY: CMBLOC and CMBSZ fields (the Base Indicator Register and whether a CMB may share BAR0), the doorbell stride formula, the 16 KB minimum, and the location of PCIe-specific requirements in the NVMe over PCIe Transport specification versus the Base Specification 2.x.

@@ 9.16 | Advanced | Debug | tags=all-ones,ffffffff,bar,mmio,link-down,nvme
Q: An MMIO read of a BAR, or a config read, returns FFFFFFFFh. What can that mean and how do you narrow it down?
SHORT: All ones is what the platform returns when a read fails or is not answered. It can mean no device, link down or in Recovery, a read that timed out or was completed with UR or Completer Abort, MMIO with Memory Space Enable off or the BAR outside a bridge window, or a device in reset or a low power state. Check config space first: if Vendor ID also reads FFFFh, the function is gone from the bus. If config is fine, look at decode and the bridge path.
DEEP:
| Observation | Likely meaning |
|---|---|
| Vendor ID reads FFFFh | No answer: absent, link down, in reset, powered off, or bad bus routing |
| Vendor ID valid, BAR0 MMIO reads FFFFFFFFh | Decode or path problem, or the device ignores MMIO |
| Vendor ID reads 0001h | CRS: device not ready yet, retry |
| Only some reads FFFFFFFFh | Intermittent link, retraining or a timeout |

Steps for the second row:
1. Read Command: is Memory Space Enable set? Read the BAR: is it programmed inside the parent's window?
2. Read each bridge above: Memory Base/Limit covers the BAR, Memory Space Enable set, and no closed window.
3. Read the parent's Link Status: Link Training, Data Link Layer Link Active and current speed. A link in Recovery gives timeouts.
4. Read the PM Control/Status power state (D3hot disables memory decode).
5. Check root port AER for Unsupported Request or Completion Timeout, and dmesg for `surprise down` or DPC events.
6. Check FLR or reset in progress and controller state (CSTS.CFS).

- **NVMe hint:** Linux logs `nvme nvme0: controller is down; will reset: CSTS=0xffffffff, PCI_STATUS=0xffff`. A PCI_STATUS of ffff means config is also gone (device removed or link dead). A valid PCI_STATUS with CSTS all ones points to decode, path or reset.
- **Sizing trap:** a BAR sizing tool that reads FFFFFFFFh back should report "no device", not "4 GB".
FOLLOW:
- Why does the CPU get all ones instead of an error? => On x86 the host bridge completes a failed read with all ones and, unless configured to report, no exception is raised. Look at AER and platform error logs.
- How do you tell a link drop from a controller crash? => Link down shows Data Link Layer Link Active clear and config reads fail. A controller crash leaves config alive with the NVMe controller fatal status set.
PITFALL: Stopping at "device gone". A device with a valid Vendor ID and MMIO all ones is alive at the PCIe level, and the root cause is usually decode, reset or power state, not the link.
VERIFY: The exact Linux nvme driver message text on your kernel, and how your platform reports failed MMIO reads.

@@ 9.17 | Principal | Scenario | tags=cold-boot,missing-device,crs,perst,triage,reliability
Q: An SSD sometimes does not appear after a cold boot, about one boot in 200. How do you find the cause?
SHORT: Split the failure by how far the device got: power and reset sequencing, link training, configuration readiness (CRS or an early BIOS timeout), then resource assignment. On a failed boot, check whether a later `rescan` finds the device, what the root port link status says and what the BIOS and kernel logs show. Then reproduce with automated power cycling. At 1/200 you need about 600 boots for a 95 percent chance to see one failure.
DEEP:
1. **Statistics first:** P(at least one failure in n boots) = 1 - (1 - 1/200)^n. For 95 percent, n = ln(0.05) / ln(0.995) = about 598, so run roughly 600 cycles. A relay-controlled power cycler makes that a day's work.
2. **Classify each failure:**

| Evidence on failed boot | Points to |
|---|---|
| Rescan finds it, no link errors | Readiness timing (CRS, firmware boot time, BIOS wait) |
| Link down, LTSSM stuck in Detect or Polling | Power, PERST# or REFCLK sequencing, connector, retimer |
| Link up, config reads all ones | Reset timing, device stuck, wrong routing |
| Config fine, BAR not assigned in dmesg | Resource allocation, Above 4G Decoding, window sizes |
| Device in a lower speed or width | Link training or equalization (see the link modules) |

3. **Capture:** scope or logic analyzer on power good, REFCLK and PERST#, an analyzer or on-chip LTSSM log, BIOS POST codes, early `dmesg`, and `lspci -vvv` before and after `rescan`.
4. **Correlate:** temperature, time since previous power-off, unsafe power loss history, firmware and BIOS version.
5. **Bracket the margin:** add delay between power good and PERST# deassert, or extend the BIOS wait, and see whether the rate moves. Log the device's time to first valid config read.
6. **Fix owners:** firmware (respond with CRS, faster boot), BIOS (wait time, sequencing) or hardware (rails, reference clock).

- **Decision rule:** if failure rate depends strongly on delay margin, it is a timing race, and fix ownership follows from which side is late.
FOLLOW:
- What if `rescan` never finds the drive? => Then it is at link or hardware level. Read the root port link state and LTSSM and follow the link triage from the earlier modules.
- Is the 95 percent figure enough? => It is for finding the failure. For qualifying a fix you need enough clean cycles to bound the failure rate, so several thousand.
PITFALL: Treating it as one bug. Missing on a cold boot has at least four distinct causes, and one rate hides all of them.
VERIFY: PERST# and power-good timing requirements in the CEM specification for your form factor.

@@ 9.18 | Principal | Scenario | tags=automation,regression,golden,masks,config-space,volatile,sticky
Q: How would you design an automated config-space regression tool that diffs against a golden image across resets and power states?
SHORT: Capture the full 4 KB of every function, decode it with the capability walk, and compare against a golden per-field, not per-byte. Each field gets a rule: exact match, masked, expected range or ignore. Volatile fields such as Status error bits, link status, AER status and BAR base addresses are masked or checked against expectations instead. Capture after cold boot, warm reset, hot reset, FLR, D3hot to D0 and link retrain, and flag any difference that is not an allowed one.
DEEP:
- **Capture:** read via sysfs `config` or `lspci -xxxx` as root, retry until Vendor ID is valid (CRS aware), read twice and require agreement, keyed by domain:bus:device.function. Store the raw bytes plus the decoded capability chain and BAR sizes.
- **Golden creation:** capture the same unit many times with no change, XOR the runs, and mark bits that flip as candidate volatile. A human reviews them. Keep one golden per firmware version and platform.
- **Field rules:**

| Class | Examples | Rule |
|---|---|---|
| Must match exactly | Vendor, Device, Subsystem IDs, Revision, Class Code, Header Type, capability chain and versions, most capability registers, BAR type and size | Exact |
| Depends on OS or BIOS | BAR base address, Command, Cache Line Size, Interrupt Line, MPS, MRRS, MSI address and data | Check validity (aligned, in window), not equality |
| Volatile | Status flags, Device Status, Link Status bits (Link Training, sticky Link Bandwidth flags), AER status and header log, PM status | Mask |
| Expected value | Current Link Speed and Width | Compare against the target, not the golden |
| Reserved | Reserved bits | Must read zero |

- **Reset expectations:** FLR, hot reset and D3hot to D0 (when it causes a soft reset) return non-sticky registers to defaults, so compare to the default golden and then to the post-driver golden. Sticky registers (AER status, some link and PM bits) survive resets but clear on fundamental reset without auxiliary power.
- **Reporting:** decoded diff (field name, old, new, severity), and pass or fail per reset type. Store history to spot drift by firmware build.
FOLLOW:
- What is the risk of masking too much? => Hiding real bugs. Masking the whole Link Status hides a downgrade, so use expected-value checks instead.
- How do you avoid false positives from the OS? => Compare only fields the OS should not change, and capture before the driver loads for pure device-owned state.
PITFALL: Diffing raw hex. Status and sticky bits change on every run, and the tool cries wolf until people stop reading it.
VERIFY: Which registers are sticky and which reset on hot reset, FLR and fundamental reset (per register attribute definitions such as RW1CS) in the Base Specification.
