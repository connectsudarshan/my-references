# Module 5: Condition Variables & Signaling

@@ 5.01 | Basic | Concept | tags=condvar,wait,atomic-release
Q: What does pthread_cond_wait() actually do to the mutex you pass it?
SHORT: It atomically releases the mutex and blocks the calling thread on the condition variable, so no other thread can slip in between "I released the lock" and "I started waiting" and have a signal go unseen; when it returns, the mutex has been re-acquired and is owned by the calling thread again. The mutex must already be locked by the caller when pthread_cond_wait() is called, or the behavior is undefined.
DEEP:
- POSIX's own wording: "These functions atomically release mutex and cause the calling thread to block on the condition variable cond; atomically here means 'atomically with respect to access by another thread to the mutex and then the condition variable.'"
- The practical consequence: if another thread acquires the mutex right after the about-to-block thread releases it (inside the wait call), a pthread_cond_signal() or pthread_cond_broadcast() that thread then issues is guaranteed to behave as if it happened after the first thread was already waiting -- the "unlock, then wait" transition is a single indivisible step from an observer's point of view, not two separate steps with a gap.
- On successful return, "the mutex shall have been locked and shall be owned by the calling thread" -- you never need to re-lock it yourself after a cond_wait returns.
- A condition variable becomes dynamically bound to whichever mutex the first waiting thread used, for as long as any thread is waiting on it; using a second, different mutex concurrently with the same cond var is undefined behavior.
FOLLOW:
- Why does this atomicity matter instead of just calling unlock() then wait() as two separate calls? => Two separate calls leave a window where another thread could lock the mutex, change the shared state, signal, and unlock, all before the first thread's separate wait() call ever runs -- exactly the lost-wakeup bug in 5.04, which is why POSIX bundles unlock-and-wait into one atomic operation.
- Must the SAME mutex be passed on every call to pthread_cond_wait() for a given cond var? => Yes while any thread is waiting; the binding is dynamic and ends when the wait returns, but concurrent waits on the same cond var with different mutexes is explicitly undefined behavior.
PITFALL: Manually calling pthread_mutex_unlock() followed by pthread_cond_wait() as two statements instead of trusting cond_wait to do the release atomically. That reintroduces exactly the race the atomic release exists to prevent.
VERIFY: POSIX.1-2017, pthread_cond_wait() DESCRIPTION (the "atomically release mutex" paragraph and the mutex-binding paragraph).

@@ 5.02 | Basic | Concept | tags=condvar,predicate-loop,mandatory
Q: Why must every pthread_cond_wait() call be wrapped in a while loop that re-checks a predicate, never a bare wait?
SHORT: POSIX documents that "spurious wakeups... may occur" and that "a return from the wait does not imply that the associated predicate is either true or false" -- a thread can wake with nothing actually changed. A bare wait can proceed on stale state, and if used before the predicate is checked at all it can also miss a signal that already happened (5.04's lost wakeup), so the standard's own recommendation is a while loop around the wait, always.
DEEP:
- The correct shape, used identically everywhere a condition variable appears in real code: lock the mutex, `while (!predicate) pthread_cond_wait(&cond, &mtx);`, then act on the now-true predicate, still holding the mutex.
- "It is thus recommended that a condition wait be enclosed in the equivalent of a 'while loop' that checks the predicate" -- POSIX's own RATIONALE, stated as a direct recommendation, not left to interpretation.
- The loop simultaneously defends against two distinct problems: a spurious wakeup (5.05, waking with no real state change) and a superfluous signal/broadcast issued by some other part of the application on the same cond var that was not meant for this waiter.
- Checking the predicate before the first wait call also matters: if the predicate is already true when a thread arrives, it should proceed immediately without ever calling pthread_cond_wait() at all, which is exactly what the while-loop's initial condition check gives you for free.
FOLLOW:
- Is a plain `if` instead of `while` ever safe here? => No; `if` checks the predicate once, either before or after a single wait call, and does not re-check after that wait returns, so it is exposed to exactly the spurious-wakeup and superfluous-signal risks a `while` loop is designed to close.
- Does the loop need a timeout to be "safe"? => Not for correctness against spurious wakeups; a timeout (pthread_cond_timedwait()) is a separate, optional feature for bounding how long you are willing to wait at all, unrelated to the predicate-loop requirement.
PITFALL: Writing `if (!predicate) pthread_cond_wait(...)` instead of `while (!predicate) pthread_cond_wait(...)`. It looks nearly identical and passes casual testing, but is not safe against spurious wakeups or superfluous signals.
VERIFY: POSIX.1-2017, pthread_cond_timedwait()/pthread_cond_wait() RATIONALE, "Condition Wait Semantics" subsection.

@@ 5.03 | Basic | Concept | tags=signal,broadcast,difference
Q: What is the basic difference between pthread_cond_signal() and pthread_cond_broadcast()?
SHORT: pthread_cond_signal() unblocks "at least one" of the threads waiting on the condition variable, chosen by the scheduling policy; pthread_cond_broadcast() unblocks all of them. Both have no effect at all if no thread is currently blocked on that condition variable -- the call is not queued or remembered for a future waiter.
DEEP:
- Exact wording: "The pthread_cond_broadcast() function shall unblock all threads currently blocked on the specified condition variable cond," while "pthread_cond_signal()... shall unblock at least one of the threads that are blocked... (if any threads are blocked on cond)."
- "At least one" is deliberate: POSIX's RATIONALE explains that on a multiprocessor, an implementation of cond_signal cannot always avoid waking more than one thread (this is exactly where "spurious wakeup," 5.05, comes from at the specification level), so the standard says "at least one" rather than "exactly one."
- "These functions... shall have no effect if there are no threads currently blocked on cond" -- signaling into an empty room is a silent no-op, not an error and not something a later waiter will see; this is precisely the mechanism behind the lost-wakeup bug (5.04).
- Every thread woken by either call re-acquires the associated mutex before returning from cond_wait, contending for it "as if each had called pthread_mutex_lock()" -- broadcast does not mean all woken threads run at once, only that all of them are made runnable and will each, in turn, get the mutex and re-check their predicate.
FOLLOW:
- If broadcast wakes everyone, doesn't that waste work compared to signal? => Only the thread(s) whose predicate actually becomes true after re-acquiring the mutex do useful work; the rest re-check their while-loop condition, find it still false, and go back to waiting -- correct, but with the CPU cost of waking threads that had nothing to do.
- When must you use broadcast instead of signal? => Whenever more than one waiter's predicate could become true from the same state change (5.08's producer/multi-consumer case), or when different waiters are blocked on different predicates sharing one cond var (5.14) -- signal alone risks waking the wrong one.
PITFALL: Defaulting to pthread_cond_signal() everywhere because "there's usually only one waiter," without checking whether that assumption actually holds for every caller of the code, now and after future changes.
VERIFY: POSIX.1-2017, pthread_cond_signal()/pthread_cond_broadcast() DESCRIPTION.

@@ 5.04 | Intermediate | Trap | tags=lost-wakeup,demo,predicate,bare-wait
Q: Reproduce an actual lost wakeup in a compiled program, then fix it.
SHORT: A producer thread sets a flag and signals before the consumer thread has even started; a consumer that does a bare pthread_cond_wait() (no predicate check) then blocks forever, since the signal already fired into an empty room and "shall have no effect if there are no threads currently blocked on cond." Making the consumer check the predicate first (`while (!ready) pthread_cond_wait(...)`) fixes it deterministically: it sees ready is already 1 and never waits at all.
DEEP:
```c
#define _POSIX_C_SOURCE 200809L
#include <stdio.h>
#include <pthread.h>

static pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t cond = PTHREAD_COND_INITIALIZER;
static int ready = 0;
static int use_predicate = 0;

static void *producer(void *arg) {
    (void)arg;
    pthread_mutex_lock(&mtx);
    ready = 1;
    pthread_cond_signal(&cond);   /* fires while nobody is waiting yet */
    pthread_mutex_unlock(&mtx);
    return NULL;
}

static void *consumer(void *arg) {
    (void)arg;
    pthread_mutex_lock(&mtx);
    if (use_predicate) { while (!ready) pthread_cond_wait(&cond, &mtx); }
    else               { pthread_cond_wait(&cond, &mtx); }   /* broken: bare wait */
    pthread_mutex_unlock(&mtx);
    printf("consumer: saw ready=%d, proceeding\n", ready);
    return NULL;
}

int main(int argc, char **argv) {
    use_predicate = (argc > 1 && argv[1][0] == '1');
    pthread_t p, c;
    pthread_create(&p, NULL, producer, NULL);
    pthread_join(p, NULL);        /* producer fully finishes, and signals, before consumer starts */
    pthread_create(&c, NULL, consumer, NULL);
    pthread_join(c, NULL);
    return 0;
}
```
Compiled with `gcc -std=c11 -Wall -Wextra -pthread` and run under `timeout 2 ./a.out 0` (bare wait), it printed "producer done, ready=1; starting consumer..." and then hung; the shell reported exit code 124 (killed by timeout), and "consumer: saw ready" never printed. Run as `./a.out 1` (predicate loop), it printed the ready message immediately and returned exit code 0, every time.
FOLLOW:
- Why is this reproduced deterministically here, when lost wakeups are usually described as a rare timing bug? => By joining the producer thread before creating the consumer, the signal-before-any-waiter ordering is forced every single run instead of depending on scheduling luck -- real lost wakeups in production code are usually this same bug, just with a timing window that only sometimes lines up this way.
- Would adding a sleep() in the consumer before its bare wait "fix" this? => No, and it would only make the bug rarer and harder to find; the signal still already happened (and was a no-op) before the wait call runs, regardless of how much time passes first. Only checking the predicate fixes it.
PITFALL: "Fixing" an observed hang by adding a delay somewhere, which sometimes masks the timing window without addressing the actual bug (a missing predicate check before the wait).
VERIFY: POSIX.1-2017, pthread_cond_signal() DESCRIPTION ("shall have no effect if there are no threads currently blocked on cond").

@@ 5.05 | Intermediate | Concept | tags=spurious-wakeup,rationale,multiprocessor
Q: Where does a spurious wakeup actually come from, and why does POSIX allow it instead of forbidding it?
SHORT: POSIX's RATIONALE walks through a multiprocessor scenario where a cond_signal() and a cond_wait() interleave across internal lock/unlock steps so more than one waiting thread can be unblocked by a single signal -- an implementation artifact, not an application bug. The standard allows it deliberately: forbidding it costs efficiency for a rare case, and it forces every application to use a predicate loop anyway, which then tolerates superfluous signals elsewhere too.
DEEP:
- The RATIONALE's example shows pthread_cond_wait() and pthread_cond_signal() each taking an internal lock on the condition variable's own bookkeeping (distinct from the user's mutex) in a way that, interleaved just right across two threads and a signal, can result in a thread already on the waiter list being woken even though the signal was "for" a different, later arrival.
- Direct quote: "This effect is called 'spurious wakeup.' Note that the situation is self-correcting in that the number of threads that are so awakened is finite."
- The efficiency argument: "the loss of efficiency for a fringe condition that occurs only rarely is unacceptable, especially given that one has to check the predicate associated with a condition variable anyway."
- The forced-robustness argument: "An added benefit of allowing spurious wakeups is that applications are forced to code a predicate-testing-loop... This also makes the application tolerate superfluous condition broadcasts or signals... coded in some other part of the application."
FOLLOW:
- Does a spurious wakeup mean pthread_cond_wait() returned an error? => No, it returns 0 (success) exactly as a legitimate wakeup would; there is no way to distinguish a spurious wakeup from a real one except by re-checking your own predicate, which is the entire point.
- Can a spurious wakeup happen an unbounded number of times to the same wait call? => No -- POSIX calls the effect "self-correcting" and finite; it is not something a predicate loop needs to defend against as an infinite risk, just as a possible-at-all one.
PITFALL: Treating a spurious wakeup as an exotic edge case unlikely to matter in practice, rather than as a routine event any predicate loop must already handle for free.
VERIFY: POSIX.1-2017, pthread_cond_signal() RATIONALE, "Multiple Awakenings by Condition Signal" subsection.

@@ 5.06 | Intermediate | Concept | tags=signal,without-mutex,predictable-scheduling
Q: Is it legal to call pthread_cond_signal() without holding the associated mutex? What do you give up if you do?
SHORT: Yes, POSIX explicitly permits it: the signaling/broadcasting thread does not need to own the mutex the waiters are using. But the standard adds a caveat -- "if predictable scheduling behavior is required, then that mutex shall be locked by the thread calling pthread_cond_broadcast() or pthread_cond_signal()" -- so signaling outside the lock is legal but can change the observable order of who wakes and when.
DEEP:
- Without holding the mutex during the signal, a woken thread's re-acquisition of the mutex can race with the signaling thread's own later attempt to lock it (if it locks afterward), making the exact interleaving less deterministic than the "signal while still holding the lock" pattern.
- The common, safest idiom is still: lock, mutate the shared state, signal/broadcast, unlock -- signaling while the lock is held, which is also what every demo in this module does (5.04, 5.09).
- A narrower, sometimes-used optimization is to unlock first and signal after, to avoid the woken thread immediately blocking again on the same mutex the signaler still holds; this trades a small scheduling efficiency gain for the "predictable scheduling" guarantee POSIX ties to signaling-while-locked -- see 5.19 for the fuller trade-off discussion.
- Whichever order is chosen, the mutation of shared state itself must always happen under the lock; only the signal/broadcast call's exact position relative to the unlock is what is flexible.
FOLLOW:
- Does calling pthread_cond_signal() from a signal handler (the OS kind, SIGINT etc.) count as "without the mutex," and is that safe? => That is a different, stricter problem: POSIX's APPLICATION USAGE text says explicitly "it is not safe to use the pthread_cond_signal() function in a signal handler that is invoked asynchronously," regardless of mutex ownership, because of an unavoidable race with the predicate check.
- If you skip holding the mutex when signaling, do you still need the predicate loop on the waiter side? => Yes, unconditionally; the predicate loop's necessity (5.02) has nothing to do with whether the signaler held the mutex, only with spurious wakeups and superfluous signals, which can happen either way.
PITFALL: Assuming "the signaler doesn't need the mutex" means the shared state it is signaling about does not either. The state mutation still must happen under the lock; only the signal call itself has flexibility in exactly when it happens relative to the unlock.
VERIFY: POSIX.1-2017, pthread_cond_signal() DESCRIPTION (the "may be called... whether or not it currently owns the mutex" paragraph) and APPLICATION USAGE (signal-handler safety).

@@ 5.07 | Intermediate | Numeric | tags=context-switch,overhead,wait-signal
Q: Roughly how much more expensive is a genuine wait-then-signal round trip than an uncontended mutex lock/unlock?
SHORT: An uncontended mutex lock/unlock is typically tens of nanoseconds (4.12 measured 70-85 ns/op on a 2-core sandbox); a condition wait that actually blocks and wakes involves a full context switch out and back, commonly cited at low single-digit microseconds on commodity Linux -- roughly one to two orders of magnitude more. Treat both as rough, hardware- and load-dependent figures, not guarantees; the only way to know your own target's cost is to measure it there.
DEEP:
- POSIX itself only states the qualitative expectation, not a number: "The cost of waiting on a condition variable should be little more than the minimal cost for a context switch plus the time to unlock and lock the mutex" -- it deliberately leaves the actual figure to the implementation and hardware.
- The same RATIONALE text also states the common case (lock, touch shared data, unlock, no wait needed) should dominate: "the efficiency of a synchronization operation is bounded by the cost of mutex lock/unlock and not by condition wait... in the usual case there is no context switch" -- a condition variable is meant to be the rare path, not the common one, in a well-designed producer/consumer system.
- The "low single-digit microseconds" figure for a Linux context switch is a widely cited approximate order of magnitude from general systems-performance literature, not a number this session measured directly on this sandbox; flagged here as a hedge rather than a fetched benchmark.
- Practical implication for a bounded queue (5.13): sizing the buffer so producers/consumers rarely actually block (rather than exactly-1-deep) trades some memory for staying on the cheap, no-context-switch path most of the time.
FOLLOW:
- Does this mean condition variables are "slow" and should be avoided? => No; the comparison is against an uncontended lock, which is about as cheap as synchronization gets. A blocking wait is only ever reached when there is genuinely nothing useful to do yet, which is exactly when paying a context-switch cost (instead of spinning) is the right trade.
- Would a busy-wait/spin loop on the predicate ever beat a real cond_wait? => Only under the same narrow conditions spinlocks beat mutexes (4.12): an extremely short expected wait and spare cores to burn; for anything longer, spinning wastes far more CPU than the one-time context-switch cost of blocking properly.
PITFALL: Quoting the "context switch is expensive" fact to justify busy-waiting on a shared flag instead of using a condition variable, without first checking whether the actual wait times involved are short enough for that trade-off to make sense.
VERIFY: POSIX.1-2017, pthread_cond_timedwait() RATIONALE, "Performance of Mutexes and Condition Variables"; the microsecond context-switch figure is general systems-performance folklore, not a POSIX or vendor-published number -- treat it as an approximate hedge only.

@@ 5.08 | Intermediate | Scenario | tags=broadcast,multi-consumer,application-usage
Q: A producer can insert several items at once onto a shared list that several consumer threads each pull one item from. Why does POSIX's own guidance point at broadcast here, not signal?
SHORT: If the producer inserted N items and only signals once, at most one consumer is guaranteed to wake even though up to N consumers could now usefully proceed; broadcast wakes all waiting consumers so each can re-check the predicate and grab work if any is left. POSIX's APPLICATION USAGE text names this exact case: "the producer would notify all consumers that might be waiting, and thereby the application would receive more throughput on a multi-processor."
DEEP:
- The predicate loop makes this safe even though every consumer wakes: each one re-checks "is there an item for me" under the mutex, and any consumer that finds the list already emptied by a faster sibling just goes back to waiting -- broadcast only wastes some wakeups, it never causes incorrect double-consumption, because the mutex still serializes the actual pop.
- This is precisely the shape used in the bounded blocking queue's "no more items, producers are done" signal in 5.13: broadcasting done_producing ensures every consumer notices, not just one, since a signal might otherwise wake a consumer that then finds nothing and (incorrectly, on a signal-only design) has no way to learn that no more items are coming.
- The same APPLICATION USAGE text also mentions broadcast making a read-write lock's writer-releases-to-all-waiting-readers case easier to implement, and a two-phase-commit "notify all clients" case -- the common thread in all three is "more than one waiter's predicate can become true from a single state change."
FOLLOW:
- If the producer only ever inserts exactly one item at a time, does that change the answer? => Then signal is enough for the "new item available" case specifically (only one consumer can usefully take it), but the "producer is completely done, no more items ever" case still needs broadcast so every remaining consumer learns to stop waiting, exactly as 5.13's queue does.
- Does broadcasting here risk a thundering-herd performance problem with many consumers? => It can under heavy contention (every woken thread re-contends for the mutex), which is a real cost to weigh against correctness; for a small number of consumers it is rarely significant, and it is always correct, which signal-only is not in this scenario.
PITFALL: Using signal for a "many items became available at once" event because "it's usually one item at a time in testing," without checking what happens under the actual production insert pattern.
VERIFY: POSIX.1-2017, pthread_cond_broadcast() APPLICATION USAGE (single-producer/multiple-consumer example, read-write lock example, two-phase-commit example).

@@ 5.09 | Intermediate | Concept | tags=condvar,static-init,pthread-cond-initializer
Q: What is PTHREAD_COND_INITIALIZER, and when do you still need pthread_cond_init() instead?
SHORT: PTHREAD_COND_INITIALIZER is a static-initialization macro for a statically or globally allocated condition variable with default attributes, equivalent to calling pthread_cond_init(&c, NULL) except that no error checks are performed for the static form. You still need pthread_cond_init() explicitly for a heap-allocated condition variable, or whenever you need non-default attributes such as PTHREAD_PROCESS_SHARED or a specific clock for timed waits.
DEEP:
- Exactly parallel to the mutex case (4.03): "the macro PTHREAD_COND_INITIALIZER can be used to initialize condition variables that are statically allocated. The effect shall be equivalent to dynamic initialization by a call to pthread_cond_init()... except that no error checks are performed."
- Destroying a condition variable follows the same rule as mutexes: "It shall be safe to destroy an initialized condition variable upon which no threads are currently blocked. Attempting to destroy a condition variable upon which other threads are currently blocked results in undefined behavior."
- POSIX's own EXAMPLES section shows a condition variable safely destroyed immediately after a broadcast wakes every waiter and the mutex protecting it is unlocked -- the same "quiesce, then destroy" discipline as the mutex teardown example in 4.01.
- Like mutexes, only the condition variable object itself (never a copy of it) may be used for synchronization; the same copy-and-lifetime traps from 4.13 apply identically here.
FOLLOW:
- Can you call pthread_cond_init() on a statically-initialized condition variable to "reset" it? => No; attempting to initialize an already-initialized condition variable is undefined behavior, exactly as with mutexes -- if you need a fresh one, destroy it first (once no thread is waiting) and then re-init.
- Does the condition variable's attributes object need to outlive the pthread_cond_init() call? => No; "after a... attributes object has been used to initialize one or more [condition variables], any function affecting the attributes object... shall not affect any previously initialized [condition variables]" -- the same rule POSIX states for mutex attributes objects applies to condition variable attributes objects.
PITFALL: Re-initializing or destroying a condition variable while a thread is still blocked on it, assuming (incorrectly) that a broadcast issued moments earlier already guarantees every waiter has fully returned from pthread_cond_wait() and released its reference to the cond var.
VERIFY: POSIX.1-2017, pthread_cond_init()/pthread_cond_destroy() DESCRIPTION and EXAMPLES.

@@ 5.10 | Advanced | Concept | tags=condvar,mutex-binding,undefined
Q: What exactly does it mean for a condition variable to be "dynamically bound to a unique mutex," and what happens if you violate that?
SHORT: POSIX states "a condition variable becomes bound to a unique mutex when a thread waits on the condition variable, and this (dynamic) binding shall end when the wait returns" -- so while any thread is blocked in pthread_cond_wait() on a cond var, every concurrent wait on that same cond var must use the identical mutex, or the result is undefined. The binding is not declared anywhere in the API; it exists implicitly, only while at least one thread is actually waiting.
DEEP:
- This is why a condition variable's associated mutex is a convention your code must maintain, not something pthread_cond_init() lets you declare or enforce up front -- the type signature of pthread_cond_wait() takes a mutex parameter precisely because the binding is per-call, not fixed at init time.
- In practice, a design that always pairs one specific mutex with one specific condition variable (as the bounded queue in 5.13 does, one mutex with two condition variables, not one condition variable with two mutexes) never risks this, because there is only ever one mutex in the picture for that cond var to begin with.
- A design that risks this is one condition variable shared across multiple, differently-locked subsystems "to save a cond var" -- if subsystem A waits on it using mutex_A while subsystem B concurrently waits on the same cond var using mutex_B, that is exactly the undefined-behavior case, and it will not necessarily crash or warn, just misbehave in implementation-specific ways.
- EINVAL is listed as a possible (not guaranteed) error return "Different mutexes were supplied for concurrent pthread_cond_timedwait() or pthread_cond_wait() operations on the same condition variable" -- some implementations catch this, but POSIX does not require it, so passing the check on one platform proves nothing about another.
FOLLOW:
- Does the binding still apply if the two waits happen sequentially, not concurrently? => No -- the rule is specifically about concurrent waits; once every prior waiter has returned (ending the binding), a completely different mutex can be used for the next wave of waits on the same cond var without any violation.
- Is this the same issue as the "one condition variable, two different predicates" case from 5.14? => No, that is about which threads a signal wakes; this is about which mutex a wait call is allowed to pass. They can combine (one cond var, two predicates, and mistakenly two mutexes too), but each is its own distinct rule to get right.
PITFALL: Sharing one condition variable across two different subsystems that each have their own mutex, on the theory that "it's just a wakeup mechanism." The mutex-binding rule makes that combination undefined behavior the moment their waits overlap in time.
VERIFY: POSIX.1-2017, pthread_cond_wait() DESCRIPTION (the mutex-binding paragraph) and ERRORS (EINVAL, "different mutexes" case, listed as "may fail").

@@ 5.11 | Advanced | Cross-layer | tags=cancellation,cond-wait,cleanup
Q: What happens to the mutex if a thread blocked in pthread_cond_wait() is canceled?
SHORT: A condition wait is a cancellation point, and POSIX specifies the mutex is re-acquired before the cancellation cleanup handler runs -- "the effect is as if the thread were unblocked, allowed to execute up to the point of returning from the call... but at that point notices the cancellation request and... starts the thread cancellation activities." This guarantees a cleanup handler always finds the mutex locked, as on a normal return, regardless of where cancellation landed inside the wait.
DEEP:
- The reasoning, from POSIX's own RATIONALE: "since some statement has to be made regarding the state of the lock when a cancellation is delivered during a wait, a definition has been chosen that makes application coding most convenient and error free" -- without this rule, a cleanup handler would need to know (and handle differently) whether cancellation happened before, during, or after re-acquiring the mutex.
- A second guarantee travels with this: a canceled thread "shall not consume any condition signals... if there are other threads blocked on the condition variable" -- cancellation and signaling are kept independent, so a canceled thread being torn down never silently steals a wakeup meant for someone else.
- This matters directly for code with a pthread_cleanup_push() handler wrapping a cond_wait loop (a common pattern for a worker thread that must be cancelable while idle-waiting for work): the handler can always assume the mutex is locked and unlock it itself, without special-casing where the cancellation was delivered.
- This is squarely a cross-layer fact: the language-level API call (cond_wait) has a kernel-visible, cancellation-subsystem-level contract layered on top of its ordinary blocking behavior.
FOLLOW:
- Does this rule apply to pthread_cond_timedwait() the same way? => Yes, identically; POSIX states the condition-wait cancellation-point behavior for both timed and non-timed waits without distinction.
- Is PTHREAD_CANCEL_ASYNCHRONOUS relevant here, or only PTHREAD_CANCEL_DEFERRED? => The described mutex-reacquisition behavior is specifically tied to "the cancelability enable state of a thread... set to PTHREAD_CANCEL_DEFERRED," which is also the default and by far the common case; asynchronous cancellation can act at arbitrary instructions and does not get this same orderly guarantee.
PITFALL: Writing a cancellation cleanup handler for a cond_wait loop that assumes the mutex might be unlocked at cleanup time "just in case." POSIX guarantees it is locked; unlocking an already-unlocked mutex there would itself be a bug.
VERIFY: POSIX.1-2017, pthread_cond_timedwait()/pthread_cond_wait() RATIONALE, "Cancellation and Condition Wait" subsection.

@@ 5.12 | Advanced | Scenario | tags=bounded-queue,design,two-condvars
Q: Design the two predicates for a bounded blocking queue built from one mutex and two condition variables.
SHORT: One mutex protects the shared buffer/head/tail/count state; a not_full condition variable's predicate is "count < capacity" (producers wait on it before pushing), and a not_empty condition variable's predicate is "count > 0" (consumers wait on it before popping). Every push signals not_empty after inserting, and every pop signals not_full after removing, so the side whose condition just became true is exactly the side that gets woken.
DEEP:
- Using two condition variables instead of one is what avoids unnecessary wakeups: a producer that just made room does not need to wake other producers (they would still see count < capacity and could have just checked it themselves), it needs to wake a waiting consumer, and vice versa -- one cond var per direction keeps signal wakeups targeted.
- Both predicates are checked in a while loop exactly as 5.02 requires: `while (count == CAP) pthread_cond_wait(&not_full, &mtx);` for push, `while (count == 0) pthread_cond_wait(&not_empty, &mtx);` for pop -- both under the same single mutex, so both predicates are always read and written consistently.
- A third condition needs its own signal: "no more items will ever come" (producers finished). 5.13's implementation adds a `done_producing` flag, checked in the consumer's predicate as `count == 0 && !done_producing`, and broadcasts (not signals) not_empty when producers finish, so every waiting consumer -- not just one -- learns to stop waiting rather than blocking forever (5.08's multi-waiter broadcast reasoning applies directly here).
- This design generalizes: any bounded resource with two directions of pressure (space becoming available vs. items becoming available) tends to want exactly this "one mutex, one cond var per direction" shape, rather than cramming both predicates onto a single condition variable.
FOLLOW:
- Why not just use one condition variable for both not_full and not_empty? => It would work correctness-wise (broadcast on every push/pop and let every waiter re-check its own predicate), but wakes every waiting thread on every operation instead of only the relevant side, which is wasted work exactly like 5.08's thundering-herd trade-off, just avoidable here by using two cond vars.

@@ 5.18 | Principal | Trap | tags=predictable-scheduling,signal-placement,tradeoff
Q: Should you call pthread_cond_signal()/broadcast() before or after pthread_mutex_unlock()? Walk through the trade-off.
SHORT: Signaling while still holding the mutex ("signal-then-unlock") is what POSIX ties its "predictable scheduling behavior" language to, and is the safer default; signaling after unlocking can, on some implementations, avoid a woken thread immediately reblocking on a mutex the signaler still held, but gives up that guarantee. Default to signal-then-unlock; switch only with a measured reason, and re-verify correctness under real concurrency (5.13's method) after doing so.
DEEP:
- POSIX's exact hedge: signal/broadcast "may be called by a thread whether or not it currently owns the mutex... however, if predictable scheduling behavior is required, then that mutex shall be locked by the thread calling pthread_cond_broadcast() or pthread_cond_signal()." This is a "should" dressed as a "shall... if required" -- it is legal either way, but only one way keeps the standard's own predictability promise.
- The theoretical unlock-then-signal benefit: on an implementation where the newly-woken thread cannot yet re-acquire the mutex only because the signaling thread is still about to call unlock(), waking it "one step early" relative to the unlock can reduce one avoidable wakeup-then-immediately-reblock cycle. Modern glibc's futex-based implementation makes this benefit small to negligible in practice, which is why it is rarely worth the trade.
- The cost: with unlock-then-signal, the window between "state changed" and "signal issued" is no longer inside the same locked region as the mutation, which reopens exactly the kind of timing gap 5.04's lost-wakeup bug lives in if the code is not written with extra care (e.g. a waiter's check-then-wait sequence racing a not-yet-issued signal that is now outside the lock's protection).
- The Principal-level judgment call: this is a micro-optimization with a real correctness risk if done carelessly, for a benefit that is often unmeasurable; the default recommendation for nearly all application code is signal/broadcast while still holding the mutex, and only reconsider with actual profiling data showing the reblock cycle matters for a specific hot path.
FOLLOW:
- Does this trade-off apply to broadcast the same way it applies to signal? => Yes, identically; POSIX's wording covers both functions together, and the same predictability-vs-theoretical-efficiency trade-off applies whether one or many threads are being woken.
- Is there a way to get the efficiency benefit without the correctness risk? => Only by being very deliberate: keep the state mutation and the predicate's truth value change entirely inside the lock, unlock, then immediately signal with nothing else happening in between -- and treat this as an optimization to justify with a profiler, not a default style choice.
PITFALL: Moving a signal/broadcast call outside the lock as a "performance improvement" without profiling data showing it matters, and without re-running the same kind of repeated-execution correctness check (5.13, 5.14) that would catch a newly-introduced timing gap.
VERIFY: POSIX.1-2017, pthread_cond_signal()/pthread_cond_broadcast() DESCRIPTION (the "predictable scheduling behavior" clause).

Q: Why did POSIX deliberately decouple condition-variable waiting from mutex acquisition instead of offering one combined "atomically unlock, wait, relock" primitive with no separate mutex object at all?
SHORT: It did offer that combined operation (pthread_cond_wait() already does atomic unlock-wait-relock, 5.01) -- what it declined is offering mutex acquisition and condition waiting as separate, composable steps. DEEP:
- Direct quote: "It had been suggested that the mutex acquisition and release be decoupled from condition wait. This was rejected because it is the combined nature of the operation that, in fact, facilitates realtime implementations. Those implementations can atomically move a high-priority thread between the condition variable and the mutex in a manner that is transparent to the caller."
- The stated benefit: "this can prevent extra context switches and provide more deterministic acquisition of a mutex when the waiting thread is signaled" -- decoupling the two operations would reopen exactly the kind of race window pthread_cond_wait()'s atomicity (5.01) exists to close, just at the wake side instead of the sleep side.
- This is a good example of a POSIX design choice driven by a use case (hard real-time scheduling) that most application code never directly exercises, but that shapes the API everyone uses -- the predicate-loop discipline (5.02) and the mutex-binding rule (5.10) are both downstream consequences of keeping cond_wait's mutex handling atomic and built-in rather than exposed as separate composable pieces.

PITFALL: Treating the mutex-plus-cond-var pairing as an arbitrary API inconvenience to work around with a "simpler" hand-rolled decoupled version. The coupling is a deliberate correctness and real-time-determinism choice, documented as such, not an accident of history.
