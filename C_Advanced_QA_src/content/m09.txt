# Module 9: Classic Concurrency Problems

@@ 9.01 | Basic | Concept | tags=classic-problems,overview,what-each-teaches
Q: What are the three "classic" concurrency problems this module covers, and what does each one specifically teach?
SHORT: Producer-consumer with a bounded buffer teaches correct handoff when the buffer can be full (producers wait) or empty (consumers wait). Readers-writers teaches that "more than one kind of access" needs its own fairness policy, not just mutual exclusion. Dining philosophers teaches how a symmetric, simultaneous resource grab among peers -- no producer/consumer or reader/writer asymmetry to exploit -- creates circular wait, and how to break it.
DEEP:
- All three are decades-old (Dijkstra formulated the bounded-buffer and dining-philosophers problems; Courtois, Heymans, and Parnas formulated readers-writers) precisely because each isolates one specific concurrency shape in its purest, smallest form -- real systems combine and complicate these shapes, but rarely invent a wholly new one.
- Producer-consumer's shape already appeared, solved with condition variables, in module 5 (5.13); this module rebuilds it with the classic semaphore-pair solution (9.04) instead, the historically original approach and still the common textbook one.
- Readers-writers already appeared via `pthread_rwlock_t` in module 6 (6.10, 6.17); this module rebuilds the actual scheduling policy (who gets admitted next) from raw mutexes instead of relying on the library's built-in (and, as 6.10 found, not necessarily reader-preferring) policy.
- Dining philosophers is new territory for this study guide: five peers, each needing two shared resources at once, with no natural "producer vs consumer" or "reader vs writer" role difference to exploit for a fix -- the fix has to come from resource ordering or admission limiting alone (9.12-9.14).
FOLLOW:
- Why re-solve producer-consumer and readers-writers when modules 5 and 6 already covered them? => Because the *mechanism* differs meaningfully: semaphores versus condition variables for producer-consumer, and hand-rolled scheduling policy versus a library's built-in policy for readers-writers -- both real, useful alternate implementations, not redundant repetition.
- Is there a "fourth" classic problem worth knowing? => The sleeping-barber problem is another well-known one (a bounded-buffer variant with a single server), but this study guide's scope is the three named in the module brief; the same bounded-buffer and mutual-exclusion techniques covered here transfer directly to it.
PITFALL: Treating these as academic exercises disconnected from real systems. 9.08 maps all three directly onto real OS/firmware scenarios -- a command queue, a config cache, and a multi-lock validation harness are the same shapes in production clothing.
VERIFY: General concurrency-theory history (Dijkstra; Courtois/Heymans/Parnas); not itself POSIX or C11 text.

@@ 9.02 | Basic | Concept | tags=producer-consumer,bounded-buffer,problem-statement
Q: What exactly is the bounded-buffer producer-consumer problem, and what makes the "bounded" part specifically hard?
SHORT: One or more producer threads generate items and place them into a fixed-capacity buffer; one or more consumer threads remove and process them; the buffer must never be written to when full (producers must wait for a free slot) or read from when empty (consumers must wait for an item). The "bounded" part is what makes it harder than an unbounded queue: producers now have a wait condition too, not just consumers, and both conditions need correct, race-free handling.
DEEP:
- An unbounded (infinite) buffer only ever needs consumers to wait (on empty); a bounded buffer adds a second, symmetric wait condition on the producer side (on full), doubling the number of race conditions a correct solution must close off.
- The two historically standard solutions are a mutex-plus-condition-variable pair with an explicit predicate loop (module 5.13's `while (count == 0) wait` / `while (count == BUFSZ) wait`), and the semaphore-pair solution this module builds (9.04): a counting semaphore for "empty slots available" and another for "items available," plus a plain mutex only for the buffer's own index bookkeeping.
- Correctness for this problem specifically means: no item is ever lost or duplicated, no consumer ever reads a slot no producer has written yet, and no producer ever overwrites a slot a consumer has not yet read -- 9.04's compiled test checks all of this directly via an exact checksum match, not just a count.
- The buffer's capacity (module 9.16 reasons about choosing it) is a real design parameter, not just a data-structure detail: too small serializes producers and consumers unnecessarily; too large wastes memory and can hide backpressure signals a smaller buffer would surface earlier.
FOLLOW:
- Is a bounded buffer strictly necessary, or could an unbounded queue always be used instead? => An unbounded queue removes the producer-side wait condition entirely, but real systems have finite memory, so "unbounded" is really "bounded by however much memory happens to be available," an implicit and much less controlled bound than an explicit, chosen capacity.
- Does the number of producers or consumers change the fundamental problem? => Not the correctness requirements (still no lost/duplicated items, no reading unwritten slots), but it does change the bookkeeping: multiple producers now need mutual exclusion among themselves for the buffer's write index, and multiple consumers likewise for the read index (9.05 covers exactly this).
PITFALL: Assuming a "thread-safe queue" data structure automatically handles the bounded case correctly just because it handles concurrent access safely. Bounded capacity needs its own explicit wait/signal handling (whichever primitive provides it) beyond whatever makes individual pushes and pops safe.
VERIFY: General concurrency-theory problem statement (Dijkstra); not itself POSIX or C11 text.

@@ 9.03 | Basic | Concept | tags=readers-writers,first-vs-second,problem-statement
Q: What is the readers-writers problem, and why do "first" and "second" variants exist?
SHORT: Any number of readers may access shared data concurrently as long as no writer is active; a writer needs exclusive access, with no readers and no other writer active. The "first" problem (Courtois/Heymans/Parnas's original formulation) is reader-preferring: a new reader is never blocked just because a writer is waiting. The "second" problem is writer-preferring: once a writer is waiting, no new reader may start, though already-active readers finish normally.
DEEP:
- Neither variant is "more correct" than the other -- they encode different fairness policies for the identical mutual-exclusion requirement (concurrent readers, exclusive writer), and the choice between them is a design decision, not a bug fix, driven by which side's starvation risk the application can tolerate less.
- The first (reader-preferring) problem is exactly what 9.10 builds and reproduces: a continuous stream of readers can starve a writer indefinitely, since a new reader arriving while a writer waits is still admitted ahead of it, by design.
- The second (writer-preferring) problem is exactly what 9.11 builds as the fix: an extra "no new readers" gate that a waiting writer closes, bounding the writer's wait to whatever readers were already active when it arrived, at the cost of now being able to starve a continuous stream of new readers instead (9.15 covers this trade-off precisely).
- `pthread_rwlock_t` (module 6) does not commit to either variant by specification -- POSIX only says an implementation "may favor writers... to avoid writer starvation," a permission, and module 6.10 found this specific glibc's default in practice resists (but does not eliminate) writer starvation without fully committing to strict writer preference either.
FOLLOW:
- Is there a variant that starves neither side? => Yes -- a strict FIFO/ticket-based admission policy (9.17) serves every request, reader or writer, in arrival order, which starves neither side by construction, at the cost of more bookkeeping than either the first or second problem's simpler policies need.
- Why would anyone choose the first (reader-preferring) variant if it can starve a writer? => When writes are rare and not latency-critical, and read throughput matters more (module 6.08's exact read-heavy-workload scenario) -- reader preference maximizes read concurrency at the cost of a risk that may simply never materialize for that specific workload's write frequency.
PITFALL: Assuming "readers-writers problem" has one canonical solution. It names a mutual-exclusion *shape*; the specific fairness policy (first, second, or a fair ticket-based third option) is a separate decision every implementation has to make explicitly.
VERIFY: Courtois, Heymans, Parnas (1971), "Concurrent Control with 'Readers' and 'Writers'"; general concurrency-theory, not POSIX or C11 text.

@@ 9.04 | Intermediate | Debug | tags=producer-consumer,semaphore-pair,compiled,checksum
Q: Build the classic semaphore-pair bounded-buffer solution (not the condition-variable version from module 5) and confirm it under real multi-producer, multi-consumer load.
SHORT: Two counting semaphores (`empty_slots` starting at the buffer capacity, `full_slots` starting at 0) plus a plain mutex for the buffer's own read/write index bookkeeping. With 3 producers and 3 consumers moving 1500 items total through an 8-slot buffer, the run completed with consumed count and checksum matching produced count and checksum exactly: `produced=1500 consumed=1500 checksum_produced=150374250 checksum_consumed=150374250 match=OK`, on all three runs tested.
DEEP:
```c
sem_t empty_slots, full_slots;                 /* sem_init(&empty_slots, 0, BUFSZ); sem_init(&full_slots, 0, 0); */
pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;

static void *producer(void *arg) {
    for (each item) {
        sem_wait(&empty_slots);                 /* take a free slot */
        pthread_mutex_lock(&mtx);
        buffer[head] = item; head = (head + 1) % BUFSZ; checksum_produced += item;
        pthread_mutex_unlock(&mtx);
        sem_post(&full_slots);                  /* announce a filled slot */
    }
}
static void *consumer(void *arg) {
    for (each expected item) {
        sem_wait(&full_slots);
        pthread_mutex_lock(&mtx);
        int item = buffer[tail]; tail = (tail + 1) % BUFSZ; total_consumed++; checksum_consumed += item;
        pthread_mutex_unlock(&mtx);
        sem_post(&empty_slots);                 /* return the slot */
    }
}
```
Compiled with `gcc -std=c11 -Wall -Wextra -pthread` and run three times (3 producers x 500 items, 3 consumers each assigned exactly 500 items to drain), every run printed `produced=1500 consumed=1500 checksum_produced=150374250 checksum_consumed=150374250 match=OK` -- exact match, no lost or duplicated items, across all three runs.
- This is precisely 6.01/6.04's semaphore-vs-mutex distinction applied end to end: the semaphores alone bound concurrency correctly (no more than BUFSZ items ever in flight), but the shared `head`/`tail` indices still need their own mutex, which is exactly module 9.05's question.
FOLLOW:
- How does this differ from module 5.13's condition-variable bounded queue? => Mechanism, not outcome -- 5.13 uses one mutex and predicate-checked condition-variable waits for both "not full" and "not empty"; this uses two purpose-built counting semaphores instead, each semaphore's count directly *being* the "how many slots/items are available" state, with no separate predicate to check.
- Would this still work correctly with only 1 producer and 1 consumer? => Yes, and more simply -- with exactly one of each, the mutex around `head`/`tail` becomes unnecessary (no concurrent writer to `head`, no concurrent writer to `tail`), the same single-writer-per-index insight module 7.16's SPSC ring buffer used to drop synchronization down to plain release/acquire.
PITFALL: Assuming the two semaphores alone are sufficient and skipping the mutex around `head`/`tail`. With more than one producer (or more than one consumer), that is a real, unguarded data race on the shared index, identical in kind to 6.04's exact warning about the same pattern.
VERIFY: General concurrency theory (Dijkstra's original bounded-buffer solution); POSIX.1-2017 sem_wait()/sem_post() DESCRIPTION for the semaphore semantics themselves (cited fully in module 6). Compiled and run: prodcons_sem.c (three runs, exact match each time).

@@ 9.05 | Intermediate | Concept | tags=semaphore-plus-mutex,why-both,index-bookkeeping
Q: Why does the semaphore-pair bounded-buffer solution still need a separate mutex, when the two semaphores already correctly bound how many items can be in flight?
SHORT: The semaphores enforce a purely numeric invariant (never more than BUFSZ items in flight, never a consumer proceeding when zero are available) but do nothing about the shared `head`/`tail` indices themselves -- with more than one producer, two producers can both pass `sem_wait(&empty_slots)` concurrently and race to write `buffer[head]` and increment it, the same unprotected read-modify-write race 4.02/4.05 demonstrated for a plain counter.
DEEP:
- This is precisely 6.04's own finding restated in this problem's specific shape: "the semaphore only limits how many threads can be past sem_wait() at once, it does nothing to make the increment/compare/decrement of a shared counter atomic" -- here the "shared counter" is the buffer's write (or read) index.
- With exactly one producer, no mutex is needed around `head` (only one thread ever writes it, module 7.16's single-writer-per-index insight); the mutex becomes necessary specifically once a second producer (or second consumer, for `tail`) is introduced.
- The mutex's critical section here is deliberately tiny -- an array write, a modular increment, and a checksum update -- which is exactly the right scope: the semaphores already did the "wait until it's safe to proceed at all" work, so the mutex only needs to protect the handful of instructions that are not already made safe by the semaphore's counting.
- A common, subtly wrong "simplification" is trying to fold the mutex's job into the semaphore itself (e.g. initializing a semaphore to 1 and using it as a de facto mutex around the index) -- this works but reintroduces exactly the ownership-less, no-ERRORCHECK downsides module 6.01/6.19 already flagged for using a binary semaphore as a mutex substitute.
FOLLOW:
- Would using an atomic index (module 7's atomic_size_t, CAS-based) instead of a mutex work here? => Yes in principle for the index update alone, following the same CAS-loop pattern as 7.11's Treiber stack, but for this problem's small, uncontended critical section, a plain mutex is simpler and was not shown by any measurement in this study guide to cost meaningfully more.
- Does the mutex need to be held across the sem_post() call? => No, and 9.04's code deliberately does not -- releasing the mutex before the sem_post() keeps the critical section as narrow as module 4.06's own "critical section sizing" discipline recommends.
PITFALL: Reasoning "the semaphores already handle synchronization, so the buffer access itself must be safe too." The semaphores synchronize *how many* threads may be past a certain point; they say nothing about races between threads that are all correctly past that point simultaneously.
VERIFY: POSIX.1-2017, sem_wait()/sem_post() DESCRIPTION (counting semantics only, no ownership or mutual-exclusion-of-arbitrary-code guarantee); this exact point is also made directly in module 6.04.

@@ 9.06 | Intermediate | Trap | tags=single-semaphore,wrong-design,ambiguous-count
Q: What goes wrong if a bounded-buffer solution tries to use one shared semaphore instead of two (empty_slots and full_slots)?
SHORT: A single semaphore's count cannot simultaneously represent two opposite-direction bounds -- "how many free slots remain" and "how many filled slots are available to consume" are complementary values (they always sum to the buffer's capacity), but a producer and a consumer each need to wait on a *different* one of those two conditions, and one semaphore can only ever expose one count to wait on, not both.
DEEP:
- If a single semaphore is initialized to BUFSZ and both producers and consumers `sem_wait()`/`sem_post()` on it indiscriminately, there is no way for a producer's wait to mean "block until there is a free slot" while a consumer's wait simultaneously means "block until there is an item" -- both waits would be checking the exact same count for two logically opposite conditions.
- A concrete failure mode: initialize the single semaphore to 0 and have producers `sem_post()` after writing, consumers `sem_wait()` before reading (mimicking only `full_slots`) -- this correctly stops consumers from reading an empty buffer, but has completely dropped the "producer must wait for a free slot" bound entirely, since nothing stops a producer from writing past the buffer's actual capacity and corrupting adjacent slots a consumer has not yet read.
- The two-semaphore design works precisely because `empty_slots` and `full_slots` are two independent counts that happen to be complementary (`empty_slots + full_slots == BUFSZ` is an invariant of the correct solution), each with its own dedicated waiters (producers wait on one, consumers on the other) -- collapsing them into one shared count throws away the ability to express both bounds at once.
- This is a designed-in structural requirement of the classic solution, not an implementation detail that could be optimized away; Dijkstra's original formulation already uses exactly this two-semaphore shape for precisely this reason.
FOLLOW:
- Could three or more semaphores ever be useful for a variant of this problem? => Yes, for a variant with additional constraints (e.g. a priority class of "urgent" items needing a separate capacity-bounded lane) -- but that is a different, extended problem, not a simplification of the basic two-semaphore bounded buffer.
- Is this the same mistake as module 6.06's "wrong waiter" semaphore trap? => Related but distinct -- 6.06 is about one semaphore ambiguously serving more than two *parties* for a signal meant for one specific consumer; this is about one semaphore ambiguously serving two opposite *conditions* (full versus empty) that structurally need two separate counts.
PITFALL: "Simplifying" the classic two-semaphore bounded-buffer solution down to one semaphore because "it's the same buffer, so one counter should do." The two counts are complementary but serve two different waiting parties with two different, individually necessary conditions.
VERIFY: General concurrency theory (Dijkstra's original two-semaphore bounded-buffer formulation); not itself POSIX or C11 text.

@@ 9.07 | Intermediate | Concept | tags=dining-philosophers,problem-statement,symmetric-resource-grab
Q: What is the dining philosophers problem, and why is the symmetric, simultaneous nature of the resource grab specifically what causes deadlock?
SHORT: Five philosophers sit at a round table with five forks, one between each adjacent pair; each needs both their left and right fork to eat, and forks are shared with neighbors. If every philosopher simultaneously grabs their left fork first, all five forks are immediately held, and every philosopher is stuck waiting for their right fork, held by a neighbor in the identical situation -- a five-node circular wait with no asymmetry anywhere to break it.
DEEP:
- This is a deliberately symmetric version of the general "acquire multiple shared resources" problem module 8 covers in the two-mutex case: with only two threads and two locks (8.04), an *asymmetric* fix (both threads agree to lock A before B) is simple to state; with five peers each needing two of five circularly-shared resources, "always lock the lower-numbered fork first" needs slightly more care, since the fifth philosopher's "left" and "right" forks are numbered N-1 and 0 -- the wraparound is exactly where the naive per-philosopher "always left first" rule breaks the ordering it needs (9.12's naive version is precisely this un-fixed case).
- Every philosopher running identical code (same left-then-right logic) is what makes the naive version deadlock *deterministically* under the right timing, not just probabilistically -- 9.12's compiled reproduction confirms this directly (all 5 philosophers picked up their left fork, then all 5 blocked trying for their right, every time this was run).
- The two standard fixes are resource ordering (9.13: break the symmetry by having philosophers acquire whichever of their two forks has the lower index first, not always "left" first) and admission limiting (9.14: cap how many philosophers may attempt to eat simultaneously to strictly fewer than the total, using a counting semaphore, so at least one fork is always available somewhere).
- Unlike producer-consumer or readers-writers, there is no natural role asymmetry (no "producer" versus "consumer," no "reader" versus "writer") to hang a fix on -- every philosopher's code is identical, which is exactly why the fix has to come from breaking a *structural* symmetry (acquisition order, or how many may compete at once) rather than assigning different behavior to different roles.
FOLLOW:
- Does the deadlock require exactly 5 philosophers? => No -- any number N >= 2 sharing N forks in a circle has the identical structural risk; 5 is simply Dijkstra's original, commonly-taught instance.
- Is a global lock ordering (module 8.16) the same fix as 9.13's resource ordering here? => Conceptually identical -- 9.13 is module 8.16's general "assign every lock a stable, comparable identity and always acquire in increasing order" design, applied to the specific circular case where the naive per-thread rule ("always left first") already almost works except at the wraparound.
PITFALL: Assuming any single philosopher's code, read in isolation, looks obviously correct -- lock, then lock, then unlock, then unlock. The bug is not in any one philosopher's logic; it is in what happens when all five run that same, individually-reasonable logic at the same moment.
VERIFY: General concurrency theory (Dijkstra's dining philosophers, 1965); not itself POSIX or C11 text.

@@ 9.08 | Intermediate | Cross-layer | tags=firmware-mapping,command-queue,config-cache,lock-ordering
Q: Map each of the three classic problems onto a concrete real OS/firmware scenario -- what does each one actually look like in production code?
SHORT: Producer-consumer is a command queue: workers submit storage commands (producers) into a bounded queue, drained by a completion thread (consumer) -- 6.16's semaphore design names these roles directly. Readers-writers is a config/cache structure read constantly by workers and updated rarely by control-plane code (6.08's scenario). Dining philosophers is any validation harness where worker threads each need more than one shared resource, in an order no single thread controls.
DEEP:
- The command-queue mapping is the most direct: 9.04's `empty_slots`/`full_slots` semaphore pair *is* 6.16's "resource-limiting layer... N NVMe command queues in flight at once" design, just with the producer/consumer terminology made explicit instead of "submit path"/"completion path."
- The config/cache mapping inherits every trade-off module 6.08/9.03 already covered: if updates are rare and reads vastly outnumber them, reader preference (9.02's "first" problem) is usually fine; if updates must never be delayed unpredictably (a safety-critical configuration reload, for instance), writer preference or strict fairness (9.11, 9.17) is the safer default.
- The dining-philosophers mapping is the least obvious but arguably the most common in practice: any test harness or driver that must acquire, say, a hardware channel lock *and* a shared results-buffer lock *and* a logging lock, where different worker threads acquire these in whatever order their specific test case happens to need them, is structurally the dining-philosophers problem with more than two "forks" -- module 8.16's global lock-ordering design is the direct, general-purpose fix for this exact shape.
- Recognizing which of the three shapes a real design problem actually is (bounded handoff, differentiated-access mutual exclusion, or symmetric multi-resource acquisition) is itself the practical skill -- each shape has a known, well-understood family of fixes, and misidentifying the shape leads to reaching for the wrong one (e.g. trying to apply a readers-writers fairness policy to what is actually a multi-lock-ordering problem).
FOLLOW:
- Can a single real system exhibit more than one of these shapes at once? => Routinely -- a validation harness might have a command-queue (producer-consumer) feeding a shared results cache (readers-writers) while multiple worker threads separately need channel-plus-logging locks (dining philosophers) -- each sub-problem gets its own fix, applied independently to the part of the design that actually has that shape.
- Is there a shape none of these three directly covers? => Phased, all-must-arrive synchronization (module 6.09's barriers) is a different shape none of the three classic problems addresses -- "wait for everyone to reach this point" is neither a handoff, nor a differentiated-access policy, nor a multi-resource acquisition problem.
PITFALL: Reaching for a readers-writers-style fix (rwlock, or a reader/writer-preference policy) for a problem that is actually a multi-resource dining-philosophers shape, because both "sound like" they are about coordinating shared access. The correct fix families are different (fairness policy versus resource ordering/admission limiting).
VERIFY: General systems-design synthesis of this module's own results plus module 6.08/6.16/8.16; not itself POSIX or C11 text.

@@ 9.09 | Intermediate | Concept | tags=hand-rolled-vs-rwlock,structural-difference
Q: What does hand-rolling readers-writers from a plain mutex (as this module does) let you control that pthread_rwlock_t (module 6) does not expose directly?
SHORT: `pthread_rwlock_t`'s admission policy (which side is preferred when both wait) is up to the implementation -- POSIX only permits, never requires, writer preference, and 6.10 found this glibc's default resists but does not eliminate starvation. Hand-rolling the scheduling logic from a mutex (plus, for 9.11's fix, a "no new readers" mutex) makes the admission policy explicit and changeable in application code, instead of inherited and platform-dependent.
DEEP:
- 9.10's naive hand-rolled version and 9.11's fixed hand-rolled version are not "reimplementing pthread_rwlock_t badly" -- they are deliberately choosing and encoding a *specific* fairness policy (reader-preferring, then writer-preferring) that a real pthread_rwlock_t leaves to the implementation's own, usually undocumented, internal choice.
- This matters concretely whenever the exact fairness guarantee is a hard requirement (a safety-critical config reload that must never wait unboundedly, for instance) rather than a "probably fine in practice" assumption -- module 6.17's own fix for a production rwlock-starvation report reached for a Linux-specific, non-portable rwlockattr extension (`PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP`) precisely because POSIX itself offers no portable way to request writer preference from `pthread_rwlock_t` directly.
- Hand-rolling from a mutex (and, in 9.17, a mutex plus a condition variable and an explicit ticket counter) trades pthread_rwlock_t's simplicity and likely-optimized internal implementation for full, portable control over exactly which policy is enforced -- a real engineering trade-off, not a strictly better approach in every case.
- The core mutual-exclusion invariant (concurrent readers, exclusive writer) is identical either way; what differs is entirely the admission/scheduling policy layered on top of that invariant, which is precisely the layer this module's 9.10/9.11/9.17 make fully explicit and testable.
FOLLOW:
- Is a hand-rolled version ever faster than pthread_rwlock_t? => Not automatically, and likely not for the general case -- pthread_rwlock_t's implementation is typically well-optimized for the common uncontended and lightly-contended cases; the reason to hand-roll is policy control, not raw performance, unless measurement on the actual target shows otherwise.
- Would you ever hand-roll this in real production code, or only for learning the mechanism? => Real production code does this specifically when the portable fairness guarantee is a hard requirement pthread_rwlock_t cannot provide (6.17's own scenario); otherwise, defaulting to pthread_rwlock_t and only hand-rolling if a measured, confirmed fairness problem demands it is the more common, pragmatic path.
PITFALL: Hand-rolling a readers-writers scheme reflexively "for control," without first confirming pthread_rwlock_t's actual, measured behavior on the target platform is insufficient for the requirement at hand. Module 6.10's own measurement found this specific glibc's default already resists starvation reasonably well -- confirm the gap exists before building a replacement for it.
VERIFY: POSIX.1-2017, pthread_rwlock_wrlock() DESCRIPTION ("Implementations may favor writers... to avoid writer starvation" -- a permission, not a requirement); cross-referenced against module 6.10/6.17's own findings.

@@ 9.10 | Advanced | Debug | tags=readers-writers,naive,writer-starvation,compiled
Q: Reproduce real, severe writer starvation with a hand-rolled, reader-preferring readers-writers implementation (the "first" problem, not pthread_rwlock_t).
SHORT: A resource mutex is locked by the first arriving reader and unlocked by the last departing one (tracked via a read-count mutex); 8 continuously-looping readers, each holding a brief 0.2ms simulated read, kept the resource mutex essentially always held. A waiting writer was killed after 3 seconds without ever acquiring the lock, while readers acquired it 85,223 and 85,775 times (two runs) in that window -- real, reproduced starvation.
DEEP:
```c
static int read_count = 0;
static pthread_mutex_t resource, rcount_mtx;

static void *reader(void *arg) {
    while (!stop) {
        pthread_mutex_lock(&rcount_mtx);
        read_count++;
        if (read_count == 1) pthread_mutex_lock(&resource);  /* first reader locks out writers */
        pthread_mutex_unlock(&rcount_mtx);

        /* simulated read, ~0.2ms */

        pthread_mutex_lock(&rcount_mtx);
        read_count--;
        if (read_count == 0) pthread_mutex_unlock(&resource); /* last reader lets a writer in */
        pthread_mutex_unlock(&rcount_mtx);
    }
}
static void *writer(void *arg) { pthread_mutex_lock(&resource); /* ... */ }
```
Compiled with `gcc -std=c11 -Wall -Wextra -pthread` and run twice (8 readers looping continuously, 1 writer arriving after a brief warmup, a 3-second monitoring window), both runs printed the identical pattern: `[t=1s] writer still waiting; reader_acquisitions=~30000`, `[t=2s] ...~58000`, `[t=3s] ...~85000`, ending in `writer: STARVED -- did not acquire the lock in 3s while readers acquired it 85223 times` (run 1) and `85775 times` (run 2).
- This is the "first" readers-writers problem (9.03) exactly as specified: a new reader arriving while a writer waits is never blocked by that waiting writer, only by other readers doing the read-count bookkeeping -- with 8 readers continuously re-arriving, `read_count` essentially never sustains a drop to zero long enough for the writer's already-blocked `pthread_mutex_lock(&resource)` call to win the race.
- This contrasts directly with module 6.10's finding for `pthread_rwlock_t`, where this same glibc's *built-in* rwlock did not show severe starvation under a broadly similar test -- confirming 9.09's point that a specific, chosen policy (this hand-rolled reader-preferring one) can behave very differently from an implementation's own internal default.
FOLLOW:
- Why does this starve so much more severely than 6.10's pthread_rwlock_t test did? => This implementation has no writer-preference mechanism at all (by design, since it deliberately encodes the "first" problem's policy); 6.10's glibc rwlock, despite POSIX not requiring it, apparently applies some internal admission bias that reduces (without eliminating) starvation risk -- this hand-rolled version has no such bias.
- Would fewer readers (say, 2 instead of 8) still starve the writer this severely? => Likely less severely, since read_count would more often reach zero between arrivals, giving the writer's already-queued lock attempt more chances to win the race -- the severity here scales with how continuously readers keep arriving relative to how long the writer has been waiting.
PITFALL: Concluding from module 6.10's pthread_rwlock_t result ("this glibc did not show severe starvation") that reader-preferring readers-writers designs generally do not starve writers in practice. @@ 9.19 | Principal | Concept | tags=deadlock-free-vs-starvation-free,synthesis
Q: Why are "deadlock-free" and "starvation-free" two distinct guarantees, and can a design have one without the other?
SHORT: Deadlock-freedom means the system can never reach a state where progress is permanently impossible for everyone; starvation-freedom means no participant is perpetually passed over while others keep progressing. A system can be deadlock-free while starving one participant indefinitely (9.10's reader-preferring readers-writers: readers keep succeeding, but one writer never does); a resource-cap or ordering fix (9.13, 9.14) can be both, or only the former.
DEEP:
- 9.10's naive readers-writers is the clearest demonstration in this module: it is deadlock-free (the system never gets stuck as a whole -- readers keep acquiring and releasing the resource mutex continuously, real progress by *some* thread happens forever) but not starvation-free (one specific thread, the writer, never gets to run at all in the measured window).
- 9.12's naive dining philosophers is the mirror case: it is not deadlock-free (the whole system can and does get stuck, with *zero* threads making progress under the forced-simultaneous-grab condition) -- deadlock is a stronger, more catastrophic failure than starvation, since it stops everyone, not just one victim.
- 9.13's and 9.14's fixes both restore deadlock-freedom (no more all-stuck-forever states), but neither one, by itself, additionally guarantees starvation-freedom for every individual philosopher -- a philosopher could in principle be repeatedly "unlucky" in the scheduling of who grabs the shared forks first, even though the system as a whole always keeps making progress; this study guide did not measure per-philosopher starvation risk directly for either fix.
- 9.17's ticket-based fair readers-writers is the one design in this module that explicitly targets and verifies starvation-freedom directly (via the strict-ticket-order admission proof), on top of the mutual-exclusion (safety) property every version in this module already provides.
FOLLOW:
- Is starvation-freedom always worth its extra cost? => Not always -- 9.16's buffer-sizing judgment and 9.09's "measure before hand-rolling" discipline both apply here too: starvation-freedom's extra bookkeeping (9.17's ticket counter and broadcast) is worth it specifically when a real requirement (a bounded wait for every participant, not just most) demands it, not as a reflexive upgrade.
- Does deadlock-freedom imply anything at all about fairness? => No -- a deadlock-free system can be maximally unfair to one participant forever while remaining, by definition, never fully stuck; the two properties are logically independent, which is exactly why this module treats them as two separate questions requiring two separate kinds of verification (a hang test for deadlock-freedom, an admission-order log for starvation-freedom).
PITFALL: Treating "the system doesn't hang" (deadlock-freedom, verified by a many-round no-hang test like 9.13's) as proof the system is also fair to every participant. These are different, independently-verifiable properties, and this module's own 9.10 versus 9.17 contrast is the direct evidence that one does not imply the other.
VERIFY: General concurrency theory (liveness properties: deadlock-freedom and starvation-freedom as distinct guarantees); not itself POSIX or C11 text.

@@ 9.20 | Principal | Cross-layer | tags=synthesis,general-lock-ordering,firmware-harness
Q: Generalize 9.13's dining-philosophers resource-ordering fix into a reusable design for a real validation harness where worker threads acquire an arbitrary, dynamically-determined subset of shared hardware-channel and buffer locks -- and connect it explicitly to module 8's own general design.
SHORT: This is 8.16's dynamic global-lock-ordering design, applied concretely: assign every hardware-channel and buffer lock a stable numeric ID at registration time (channels have no natural memory address the way in-process mutexes do), require each worker thread to collect its full needed lock set before acquiring any, sort by ID, and acquire in increasing order -- structurally 9.13's "lowest fork index first" rule, generalized to an arbitrary, runtime-determined set.
DEEP:
1. **Assign stable identities at registration, not at use.** Every hardware channel and buffer gets a fixed numeric ID when the harness initializes, independent of which worker thread ends up needing it or in what order -- this is the direct analog of 9.13's fork indices, which are fixed at table-setup time, not chosen per-philosopher.
2. **A worker thread determines its full lock set before acquiring anything**, the same requirement 8.16 states generally: a test case that needs "whichever channel is free, plus the results buffer" must resolve *which specific channel* first, then include it in the set to be sorted and acquired in order -- acquiring the channel first and only then discovering the buffer is also needed (breaking the "collect everything first" rule) reopens exactly the risk 8.16's design closes.
3. **Sort and acquire in increasing ID order, unconditionally**, via a shared helper function every worker thread calls (8.16's `lock_all()`-style wrapper) rather than trusting each test case's author to remember the rule -- this is the same centralization discipline 9.14's semaphore cap achieves differently (O(1) regardless of participant count) but resource ordering achieves by making the rule impossible to accidentally skip.
4. **Test under forced-simultaneous-acquisition conditions specifically**, the same barrier-synchronized technique 9.12/9.13 used to make their respective bugs and fixes reproduce reliably -- a validation harness's own test suite should include a stress scenario where many worker threads are deliberately synchronized to request overlapping lock sets at the same instant, not just ordinary, incidentally-timed load.
5. **Consider whether admission limiting (9.14's alternative) fits better for this specific harness.** If hardware channels must be requested in a fixed, protocol-mandated order that the harness cannot reorder, 9.14's admission-cap technique (limit concurrent multi-lock-holding worker threads to fewer than the total available channels) sidesteps the ordering requirement entirely, the same trade-off 9.14's own FOLLOW covers.
- This is the concrete, worked answer to 9.08's cross-layer mapping question: the dining-philosophers shape in a real validation harness is exactly "multiple worker threads, each needing more than one shared hardware/buffer resource, in an order not fully under any single thread's control" -- and the fix is not a new idea, it is 8.16's general design and 9.13's specific instance of it, applied together.
FOLLOW:
- Does this design need a central lock-ordering registry, or can each worker thread compute the order independently? => Independent computation is sufficient and preferred -- as long as every worker thread sorts by the same stable, shared identity (the registered numeric IDs), no central coordinator is needed at acquisition time; a registry is only needed once, at initialization, to assign the IDs themselves.
- What if a new hardware channel is added to the harness after IDs have already been assigned to existing channels? => Assign the new channel the next available ID (higher than all existing ones) -- this preserves every existing acquisition order relationship without needing to renumber anything already in use, the same append-only discipline that keeps a global order stable as a system grows.
PITFALL: Building the general lock-ordering design (8.16) and the dining-philosophers-specific fix (9.13) as if they were two separate techniques, when a real system needing both should recognize them as the same mechanism at two different scales -- a fixed, small, known-in-advance resource set (9.13) is simply the special case of the general, dynamic design (8.16) where the "sort and acquire" step happens to be knowable at compile time instead of only at run time.
VERIFY: Module 8.16's general design and 9.13's specific instance, synthesized; not itself a single POSIX or C11 clause.
