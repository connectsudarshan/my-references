# Module 15: Core Data Structures & Algorithms in C

@@ 15.01 | Basic | Concept | tags=linkedlist,pushfront
Q: How do you implement a singly linked list's node and an insert-at-head operation in C, and why is head insertion O(1)?
SHORT: A node holds a value and a pointer to the next node (a struct containing a pointer to its own type, allowed by C11 6.7.2.1p3 since a struct may not contain an instance of itself but may contain a pointer to one). Insert-at-head allocates a new node, points its next at the current head, and returns the new node as the new head: no traversal, so it is O(1) regardless of list length.
DEEP:
Real, compiled, run implementation:
```c
typedef struct Node { int val; struct Node *next; } Node;

Node *push_front(Node *head, int v) {
    Node *n = malloc(sizeof *n);
    n->val = v;
    n->next = head;
    return n;
}
```
Building a list by pushing 5,4,3,2,1 in that order onto an empty list and printing it gives `1 2 3 4 5`, confirming that push_front always puts the newest value first: each call only touches the new node and rewires one pointer, never walking the existing chain.

The self-referential struct (`struct Node *next` inside `struct Node`) works specifically because the member is a *pointer* to the struct type, not the struct type itself; C11 6.7.2.1p3 states this directly: "a structure or union shall not contain a member with incomplete or function type (hence, a structure shall not contain an instance of itself, but may contain a pointer to an instance of itself)." A pointer's size does not depend on the size of what it points to, so the type is well-formed even though `Node` is not yet fully defined at the point the `next` member's type name appears.

Freeing a whole list correctly needs to save `next` before freeing the current node (a bug this page revisits directly in 15.15):
```c
void free_list(Node *head) {
    while (head) { Node *next = head->next; free(head); head = next; }
}
```
FOLLOW:
- Why does push_front take and return a Node* rather than modifying a global head variable? => It keeps the function pure and reusable for any list, including a local one in main, and makes the caller's control over the head pointer explicit rather than hidden as a side effect.
- What is the equivalent O(1) operation at the tail instead of the head? => None, for a plain singly linked list with only a head pointer; appending at the tail requires either walking to the end (O(n)) or maintaining a separate tail pointer alongside head, as the queue implementation in 15.03 does.
PITFALL: Forgetting that a freshly malloc'd node's next field is uninitialized garbage until explicitly set; every insert function must set next itself rather than assuming a fresh node starts as NULL.
VERIFY: C11 6.7.2.1 paragraph 3

@@ 15.02 | Basic | Concept | tags=stack,arraybacked,listbacked
Q: What are the trade-offs between an array-backed stack and a list-backed stack, and how do you implement each?
SHORT: Array-backed: fixed capacity chosen up front, no per-element allocation, push/pop are just an index bump plus a store/load, and the whole stack lives in one contiguous, cache-friendly block. List-backed: unbounded (until memory runs out), but every push allocates a node and every pop frees one, and elements are scattered across the heap.
DEEP:
Array-backed, real compiled code (fixed capacity CAP):
```c
typedef struct { int data[CAP]; int top; } ArrStack;
void as_push(ArrStack *s, int v) { s->data[++s->top] = v; }
int  as_pop(ArrStack *s)  { return s->data[s->top--]; }
```
Pushing 1, 2, 3 then popping until empty produced `3 2 1`, the expected LIFO order, with `top` starting at -1 to mean "empty."

List-backed, real compiled code (pushes and pops at the head, same push_front idea as 15.01):
```c
typedef struct { Node *top; } LStack;
void ls_push(LStack *s, int v) { Node *n = malloc(sizeof *n); n->val = v; n->next = s->top; s->top = n; }
int  ls_pop(LStack *s)  { Node *n = s->top; int v = n->val; s->top = n->next; free(n); return v; }
```
Pushing 1, 2, 3 then popping three times gave `3 2 1` as well, the same LIFO contract, verified independently of the array version.

The real trade-off for a firmware interview to state unprompted: the array version has a hard, compile-time-known capacity and zero allocator involvement (good for an ISR-adjacent or allocation-forbidden context, module 17's territory), while the list version never overflows short of running out of heap but pays a malloc/free call, and a pointer-chase, on every single push/pop (15.14 covers the cache-locality cost of that pointer chasing directly).
FOLLOW:
- What happens on as_push if the stack is already at capacity (top == CAP - 1)? => This minimal version has no bounds check at all, so it silently writes past data[CAP-1], a buffer overflow; a real implementation must check top against CAP before incrementing.
- Why does ls_pop free the node it just read from? => Because the list-backed stack owns its nodes; once a value is popped out, the node backing it is no longer part of the stack and would otherwise leak if not freed.
PITFALL: Shipping the array-backed stack without a capacity check "because it will never realistically overflow in practice"; that assumption is exactly the kind of unchecked-bound bug module 17 covers as a real security and reliability hazard.

@@ 15.03 | Basic | Concept | tags=queue,ringbuffer,listbacked
Q: What are the trade-offs between a circular-array queue and a list-backed queue, and how do you implement each correctly?
SHORT: A circular array queue wraps head/tail indices modulo its fixed capacity, giving O(1) enqueue/dequeue with no allocation and full cache locality, but a fixed maximum size. A list-backed queue needs both a head and a tail pointer (unlike a stack, which only ever touches one end) to get O(1) enqueue without walking the whole list; it has no fixed capacity but pays per-node allocation.
DEEP:
Circular array, real compiled code and run, deliberately wrapping the tail index around the capacity:
```c
typedef struct { int data[CAP]; int head, tail, count; } RingQueue;
void rq_push(RingQueue *q, int v) { q->data[q->tail] = v; q->tail = (q->tail + 1) % CAP; q->count++; }
int  rq_pop(RingQueue *q)  { int v = q->data[q->head]; q->head = (q->head + 1) % CAP; q->count--; return v; }
```
With CAP=5: pushing 10,20,30, popping one (10), then pushing 40,50 (which wraps `tail` back around past index 4 to index 0) and draining the rest gave `10 20 30 40 50`, the correct FIFO order across the wraparound, confirming the modulo arithmetic handles the wrap correctly.

List-backed, real compiled code and run, with the two-pointer head/tail design:
```c
typedef struct { Node *head, *tail; } LQueue;
void lq_push(LQueue *q, int v) {
    Node *n = malloc(sizeof *n); n->val = v; n->next = NULL;
    if (q->tail) q->tail->next = n; else q->head = n;
    q->tail = n;
}
int lq_pop(LQueue *q) {
    Node *n = q->head; int v = n->val;
    q->head = n->next;
    if (!q->head) q->tail = NULL;
    free(n);
    return v;
}
```
Pushing 1,2,3 then popping three times gave `1 2 3`, the expected FIFO order, verified separately from the array version.

The `if (!q->head) q->tail = NULL;` line in lq_pop is easy to miss and is the classic list-queue bug: after popping the last element, `tail` must be reset too, or the next push will link a new node onto a stale, freed tail pointer.
FOLLOW:
- Why does a stack only need one pointer (top) but a queue needs two (head and tail)? => A stack always inserts and removes at the same end, so one pointer tracks everything; a queue inserts at one end and removes at the other, so both ends need to be independently reachable in O(1).
- What happens to the circular array queue if you push when count == CAP? => This minimal version has no full-check, so it silently overwrites data at the old head index before the head pointer catches up, corrupting the oldest unread element; a production version must check count against CAP before pushing (module 18's ring buffer question covers this hardening in more depth).
PITFALL: Implementing a list-backed queue with only a head pointer and walking to the end on every push "since it is simple"; that turns every enqueue into O(n), defeating the entire point of a queue's expected O(1) operations.

@@ 15.04 | Intermediate | Concept | tags=doublylinkedlist
Q: How does a doubly linked list's insert and remove differ from a singly linked list's, and what makes O(1) removal-by-pointer possible?
SHORT: Each node carries both next and prev pointers. Removing a given node (with no traversal from the head) is O(1) because the node itself already knows both its neighbors, so their links can be rewired directly; a singly linked list needs the *previous* node's address to unlink a given node, which normally requires a traversal from the head to find it.
DEEP:
Real, compiled, run implementation:
```c
typedef struct DNode { int val; struct DNode *prev, *next; } DNode;

DNode *dll_insert_after(DNode *pos, int v) {
    DNode *n = malloc(sizeof *n);
    n->val = v;
    n->prev = pos;
    n->next = pos ? pos->next : NULL;
    if (pos) { if (pos->next) pos->next->prev = n; pos->next = n; }
    return n;
}

void dll_remove(DNode *n) {
    if (n->prev) n->prev->next = n->next;
    if (n->next) n->next->prev = n->prev;
    free(n);
}
```
Building `1 -> 2 -> 3` and then removing the middle node (`2`) directly via `dll_remove(b)` (no traversal needed since the caller already held a pointer to it) produced `1 3`, confirming the remaining nodes' prev/next links were correctly rewired around the removed node.

This O(1)-removal-given-a-pointer property is exactly why doubly linked lists are the usual backing structure for an LRU cache's internal list, or any structure where an external index (a hash table mapping a key to a list node pointer) needs to delete an arbitrary element quickly without a search.
FOLLOW:
- Why does dll_remove check n->prev and n->next for NULL before dereferencing? => Because the node being removed might be the first node (prev is NULL) or the last node (next is NULL) in the list, and unconditionally dereferencing either would be a NULL-pointer dereference in those cases.
- What is the memory cost of the extra prev pointer compared to a singly linked list? => One extra pointer per node (commonly 8 bytes on a 64-bit target), doubling the pointer overhead per node while leaving the payload (val here) unchanged.
PITFALL: Removing a node by pointer without first updating both of its neighbors' links; forgetting the prev side leaves the list traversable forward but corrupted when traversed backward, and forgetting the next side breaks forward traversal entirely.

@@ 15.05 | Intermediate | Scenario | fig=linkedlist | tags=reverse,iterative
Q: Reverse a singly linked list in place, iteratively, without allocating any new nodes. Walk through what each pointer is doing.
SHORT: Walk the list once with three pointers: prev (starts NULL), cur (starts at head), and a saved next; at each step, save cur->next, then point cur->next at prev (reversing that one link), then advance prev and cur forward. When cur becomes NULL, prev is the new head.
DEEP:
Real, compiled, run implementation:
```c
Node *reverse_iter(Node *head) {
    Node *prev = NULL, *cur = head;
    while (cur) {
        Node *next = cur->next;
        cur->next = prev;
        prev = cur;
        cur = next;
    }
    return prev;
}
```
Starting from `1 2 3 4 5` (built by pushing 5..1 as in 15.01), calling `reverse_iter` and printing the result gave `5 4 3 2 1`, confirming the reversal.

Tracing the pointer state at each iteration on a short 3-node list `A -> B -> C -> NULL` makes the mechanism concrete:

| step | prev | cur | next (saved) | link just rewired |
|---|---|---|---|---|
| start | NULL | A | - | - |
| 1 | A | B | B | A->next now points to NULL (was B) |
| 2 | B | C | C | B->next now points to A (was C) |
| 3 | C | NULL | NULL | C->next now points to B (was NULL) |

After step 3, `cur` is NULL so the loop ends, and `prev` (C) is returned as the new head: the list is now `C -> B -> A -> NULL`, exactly the reverse of the original, and no node was ever allocated or freed; only the `next` pointers were rewired.

This is the operation the assigned figure illustrates: the node/next pointer structure, and this exact link-by-link rewiring as the list is walked once.
FOLLOW:
- Why must next be saved before overwriting cur->next? => Because cur->next = prev immediately destroys the only remaining reference to the rest of the original list; without saving it first, the traversal would lose the rest of the list right after reversing the first link.
- What is the time and space complexity? => O(n) time (one pass, one pointer rewrite per node) and O(1) extra space (three pointer variables regardless of list length), which is the benchmark a recursive version (15.06) is compared against.
PITFALL: Returning cur instead of prev at the end of the loop; cur is NULL by the time the loop exits, so returning it gives a reversed list whose head pointer is lost, not the actual new head.
VERIFY: self-referential struct via pointer member, C11 6.7.2.1 paragraph 3

@@ 15.06 | Intermediate | Concept | tags=reverse,recursive,stackdepth
Q: Reverse a singly linked list recursively. How does its resource cost compare to the iterative version?
SHORT: Recurse to the end of the list first, then, unwinding back up, make each node's next point back at the node that called it, and set the original head's next to NULL. Correctness matches the iterative version exactly, but each recursive call adds a stack frame, so reversing a list of length n uses O(n) call-stack space, versus the iterative version's O(1) extra space; a long enough list risks stack overflow recursively where the loop never would.
DEEP:
Real, compiled, run implementation:
```c
Node *reverse_rec(Node *head) {
    if (!head || !head->next) return head;
    Node *new_head = reverse_rec(head->next);
    head->next->next = head;
    head->next = NULL;
    return new_head;
}
```
Applied to the already-iteratively-reversed `5 4 3 2 1` list from 15.05, calling `reverse_rec` and printing gave `1 2 3 4 5` back, confirming the recursive version reverses correctly (and, applied twice in a row here, returns to the original order, a useful sanity check of its own).

The base case (`!head || !head->next`) stops recursion at an empty list or a single remaining node, which is already "reversed" trivially. Unwinding back up the call stack, `head->next->next = head` is the key line: it makes the node that is one step *closer to the original head* point back at `head`, effectively reversing that one link, exactly mirroring what the iterative version's `cur->next = prev` does, just performed in the opposite traversal order (tail-to-head as the stack unwinds, instead of head-to-tail as the loop advances).

This function is not written as a tail call (there is work, `head->next->next = head; head->next = NULL;`, after the recursive call returns), so a compiler cannot trivially turn it into a loop even with tail-call optimization; module 3's coverage of tail calls and stack growth is directly relevant background for why this specific recursive shape costs real stack space per call, unlike an actually tail-recursive function.
FOLLOW:
- Could this be rewritten to be tail-recursive? => Yes, by passing an accumulator (the growing reversed list) as an extra parameter and doing the pointer rewiring before the recursive call instead of after, which is essentially rewriting the iterative version's loop as recursion with prev/cur as parameters.
- Why prefer the iterative version in firmware code with a hard stack size limit? => Because its O(1) extra space has no dependency on list length, while the recursive version's stack usage grows linearly with list length and can overflow a small, fixed embedded stack on a long enough list, a failure mode the iterative version cannot have.
PITFALL: Using unmodified list-length-proportional recursion (as written here) on a list whose maximum length is not tightly bounded; it is correct but trades a real, sometimes hard-to-diagnose stack-overflow risk for arguably more elegant code.

@@ 15.07 | Intermediate | Numeric | tags=middlenode,slowfast
Q: Using the slow/fast pointer technique on a 7-node list holding 1..7, trace exactly where slow and fast are after each step, and confirm why slow ends up on the middle element.
SHORT: slow and fast both start at the head; each loop step moves slow one node and fast two nodes, stopping once fast reaches the end. Since fast covers ground twice as fast as slow, when fast has traveled to the end (6 hops for a 7-node list), slow has traveled half as far (3 hops), landing exactly on node 4, the middle of 1..7. Verified: find_middle returned 4.
DEEP:
Real, compiled, run code:
```c
Node *find_middle(Node *head) {
    Node *slow = head, *fast = head;
    while (fast && fast->next) { slow = slow->next; fast = fast->next->next; }
    return slow;
}
```
Tracing the loop on the 7-node list `1 2 3 4 5 6 7` (indices 1..7 by value, so "node k" below just means the node holding value k):

| iteration | slow (before) | fast (before) | fast && fast->next? | slow (after) | fast (after) |
|---|---|---|---|---|---|
| 1 | 1 | 1 | yes | 2 | 3 |
| 2 | 2 | 3 | yes | 3 | 5 |
| 3 | 3 | 5 | yes | 4 | 7 |
| 4 | 4 | 7 | no (7->next is NULL) | loop stops | loop stops |

The loop condition `fast && fast->next` fails once fast is at node 7 (the last node, whose next is NULL), so the loop body never runs a 4th time; slow is left at node 4, exactly the middle of the 7 nodes, matching the real program's printed output `middle of 1..7 is 4`.

Generalizing: for an odd-length list of n nodes, fast needs (n-1)/2 full double-steps to reach the last node, and slow (moving half as fast) ends up at node number (n-1)/2 + 1, which is exactly the middle element (node 4 of 7 here: (7-1)/2 + 1 = 4). For an even-length list, this exact loop condition lands slow on the *second* of the two middle nodes (worth stating as a deliberate, testable convention choice, since some interview specifications instead want the first of the two).
FOLLOW:
- What would change if the loop condition were just while (fast) instead of while (fast && fast->next)? => It would attempt fast->next->next when fast is the last node (fast->next is NULL), dereferencing a NULL pointer's next field, an immediate crash; the && fast->next check exists specifically to stop one iteration earlier.
- Does this technique require knowing the list's length in advance? => No, that is exactly its advantage over "count the nodes, then walk length/2 steps," which requires two full passes; slow/fast finds the middle in a single pass.
PITFALL: Assuming this loop's specific stopping condition always lands on the mathematically "first" middle node for an even-length list; the exact node returned for an even count depends on the precise loop condition used, and different (still-correct-looking) variants disagree on which of the two middles they return.

@@ 15.08 | Intermediate | Debug | tags=cycledetection,floyd
Q: A teammate's cycle-detection function marks every visited node's address in a growing array and checks each new node against that array before continuing. Why is this both slower and riskier than Floyd's algorithm, and how do you replace it?
SHORT: The visited-array approach needs O(n) extra memory that must be sized or reallocated for an unknown-length list (and is simply wrong, not just slow, if the list turns out to be cyclic and thus unbounded in "nodes visited so far" terms), plus an O(n) scan per new node for an unsorted array, giving O(n^2) overall. Floyd's slow/fast pointer algorithm detects a cycle in O(n) time with O(1) extra space and no upfront sizing assumption at all.
DEEP:
Real, compiled, run implementation of Floyd's algorithm, and the exact scenario that breaks a visited-array approach:
```c
int has_cycle(Node *head) {
    Node *slow = head, *fast = head;
    while (fast && fast->next) {
        slow = slow->next;
        fast = fast->next->next;
        if (slow == fast) return 1;
    }
    return 0;
}
```
Built a 7-node list `1..7`, confirmed `has_cycle` correctly returns 0 on the plain list, then manually linked node 7's next back to node 4 (simulating a real corrupted-list bug) and re-ran the same function: it correctly returned 1 this time. Both results were verified against the actual list structure, not assumed.

Why the visited-array approach is worse in exactly the way that matters for this bug class: a cyclic list has no well-defined "end," so any traversal that keeps appending "nodes visited so far" to a container without ever checking for a repeat first (rather than checking membership before each append) never terminates at all on a truly cyclic list, looping forever while growing an unbounded array, exactly the failure this detection code is supposed to catch. Even a correctly-ordered "check membership, then append" version is O(n) per lookup in a plain array (or needs a hash set to get O(1) lookups, at the cost of real extra memory), while Floyd's two-pointer technique needs no auxiliary storage proportional to list size at all: just two Node* variables, regardless of whether the list has 10 nodes or 10 million.

The mechanism: if there is a cycle, fast (moving twice as fast) is guaranteed to eventually lap slow from behind within the cycle and land on the exact same node, because their relative speed inside the cycle is 1 node per iteration, so the gap between them shrinks by exactly 1 each step until it hits 0. If there is no cycle, fast simply reaches the natural NULL end first, and the loop's `fast && fast->next` condition stops it there.
FOLLOW:
- Does Floyd's algorithm tell you where the cycle begins, not just that one exists? => The basic version above only answers yes/no; a well-known extension (reset one pointer to head, then advance both one step at a time until they meet again) locates the exact node where the cycle starts, a natural interview follow-up.
- Why must the loop check fast && fast->next rather than just fast, exactly as in 15.07? => For the same reason: to avoid dereferencing fast->next->next when fast is already the last node in a non-cyclic list, which would otherwise be a NULL-pointer dereference.
PITFALL: Building "cycle detection" as "grow a set of visited addresses" without first checking membership before insertion; on an actually cyclic list, that specific ordering mistake means the detection code itself never terminates, the exact bug it was meant to catch.

@@ 15.09 | Intermediate | Concept | tags=mergelists,sorted
Q: Merge two already-sorted singly linked lists into one sorted list, without allocating any new nodes.
SHORT: Use a dummy head node and a tail pointer; repeatedly compare the two lists' current front nodes, splice the smaller one onto the result's tail, and advance that list's pointer, until one list runs out, then splice the entire remainder of the other list onto the tail in one step.
DEEP:
Real, compiled, run implementation:
```c
Node *merge_sorted(Node *a, Node *b) {
    Node dummy = {0, NULL};
    Node *tail = &dummy;
    while (a && b) {
        if (a->val <= b->val) { tail->next = a; a = a->next; }
        else { tail->next = b; b = b->next; }
        tail = tail->next;
    }
    tail->next = a ? a : b;
    return dummy.next;
}
```
Merging `1 3 5 7` with `2 4 6` produced `1 2 3 4 5 6 7`, a fully sorted, interleaved result, confirming both the comparison logic and the final "attach whatever is left" step.

The dummy stack-local node (`Node dummy = {0, NULL};`) is a standard technique to avoid special-casing "what is the very first node of the result": without it, the first splice would need its own separate code path to set a genuine head pointer instead of just advancing `tail->next`. `dummy.next` at the end is exactly that real head, decided naturally by whichever list contributed the very first node.

No new nodes are allocated: every node in the result is one of the original nodes from `a` or `b`, just relinked; this is the same "rewire pointers, do not copy data" spirit as the in-place reversal in 15.05.
FOLLOW:
- What happens if the input lists are not actually sorted? => The function still runs and produces some list, but it will not be sorted; the algorithm's correctness depends entirely on the precondition that both inputs are already sorted, exactly like bsearch's precondition in module 14.
- Is this the same core idea used in merge sort's merge step? => Yes exactly; this two-pointer, take-the-smaller-front repeatedly technique is the merge step of merge sort, just applied here to two already-independently-sorted lists rather than to two halves of a list being recursively sorted.
PITFALL: Using <= versus < in the comparison inconsistently between two similar merge functions in the same codebase; it changes which list's element comes first when values are equal, which matters if later code depends on a stable interleaving of equal keys.

@@ 15.10 | Advanced | Concept | tags=bst,insert,traversal
Q: Implement BST insertion and an inorder traversal, and explain why inorder traversal visits nodes in sorted order.
SHORT: Insert recursively: go left if the new value is smaller than the current node, right if larger, and attach a new node when you fall off the tree. Inorder traversal (left subtree, then this node, then right subtree, recursively) visits sorted order specifically because the BST invariant guarantees every node in a left subtree is smaller and every node in a right subtree is larger than the node itself, at every level.
DEEP:
Real, compiled, run implementation:
```c
typedef struct BNode { int val; struct BNode *left, *right; } BNode;

BNode *bst_insert(BNode *root, int v) {
    if (!root) { BNode *n = malloc(sizeof *n); n->val = v; n->left = n->right = NULL; return n; }
    if (v < root->val) root->left = bst_insert(root->left, v);
    else if (v > root->val) root->right = bst_insert(root->right, v);
    return root;
}

void inorder(BNode *root) {
    if (!root) return;
    inorder(root->left);
    printf("%d ", root->val);
    inorder(root->right);
}
```
Inserting `5, 3, 8, 1, 4, 7, 9` in that order and running `inorder` printed `1 3 4 5 7 8 9`, fully sorted ascending, regardless of the arbitrary insertion order.

The recursive insert function relies on the same "return the (sub)tree root, let the caller relink it" pattern used throughout this module: `root->left = bst_insert(root->left, v);` both recurses into the left subtree and, on the way back up, rewrites the parent's left pointer to whatever that subtree's root now is (unchanged for every level except the one where the new node was actually attached).

This particular insertion order (5,3,8,1,4,7,9) happens to build a reasonably balanced tree; a BST's worst case (inserting already-sorted data, e.g. 1,2,3,4,5,6,7 in order) degenerates into a linked list with O(n) height, turning every operation from the expected O(log n) into O(n), a fact worth raising unprompted as the direct motivation for self-balancing variants (AVL, red-black trees) that this page does not implement but that an interviewer will expect you to know exist.
FOLLOW:
- What would a preorder traversal (node, then left, then right) be useful for instead of sorted output? => Reconstructing the tree's own structure (e.g. serializing it for later rebuilding), since preorder visits each subtree's root before its children, capturing the shape top-down.
- Why does bst_insert return BNode* instead of taking a BNode** and modifying the root in place? => Both work; the return-and-relink style used here reads more like ordinary recursive functions elsewhere in this module and avoids explicit pointer-to-pointer syntax, at the (usually negligible) cost of reassigning a pointer at every level on the way back up even when it did not change.
PITFALL: Assuming a BST built from arbitrary insertion order is automatically balanced; sorted or near-sorted input insertion order produces a degenerate, effectively linear tree with none of a BST's expected logarithmic performance.

@@ 15.11 | Advanced | Concept | tags=bst,search,delete
Q: Implement BST search and deletion, specifically the case of deleting a node that has two children.
SHORT: Search walks left or right by comparison exactly like insert, stopping at a match or a NULL. Deleting a leaf or a one-child node just splices the single child (or NULL) into the parent's slot. Deleting a two-child node instead copies in the value of its inorder successor (the smallest value in its right subtree) and then recursively deletes that successor node from the right subtree, where it is guaranteed to have at most one child.
DEEP:
Real, compiled, run implementation:
```c
BNode *bst_search(BNode *root, int v) {
    if (!root || root->val == v) return root;
    return v < root->val ? bst_search(root->left, v) : bst_search(root->right, v);
}

BNode *bst_min(BNode *root) { while (root->left) root = root->left; return root; }

BNode *bst_delete(BNode *root, int v) {
    if (!root) return NULL;
    if (v < root->val) root->left = bst_delete(root->left, v);
    else if (v > root->val) root->right = bst_delete(root->right, v);
    else {
        if (!root->left)  { BNode *r = root->right; free(root); return r; }
        if (!root->right) { BNode *l = root->left;  free(root); return l; }
        BNode *succ = bst_min(root->right);
        root->val = succ->val;
        root->right = bst_delete(root->right, succ->val);
    }
    return root;
}
```
On the same tree as 15.10 (inorder `1 3 4 5 7 8 9`), calling `bst_search(root, 7)` found it and `bst_search(root, 6)` correctly reported missing. Deleting the root itself (value 5, which has two children) and reprinting inorder gave `1 3 4 7 8 9`: 5 is gone, the remaining values are still fully sorted, confirming the two-child deletion correctly preserved the BST invariant.

The reason the inorder successor (`bst_min` of the right subtree) is exactly the right replacement value: it is the smallest value that is still larger than everything in the deleted node's left subtree, and by construction (it is the leftmost node of the right subtree) it has no left child of its own, so deleting it recursively from the right subtree always falls into the "zero or one child" cases already handled, never re-triggering the two-child case for the successor itself.
FOLLOW:
- Could the inorder predecessor (largest value in the left subtree) be used instead of the successor? => Yes, symmetrically; either choice preserves the BST invariant equally well, and real implementations differ only by convention on which one they pick.
- What is the time complexity of bst_delete on a balanced tree of n nodes? => O(log n), the same as search and insert, since it does at most one root-to-leaf walk (plus, for the two-child case, one more walk down to find the successor, still bounded by the tree's height).
PITFALL: Deleting a two-child node by just picking one of its two children to promote directly into its place; that breaks the BST invariant for the rest of that child's original subtree unless the successor/predecessor value-copy-then-recursive-delete pattern (or an equivalent rebalancing) is used instead.

@@ 15.12 | Advanced | Concept | tags=hashtable,chaining
Q: Design and implement a hash table with chaining: what does each bucket hold, and how do insert and lookup work?
SHORT: An array of NBUCKETS bucket heads, each a singly linked list of (key, value) nodes. Insert hashes the key to pick a bucket, then pushes a new node onto that bucket's list (O(1), no collision resolution needed beyond chaining). Lookup hashes the key the same way, then walks only that one bucket's chain comparing keys, so average-case lookup is O(1 + load factor) rather than O(n) over the whole table.
DEEP:
Real, compiled, run implementation, keyed by string (a realistic case: named config fields):
```c
#define NBUCKETS 8
typedef struct HNode { char *key; int val; struct HNode *next; } HNode;
typedef struct { HNode *buckets[NBUCKETS]; } HashTable;

unsigned hash_str(const char *s) {
    unsigned h = 5381;
    while (*s) h = h * 33 + (unsigned char)*s++;   /* djb2 */
    return h;
}

void ht_put(HashTable *t, const char *key, int val) {
    unsigned idx = hash_str(key) % NBUCKETS;
    HNode *n = malloc(sizeof *n);
    n->key = dup_str(key);   /* heap-owned copy; caller's key string may not outlive this call */
    n->val = val;
    n->next = t->buckets[idx];
    t->buckets[idx] = n;
}

int ht_get(HashTable *t, const char *key, int *out) {
    unsigned idx = hash_str(key) % NBUCKETS;
    for (HNode *n = t->buckets[idx]; n; n = n->next)
        if (strcmp(n->key, key) == 0) { *out = n->val; return 1; }
    return 0;
}
```
(`dup_str` is a small manual `malloc` + `memcpy` helper; C11's string.h has no standard `strdup`, that name is a POSIX addition, so this page implements its own copy rather than reach outside ISO C.)

Inserting `"lba_start"->0`, `"lba_count"->4096`, `"block_size"->4096` and then looking up `"block_size"` correctly returned found=1, value=4096; looking up `"missing_key"` correctly returned found=0.

Each `ht_put` pushes onto the front of its bucket's chain, exactly like 15.01's `push_front`, which is why a hash table with chaining is naturally described as "an array of linked lists": every bucket is a small independent singly linked list, and this table's entire design is 15.01's data structure applied NBUCKETS times over.
FOLLOW:
- What happens as more keys land in the same bucket? => The chain for that bucket grows, and lookup degrades from O(1) toward O(chain length); this is exactly the load-factor and hash-quality concern covered directly in 15.13.
- Why hash to unsigned and then take % NBUCKETS rather than working in signed int? => To avoid a negative hash value ever reaching the modulo (which would either be undefined behavior territory for a negative dividend in some formulations or simply produce a negative index), unsigned arithmetic wraps predictably and stays non-negative by construction.
PITFALL: Growing a hash table's load far beyond its bucket count without ever resizing (rehashing into a larger bucket array); every chain grows unbounded and lookup performance degrades toward a plain linked list's O(n), silently, with no error or warning.

@@ 15.13 | Advanced | Trap | tags=hashfunction,collisions,loadfactor
Q: A hash table using `hash(key) = (key * 4) % NBUCKETS` performs badly on keys that are all multiples of 4 (a realistic pattern for, say, 4-byte-aligned addresses used as keys). Why, and how does a better hash function fix it?
SHORT: Multiplying every key by 4 before the modulo means every key's hash is itself a multiple of 4 modulo NBUCKETS; if the keys are already multiples of 4 (aligned addresses are a classic real example), the extra *4 factor collapses most of the key space into a small handful of buckets instead of spreading across all NBUCKETS. A hash that mixes the bits thoroughly (avalanche-style mixing) spreads the same key set far more evenly, regardless of the keys' own alignment pattern.
DEEP:
Real, compiled, run measurement, with 8 keys that are all multiples of 4 (0, 4, 8, ..., 28) hashed into 16 buckets:
```c
unsigned bad_hash_pow2(int key) { return (unsigned)(key * 4) % NBUCKETS; }
unsigned good_hash(int key) {
    unsigned h = (unsigned)key;
    h ^= h >> 16; h *= 0x7feb352dU;
    h ^= h >> 15; h *= 0x846ca68bU;
    h ^= h >> 16;
    return h % NBUCKETS;
}
```
Actual measured worst-case bucket load across all 16 buckets for the same 8 keys:
```
worst-case bucket load: bad_hash_pow2=8, good_hash=2 (out of 8 keys)
```
`bad_hash_pow2` put every single one of the 8 keys into the exact same bucket (a worst-case load of 8, meaning it degenerated to a plain 8-element linked list for every single lookup); `good_hash` spread the same 8 keys so that no bucket held more than 2, close to the ideal 8/16 = 0.5 average load.

Why the collapse happens mathematically: with `NBUCKETS = 16` (a power of two) and every key already a multiple of 4, `key * 4` is a multiple of 16 for every key that is itself a multiple of 4, so `(key * 4) % 16` is 0 for every single one of them. A hash function that only ever multiplies and takes a modulo with a power-of-two table size is throwing away exactly the low bits that would otherwise distinguish these keys, precisely when the input already has a nonrandom low-bit pattern (address alignment is one of the most common real sources of exactly this pattern).

`good_hash`'s xor-shift-multiply sequence (a widely used integer hash mixing pattern) deliberately spreads influence from every input bit across every output bit before the final modulo, so a shared low-bit pattern in the input no longer maps to a shared low-bit pattern in the output.
FOLLOW:
- Would simply using a prime number of buckets instead of a power of two have fixed bad_hash_pow2 on its own? => It would help somewhat (a prime modulus tends to break up simple multiplicative patterns better than a power of two), but it does not fix the root problem the same way real bit-mixing does, and it constrains the table size to primes, which complicates resizing logic.
- Is this bug something -Wall/-Wextra would catch? => No; both hash functions compile silently and "work" in the sense of returning a valid bucket index every time, the defect is purely about the statistical distribution of outputs, which no compiler warning inspects.
PITFALL: Choosing a hash function that looks "randomish" by eye (multiply by a constant, take a modulo) without checking its actual bucket-load distribution against realistic key patterns; a hash that is fine on random test keys can collapse badly on the structured key patterns real systems actually produce.
VERIFY: djb2/xor-shift-multiply mixing constants are widely published integer-hash folklore, not ISO C or POSIX-specified; treat the specific constants as implementation choice, not a standard.

@@ 15.14 | Advanced | Cross-layer | tags=cachelocality,pointerchasing
Q: Why is traversing a linked list measurably slower than traversing an equally-sized array, even though both are nominally O(n) traversals?
SHORT: An array's elements are contiguous, so sequential access lets the CPU's hardware prefetcher and cache lines do their job: one cache-line fetch covers many consecutive elements. A linked list's nodes are scattered wherever malloc happened to place them, so each next-pointer follow is a fresh, unpredictable memory address, likely a fresh cache miss every single node, turning "O(n) with a small constant" into "O(n) with a much larger constant" purely from memory latency, not instruction count.
DEEP:
Real, compiled (with -O2), measured benchmark summing 2,000,000 ints both ways:
```c
long sum1 = 0;
for (int i = 0; i < N; i++) sum1 += arr[i];          /* array traversal */

long sum2 = 0;
for (Node *p = head; p; p = p->next) sum2 += p->val;  /* list traversal, same N nodes */
```
Actual measured result on this run:
```
array sum=1999999000000 time=0.0013s
list  sum=1999999000000 time=0.0119s
list/array ratio: 9.5x
```
Both loops compute the identical mathematical result (confirmed: the two sums match exactly), and both are unambiguously O(n) in the number of elements touched, yet the list traversal took roughly 9.5 times longer in this run. The instruction count per element is similar (a load, an add, a pointer/index advance); the difference is almost entirely memory-system behavior: the array's sequential access pattern lets the CPU prefetch upcoming cache lines before they are needed, while the list's node addresses are effectively random relative to each other (wherever the allocator happened to place each malloc call), so most next-pointer dereferences miss cache and pay full DRAM latency.

This is exactly the kind of fact a Principal-level firmware interview expects stated unprompted when a candidate is asked to choose a data structure for a hot path: "asymptotically the same O(n)" is not the same claim as "equally fast in practice," and for latency-sensitive embedded code, a contiguous array (or an array-backed structure like 15.02/15.03's array-backed stack/queue) is very often the right default over a linked structure specifically because of this cache-locality gap, independent of any algorithmic complexity argument.
FOLLOW:
- Would this gap shrink or grow on a target with no data cache at all (a very small microcontroller)? => It would shrink toward zero, since without a cache hierarchy, both access patterns pay a similar flat per-access memory latency; the gap measured here is a cache-hierarchy effect specific to CPUs with cache, not a fundamental property of pointer-chasing itself.
- Does allocating all the list's nodes from one contiguous arena instead of individually malloc'ing each one help? => Yes, substantially in practice; if the nodes happen to end up physically near each other (a common technique: a node pool/arena allocator), sequential traversal gets much better locality than nodes scattered across many separate heap allocations, even though the pointer-chasing access pattern itself is unchanged.
PITFALL: Choosing a data structure purely by asymptotic complexity ("O(n) is O(n)") without considering the real memory-access pattern each option produces; two structures with identical big-O traversal cost can differ by nearly an order of magnitude in actual wall-clock time.

@@ 15.15 | Advanced | Debug | tags=useafterfree,listfree
Q: A list-freeing function frees each node and then still reads that node's next field to continue the loop. What is the bug, how does the toolchain catch it, and what is the fix?
SHORT: free(p) followed by p = p->next reads the next field of memory that was just deallocated: a use-after-free, undefined behavior. GCC 13's own -Wall diagnoses this specific pattern statically (-Wuse-after-free), and AddressSanitizer catches it dynamically at the exact faulting read with a full report. Fix: save next into a local variable before calling free on the current node.
DEEP:
The buggy function, and the fix, both real and compiled:
```c
/* BUG: use-after-free */
void free_list_bad(Node *head) {
    Node *p = head;
    while (p) { free(p); p = p->next; }   /* reads p->next AFTER p was freed */
}

/* FIX: save next before freeing */
void free_list_good(Node *head) {
    while (head) {
        Node *next = head->next;   /* saved first */
        free(head);
        head = next;               /* uses the saved copy, never touches freed memory */
    }
}
```
Just compiling `free_list_bad` with `-std=c11 -Wall -Wextra` (no sanitizer flag needed) produced this real diagnostic on this toolchain:
```
warning: pointer 'p' used after 'free' [-Wuse-after-free]
    p = p->next;
        ~~^~~~~~
  note: call to 'free' here
    free(p);
```
Building the same buggy function with `-fsanitize=address -g` and actually running it produced a full runtime report at the exact faulting line:
```
==ERROR: AddressSanitizer: heap-use-after-free on address ...
READ of size 8 ... in free_list_bad ... uafbug2.c:5
freed by thread T0 here:
    #1 free_list_bad ... uafbug2.c:5
previously allocated by thread T0 here: ... malloc ...
```
The fixed version, run on a real 4-node list, printed "ok" with no warning and no sanitizer report, confirming both that saving `next` before freeing eliminates the diagnosed defect and that the corrected function still does its actual job (freeing every node).

This exact bug (free, then dereference the just-freed pointer's own field to decide what comes next) is one of the most common real-world linked-list defects, precisely because the "obvious" one-line loop body (`free(p); p = p->next;`) reads correctly at a glance and often does not crash immediately in practice (freed memory is frequently left readable, if not reliable, for a short time by many allocators), which is exactly why relying on "it did not crash when I tested it" is not evidence of correctness for this class of bug.
FOLLOW:
- Why does this bug not reliably crash without a sanitizer? => Because free() typically does not zero or unmap the memory it releases immediately; the bytes are often still physically present and readable (though logically invalid and subject to being overwritten by any subsequent allocation), so a use-after-free read frequently "succeeds" with a plausible-looking but logically meaningless value instead of crashing.
- Would reordering to p = p->next; free(p_prev) (tracking the previous node explicitly) also fix it? => Yes, any ordering that reads next before that specific node is freed works; saving next into a local variable first is simply the most direct, minimal-state version of that same fix.
PITFALL: Trusting a clean, crash-free test run of exactly this kind of loop as proof of correctness; both the specific static warning and the dynamic sanitizer report shown here exist precisely because ordinary testing frequently fails to reveal a use-after-free at all.

Q: Design an intrusive linked list, where the link pointers live inside the struct being linked rather than in a separate wrapper node, and show how a caller recovers the containing struct from just a link pointer.
SHORT: Embed a plain { struct ListNode *next; } member directly inside the payload struct; the list itself only ever stores and walks pointers to that embedded member. DEEP:
Real, compiled, run implementation:
```c
typedef struct ListNode { struct ListNode *next; } ListNode;

#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))

typedef struct {
    int id;
    char name[16];
    ListNode link;     /* embedded node: no separate allocation for list bookkeeping */
} Device;
```
Linking two real Device structs by their embedded `link` members and walking the list purely through `ListNode *` pointers, then recovering each `Device*` at every step:
```c
Device d1 = { 1, "nand0", { NULL } };
Device d2 = { 2, "nand1", { NULL } };
d1.link.next = &d2.link;

ListNode *cur = &d1.link;
while (cur) {
    Device *dev = container_of(cur, Device, link);
    printf("device id=%d name=%s\n", dev->id, dev->name);
    cur = cur->next;
}
```
Actual output: `device id=1 name=nand0` then `device id=2 name=nand1`, confirming `container_of` correctly recovered each full `Device` from nothing but a pointer to its embedded `link` member.

`offsetof(type, member)` (stddef.h, C11 7.19) gives the exact byte distance from the start of `type` to `member`; since `link` is a plain, fixed-layout member (no padding surprises beyond what module 6 already covers for ordinary struct layout), subtracting that constant offset from the address of the embedded `ListNode` recovers the address of the struct that contains it, with zero runtime search and no extra pointer stored anywhere.

Why this earns its place as a Principal-level design question: the same list-linking machinery (`ListNode`, and the traversal logic) works completely generically for *any* struct that embeds a `ListNode`, with zero heap allocation dedicated to list bookkeeping (unlike every other list in this module, which allocates a separate wrapper node per element); this is exactly the technique the Linux kernel's own `struct list_head` uses throughout, and it is a natural fit for firmware contexts (module 17's territory) where a fixed set of long-lived driver/device structs need to be linked and relinked without ever calling an allocator.
FOLLOW:
- What is the main risk of this technique compared to a wrapper-node list? => Every struct type that wants to participate in this kind of list must dedicate a member to the embedded link, and a struct can only be a member of as many such lists as it has distinct embedded link members, unlike a wrapper-node list which can link any existing struct without modifying its definition.
- Does container_of perform any runtime check that ptr actually points at the named member of a real type instance? => No, none at all; it is pure pointer arithmetic based on a compile-time offset, so passing it a pointer that is not actually a member of that member at that struct type produces silently wrong, out-of-bounds pointers rather than any kind of detectable error.
PITFALL: Using container_of on a pointer that does not actually point at the named member (a typo'd member name compiles fine as long as the type matches accidentally, or a stray pointer entirely); there is no runtime check, so the result is a garbage pointer used with full confidence.
VERIFY: offsetof is defined in C11 7.19 (stddef.h); the container_of pattern itself is a widely used idiom (notably in the Linux kernel), not something C11 names or specifies directly.

int as_push(ArrStack *s, int v) {

    s->data[++s->top] = v;

@@ 15.18 | Principal | Scenario | tags=datastructurechoice,binarysearch,designtradeoff
Q: You need a lookup table for firmware configuration keys known entirely at compile time (page size, zone size, max open zones, and similar fixed fields). Would you reach for a BST, a hash table, or a sorted array with binary search, and why?
SHORT: A sorted static const array searched with binary search: for a fixed, compile-time-known key set, it needs zero allocation, zero pointers to chase (contiguous memory, matching 15.14's cache-locality argument directly), lives entirely in read-only .rodata/flash (module 13's section-placement argument), and gives the same O(log n) lookup complexity as a BST with none of a BST's or hash table's runtime construction cost or memory overhead.
DEEP:
Real, compiled, run implementation:
```c
typedef struct { const char *key; int value; } CfgEntry;

static const CfgEntry cfg[] = {
    { "erase_block_size", 262144 },
    { "max_open_zones",   14 },
    { "page_size",        4096 },
    { "zone_size",        1073741824 },
};
#define NCFG (sizeof cfg / sizeof cfg[0])

int cfg_lookup(const char *key, int *out) {
    int lo = 0, hi = (int)NCFG - 1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;
        int c = strcmp(key, cfg[mid].key);
        if (c == 0) { *out = cfg[mid].value; return 1; }
        if (c < 0) hi = mid - 1; else lo = mid + 1;
    }
    return 0;
}
```
Real run: `cfg_lookup("page_size", &v)` found it with value 4096; `cfg_lookup("unknown_key", &v)` correctly reported not found.

The design case for this over the two alternatives, stated the way an interviewer wants to hear it argued rather than just asserted:

- Versus a BST (15.10/15.11): a BST built from this fixed, known-in-advance key set at program startup pays real construction cost (n insertions, each involving pointer writes and, worse, a real risk of ending up degenerate if the keys happen to be inserted in sorted order, 15.10's own pitfall) and real per-node heap allocation and pointer-chasing overhead, for no benefit, since the key set never changes after the program starts; a `static const` sorted array has none of that: it is already fully "built" at compile time, sitting in flash.
- Versus a hash table (15.12/15.13): a hash table gives expected O(1) lookup, clearly better than binary search's O(log n) for a large key set, but at the cost of an array of bucket-chain pointers to allocate and maintain, a hash function to get right (15.13's whole point), and no ordering guarantee if anything downstream ever wants to iterate the keys sorted; for a small, fixed configuration table (here, 4 entries; realistically dozens, not millions), the asymptotic O(1) versus O(log n) gap is not the deciding factor at all, while the memory/allocation/flash-placement argument clearly is.
- The sorted-array approach is also directly checkable at compile time or by a simple startup assertion (the array must actually be sorted for binary search's precondition to hold, exactly module 14's bsearch precondition), whereas a hand-built BST's correctness depends on runtime insertion logic executing correctly every time the program starts.

The general design principle worth stating unprompted: reach for a pointer-based dynamic structure (BST, hash table, linked list) when the data set's membership actually changes at runtime; when it does not, a flat, sorted, statically-declared array is very often both simpler and objectively more efficient in exactly the ways that matter for firmware (flash placement, zero heap use, cache locality).
FOLLOW:
- Would you change this answer if the config table had thousands of entries instead of 4? => The core argument (fixed key set known at compile time) does not change, but at a much larger scale a hash table's O(1) lookup, or a perfect hash computed once offline for this exact known key set, would start to matter more than it does for a handful of entries, where binary search's few comparisons are already effectively free.
- What standard library function could replace the hand-written binary search loop here? => bsearch (module 14), with a comparator that calls strcmp on the key field, provided the array element size and layout still match bsearch's void*-based contract; writing the loop by hand here was for clarity, not because bsearch would not work.
PITFALL: Defaulting to "a hash table is always faster" without checking whether the actual key set size and its compile-time-fixed nature make that speed advantage irrelevant next to the real costs (allocation, hash-function correctness, memory layout) a hash table brings for a small, static table.
VERIFY: C11 6.9.2 paragraph 2 (a static const array without an explicit runtime-computed initializer is placed by the toolchain in read-only storage; the exact section name (.rodata) is a toolchain/ABI convention, not ISO C terminology)
