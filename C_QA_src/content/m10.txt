# Module 10: Undefined Behavior & Standard Compliance

@@ 10.01 | Basic | Concept | tags=undefined,unspecified,implementation-defined,definitions
Q: What is the difference between undefined, unspecified, and implementation-defined behavior in C?
SHORT: Undefined behavior (3.4.3) means the standard imposes no requirements at all, so anything can happen, including a crash or a value that looks fine but is not guaranteed. Unspecified behavior (3.4.4) means the standard allows two or more outcomes and does not say which, but the result is still a valid, in-range value. Implementation-defined behavior (3.4.1) is unspecified behavior where the vendor must pick one choice and document it.
DEEP:
| Category | Standard's promise | Example |
|---|---|---|
| Undefined | None at all | Signed integer overflow, dereferencing a null pointer |
| Unspecified | Some valid outcome, unstated which | Order of evaluation of function arguments |
| Implementation-defined | One documented outcome, chosen by the vendor | Result of right-shifting a negative signed value |

- **3.4.3, undefined behavior:** "behavior, upon use of a nonportable or erroneous program construct or of erroneous data, for which this International Standard imposes no requirements." The note adds that this ranges from ignoring the situation with unpredictable results, to behaving in a documented way, to terminating translation or execution.
- **3.4.4, unspecified behavior:** "use of an unspecified value, or other behavior where this International Standard provides two or more possibilities and imposes no further requirements on which is chosen." The value exists and is one of the allowed choices; the program has not left defined territory.
- **3.4.1, implementation-defined behavior:** "unspecified behavior where each implementation documents how the choice is made." The standard's own example is the propagation of the high-order bit when a signed integer is shifted right.
- **Why the distinction matters for review:** unspecified and implementation-defined code is still portable in the sense that it always does *something* consistent for a given implementation; undefined behavior can differ between two calls in the same binary, or be removed entirely by the optimizer.
FOLLOW:
- Is a compiler required to document undefined behavior? => No. Only implementation-defined (and locale-specific, 3.4.2) behavior must be documented; undefined behavior has no documentation obligation at all.
- Can undefined behavior produce output that looks completely correct? => Yes, and that is what makes it dangerous. A program with UB can pass every test on one compiler and version and fail only after a toolchain or optimization-level change.
PITFALL: Treating "the compiler didn't warn" as proof the code is well-defined. Absence of a diagnostic says nothing; a diagnostic is never required for undefined behavior.
VERIFY: Clause numbers 3.4.1, 3.4.3, 3.4.4 in the C11 draft (N1570).

@@ 10.02 | Basic | Concept | tags=warall,wextra,static-analysis,limits
Q: Why does code full of undefined behavior often compile cleanly with -Wall -Wextra?
SHORT: -Wall and -Wextra are heuristics built from pattern matching in the front end and a few optimizer passes; they catch UB that has an obvious syntactic shape (an uninitialized read the compiler can prove, a suspicious sequence point) but not UB that only exists as a runtime condition, such as an overflow that depends on input values or an out-of-bounds index computed from user data. The standard never requires any diagnostic for undefined behavior.
DEEP:
- **What -Wall/-Wextra realistically catch:** unsequenced modification patterns like `i = i++` (`-Wsequence-point`), some provably-uninitialized reads (`-Wuninitialized`), suspicious comparisons, and format-string mismatches. These are compile-time, data-independent judgments.
- **What they do not catch:** signed integer overflow whose operands are not compile-time constants, an array index read from a file or computed at runtime, a strict-aliasing violation through a cast the compiler cannot fully track, and use-after-free. These require either tracking runtime values (impossible in general, per the halting problem) or instrumentation that only exists at runtime.
- **Runtime tools fill the gap:** `-fsanitize=undefined` (UBSan) inserts checks around operations the standard leaves undefined and reports a violation the moment it actually happens during a run, rather than trying to prove it statically. See the later question in this module for a real UBSan report.
- **Practical takeaway for review:** a clean `-Wall -Wextra` build is necessary but never sufficient evidence that a function is UB-free; it only says the obvious static patterns were not present in the paths the compiler chose to analyze.
FOLLOW:
- Does -Wextra add any UB-specific checks beyond -Wall? => A few, such as `-Wsign-compare` catching mixed signed/unsigned comparisons that can silently misbehave, but neither flag is a substitute for a sanitizer or a fuzzer.
- Would -Wpedantic help here? => `-Wpedantic` mostly flags departures from strict standard conformance (extensions, non-standard syntax), not runtime undefined behavior; it is a different kind of check.
PITFALL: Reading a warning-free build log as a correctness certificate. Warnings and undefined behavior are only loosely correlated.

@@ 10.03 | Basic | Trap | tags=sequence-point,unsequenced,i-plus-plus
Q: Is `i = i++;` undefined behavior in C11, and why?
SHORT: Yes. C11 6.5p2 says that if a side effect on a scalar object is unsequenced relative to another side effect on the same object, the behavior is undefined. In `i = i++`, the assignment's write to `i` and the `++` write to `i` are both side effects on `i` with no sequencing between them, so the expression is undefined no matter what a particular compiler happens to produce.
DEEP:
```c
#include <stdio.h>
int main(void) {
    int i = 5;
    i = i++;
    printf("%d\n", i);
    return 0;
}
```
Compiled with `gcc -std=c11 -Wall -Wextra`, this produces a warning and printed `5` on this toolchain:
```
q03.c: In function 'main':
q03.c:4:7: warning: operation on 'i' may be undefined [-Wsequence-point]
    4 |     i = i++;
      |     ~~^~~~~
5
```
- **What changed with C11's sequencing model:** earlier standards described "sequence points"; C11 replaced that with the "sequenced before" partial order (6.5p3, footnotes 84 to 86), but the outcome for this expression is the same: the two writes to `i` are unsequenced, so the behavior is undefined either way. This is not a case where "C99 said X and C11 says Y"; both eras call it undefined.
- **Why `i++` alone is fine but `i = i++` is not:** `i++` by itself has one side effect on `i` and no competing value computation or side effect on the same object in the same full expression. `i = i++` adds the assignment's write to the same object, and nothing in the grammar sequences the two.
- **A related but different case:** `i = i + 1;` has no such problem, because there is exactly one write to `i` (the assignment) and the read of `i` on the right-hand side is a value computation, not a second side effect, and it is sequenced before the assignment by 6.5.16p3.
- **-Wall caught this one because the pattern is syntactic** (an object modified and used again with no separator), which is exactly the class of UB static analysis is good at, per the previous question.
FOLLOW:
- Is `a[i] = i++;` undefined for the same reason? => Yes, if `a[i]` and `i++` both touch `i` with no sequencing between the value computation used for the index and the side effect of the increment, the behavior is undefined; some concrete cases here are unspecified rather than undefined depending on exact wording, so treat any such expression as suspect and split it into statements.
- Does splitting into two statements fix it? => Yes: `int t = i; i = t + 1;` or simply `i++;` on its own line has one full expression per side effect, which removes the ambiguity entirely.
PITFALL: Assuming the printed value (`5` here) reveals the "real" rule. It is one observed result on one compiler and flag set, not a guarantee; a different compiler, version, or optimization level is free to print something else.
VERIFY: C11 6.5p2 and p3 (N1570) for the unsequenced-side-effect wording that replaced the older "sequence point" terminology.

@@ 10.04 | Intermediate | Numeric | tags=signed-overflow,ubsan,int-max
Q: What actually happens when a signed int overflows, and what does -fsanitize=undefined report?
SHORT: Per C11 6.5p5, if an expression's result is not in the range of representable values for its type, the behavior is undefined; signed overflow is the standard's own example of undefined behavior in 3.4.3. On this gcc/x86-64 toolchain, `INT_MAX + 1` silently wrapped to `INT_MIN` (-2147483648) when compiled plainly, but `gcc -fsanitize=undefined` caught it at the exact statement and printed a runtime diagnostic before continuing.
DEEP:
```c
#include <stdio.h>
#include <limits.h>
int main(void) {
    int a = INT_MAX;
    int b = a + 1;
    printf("%d\n", b);
    return 0;
}
```
Plain build and run (`gcc -std=c11 -Wall -Wextra`): no warning, prints `-2147483648`.

Same source with UBSan (`gcc -std=c11 -Wall -Wextra -fsanitize=undefined`):
```
q04.c:5:9: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
-2147483648
```
1. UBSan prints the exact file, line, and column, then the operation and operand values, then (by default) continues execution using the same wrapped result, so the program still finishes and prints -2147483648.
2. The two-wire's-complement wraparound seen here is not a guarantee; a different compiler, a different optimization level, or the same compiler on a different day is free to do something else entirely, including using the overflow as an excuse to remove surrounding code (see the Principal question on this later in the module).
3. This is why `INT_MAX + 1` is the canonical textbook example of undefined behavior: 3.4.3's own example text names "the behavior on integer overflow."
- **Why unsigned does not have this problem:** unsigned arithmetic is defined to wrap via 6.3.1.3p2 (modulo 2^n), covered in the next question, so there is nothing for UBSan to report there.
- **Build cost:** `-fsanitize=undefined` adds a runtime check around arithmetic, shifts, array indexing with a statically known bound, null and misaligned-pointer use, and more; it is cheap enough to run in CI and in debug or test builds, though not typically shipped in a release firmware image due to code size and timing impact.
FOLLOW:
- Does -fsanitize=undefined stop the program by default? => No, by default it prints the diagnostic to stderr and continues; `-fsanitize=undefined -fno-sanitize-recover=all` (or setting `UBSAN_OPTIONS=halt_on_error=1`) makes it abort on the first violation instead.
- Would `unsigned int b = a + 1;` with `a` still an `int` at INT_MAX avoid the problem? => No, the addition `a + 1` is still performed in `int` before any conversion to `unsigned int` happens, since `1` is an `int` constant and the usual arithmetic conversions do not apply until both operands' types are compared; the overflow already occurred.
PITFALL: Reporting the wrapped value as "the" behavior of signed overflow in a design document or test oracle. Only unsigned wraparound is a documented, reproducible contract; the signed case is not.
VERIFY: C11 6.5p5 (exceptional condition during expression evaluation is undefined) and 3.4.3 EXAMPLE (integer overflow named as undefined behavior).

@@ 10.05 | Intermediate | Concept | tags=unsigned-wraparound,modulo,defined
Q: Why is unsigned integer overflow well-defined while signed integer overflow is undefined?
SHORT: C11 6.3.1.3p2 defines conversion to an unsigned type as repeatedly adding or subtracting one more than the type's maximum value until the result is in range, which is exactly arithmetic modulo 2^n; every unsigned operation is specified to work this way, so "overflow" for unsigned types is really defined wraparound, not an error. Signed overflow instead hits 6.5p5's "exceptional condition... not in the range of representable values," which is explicitly undefined.
DEEP:
```c
#include <stdio.h>
int main(void) {
    unsigned int u = 0;
    u = u - 1;
    printf("%u\n", u);
    return 0;
}
```
Compiled with `gcc -std=c11 -Wall -Wextra` (no warning) and run: prints `4294967295`, which is `UINT_MAX` on a 32-bit `unsigned int`, exactly `2^32 - 1` as the modulo rule predicts.
- **The rule in one line:** for an n-bit unsigned type, every result is reduced modulo 2^n; there is no representable-range failure to trigger undefined behavior, because the whole point of 6.3.1.3p2 is to define what happens when the mathematical result does not fit.
- **Signed types have no such fallback rule.** 6.2.6.2p2 leaves the actual bit-level representation (two's complement, ones' complement, or sign-magnitude) implementation-defined, so the standard cannot also promise a specific wraparound value for overflow without picking a representation; instead it simply declines to define the outcome (6.5p5).
- **Practical consequence for firmware counters:** a free-running unsigned tick counter or CRC accumulator that wraps is relying on defined, portable behavior. The same code written with a signed counter is relying on undefined behavior even if two's complement wraparound is what every real target does in practice.
- **Do not use this as license to ignore unsigned wraparound:** it is defined, but a counter silently wrapping from `UINT_MAX` to `0` can still be a logic bug (for example a size or length computation going negative-then-huge); "defined" is not the same as "correct."
FOLLOW:
- Does casting a signed value to unsigned before the operation make an otherwise-overflowing computation defined? => Yes, if the addition or subtraction itself happens on the unsigned operands, since then 6.3.1.3p2's wraparound rule governs the whole computation; converting only the final result back to signed afterward does not retroactively fix a signed overflow that already happened earlier.
- Is `size_t` subtraction that goes negative the same kind of bug? => It is the same wraparound mechanism (well-defined, huge positive result) but frequently the root cause of buffer-overrun bugs, since the huge value is then used as a length or offset.
PITFALL: Assuming "no crash and no sanitizer warning" for an unsigned computation means the logic is correct. It only means the bit pattern followed the modulo rule, not that the resulting value made sense.
VERIFY: C11 6.3.1.3p2 (conversion to unsigned type) and 6.2.6.2p2 (implementation-defined signed representation).

@@ 10.06 | Intermediate | Concept | tags=strict-aliasing,effective-type,type-punning
Q: What is the strict aliasing rule, and why does naive type punning through a pointer cast violate it?
SHORT: C11 6.5p6-7 says every object has an "effective type" (normally its declared type), and its stored value may only be accessed through an lvalue whose type is compatible with that effective type, a signed/unsigned variant of it, a containing aggregate, or a character type. Casting a `float *` to `int *` and dereferencing it accesses a `float` object through an `int` lvalue, which fits none of those cases, so it is undefined behavior even though most compilers accept the cast silently.
DEEP:
```c
#include <stdio.h>
int main(void) {
    float f = 1.5f;
    int *ip = (int *)&f;
    printf("%d\n", *ip);
    return 0;
}
```
Compiled with `gcc -std=c11 -Wall -Wextra`: no diagnostic, prints `1069547520`, which is the raw IEEE-754 bit pattern of `1.5f` reinterpreted as a 32-bit signed integer. This value looked "right" here only because nothing reordered the accesses; it is not evidence the code is standard-conforming.
- **Why the character-type exception exists:** 6.5p7 explicitly allows access through a character type, which is why `unsigned char *` is the one universally safe way to inspect an object's bytes (used for the endianness check in Module 11) without violating effective type.
- **The standard-conforming ways to reinterpret bits:** `memcpy` into an object of the target type (copies bytes, no aliasing violation, and every real compiler optimizes a small fixed-size `memcpy` into the same load/store the pointer cast would have produced), or a `union` of the two types (C11 explicitly permits reading a different union member than was last written as an implementation-defined "extension" many implementations document; only `memcpy` is unconditionally portable).
- **Why this bites at -O2 and not -O0:** the whole reason a compiler is allowed to assume no aliasing between differently-typed pointers is so it can keep values in registers and skip reloading from memory across such accesses; at low optimization it usually reloads from memory every time anyway, so the visible bug often appears only after turning optimization on, which is exactly backwards from where most people go looking for it.
FOLLOW:
- Is casting `int *` to `unsigned char *` and reading bytes also a violation? => No, that direction is explicitly permitted by 6.5p7's character-type exception; it is writing through an incompatible non-character type, or reading a non-character-typed object through such a pointer, that violates the rule.
- Does `-fno-strict-aliasing` make this code correct? => It makes gcc stop optimizing on the aliasing assumption, so the specific miscompile risk goes away on that compiler, but the code is still not standard-conforming C, and it will not be portably safe on a different compiler or a future gcc release.
PITFALL: "It worked when I tested it" for a type-punning cast. The failure mode is a silent miscompile under specific optimizations, not a crash, so ad hoc testing is close to useless for catching it.
VERIFY: C11 6.5p6 and p7 (effective type and the list of allowable accessing lvalue types), footnote 88.

@@ 10.07 | Intermediate | Concept | tags=pointer-arithmetic,out-of-bounds,one-past-the-end
Q: How far can a pointer legally move past the end of an array, and where does it become undefined?
SHORT: C11 6.5.6p8 allows a pointer to move to any element of the array it points into, or exactly one element past the last one; that "one past the end" pointer may be computed and compared, but never dereferenced. Moving the pointer any further, or dereferencing the one-past-the-end pointer, is undefined behavior.
DEEP:
```c
#include <stdio.h>
int main(void) {
    int arr[4] = {1, 2, 3, 4};
    int *p = arr + 4;
    printf("%td\n", p - arr);
    return 0;
}
```
Compiled with `gcc -std=c11 -Wall -Wextra`: no warning, prints `4`. `arr + 4` is exactly the one-past-the-end pointer for a 4-element array, which 6.5.6p8 explicitly permits computing; only `*p` here would be undefined.
- **The exact rule:** "If both the pointer operand and the result point to elements of the same array object, or one past the last element of the array object, the evaluation shall not produce an overflow; otherwise, the behavior is undefined." (6.5.6p8) `arr + 4` satisfies "one past the last element"; `arr + 5` or `arr - 1` do not, and are undefined the moment they are computed, not just when dereferenced.
- **Pointer subtraction has the matching rule (6.5.6p9):** both pointers must point into the same array object (or one past its end); subtracting pointers into two unrelated arrays is undefined even if the subtraction "looks like" it produces a plausible number.
- **Why this matters for loop idioms:** `for (int *p = arr; p != arr + n; p++)` is standard-conforming precisely because the loop never dereferences `arr + n`, only compares against it; the moment code writes `for (int *p = arr; p <= arr + n; p++) use(*p);` it dereferences one past the end on the last iteration, which is undefined.
- **A common firmware variant:** iterating a ring buffer or descriptor table by pointer and "just going one more" to peek at the next unused slot is only safe if that slot exists as part of the same array object; going past the allocation entirely (for example reading one struct past a `malloc`'d array) is the same class of bug as this one, and neither -Wall nor -Wextra reliably detects it.
FOLLOW:
- Is `arr + 4` usable as a sentinel to compare against in a loop condition? => Yes, that is exactly the standard idiom the rule was written to support; computing and comparing the one-past-the-end pointer is well-defined, only dereferencing it is not.
- Would `int *p = arr - 1;` ever be legal? => No, that is one before the first element, which is outside the "elements of the array object, or one past the last element" range in 6.5.6p8, so even computing it is undefined, unlike the one-past-the-end case.
PITFALL: Assuming "the pointer arithmetic compiled and the address looked reasonable" proves it is in range. 6.5.6p8's overflow clause applies to the abstract array object, not to whatever the underlying memory layout happens to allow.
VERIFY: C11 6.5.6p8 (additive operators, pointer bounds) and p9 (pointer subtraction).

@@ 10.08 | Intermediate | Trap | tags=null-check,dead-code-elimination,dereference-before-check
Q: Why is checking a pointer for NULL after already dereferencing it dangerous, beyond the obvious crash risk?
SHORT: Dereferencing a null pointer is undefined at the point of the dereference, per 6.5.3.2's requirement that unary `*` operate on a pointer to an object. Because the standard permits anything once that line is crossed, an optimizer may reason "this pointer was already dereferenced, so it cannot be NULL by the later check" and delete the check entirely, even though the programmer meant it as a safety guard.
DEEP:
```c
#include <stddef.h>
#include <stdio.h>
void f(int *p) {
    int x = *p;
    if (p == NULL) {
        printf("null\n");
    }
    printf("%d\n", x);
}
int main(void) {
    int y = 5;
    f(&y);
    return 0;
}
```
Compiled with `gcc -std=c11 -Wall -Wextra` and called only with a valid pointer here: no warning, prints `5`. The point of this question is the *shape* of the bug, not this particular safe call; if `f` were ever invoked as `f(NULL)`, the dereference `*p` is already undefined behavior before the `if` is reached, so the standard places no obligation on what the `if` branch does afterward, including "nothing, because the optimizer proved it dead."
- **This is a real, repeatedly-reported compiler behavior**, not a hypothetical: both gcc and clang have, at various `-O2`/`-O3` settings, removed a null check that appeared textually after a dereference of the same pointer, because from the compiler's point of view a program that reaches the check has, by definition, not hit undefined behavior on the way there, so the pointer "must" be non-null.
- **The fix is ordering, not cleverness:** check first, dereference second.

```c
void f_fixed(int *p) {
    if (p == NULL) { printf("null\n"); return; }
    printf("%d\n", *p);
}
```

- **Static analyzers increasingly flag this pattern** (a check for a condition that a prior use already ruled out) precisely because it is a strong signal of exactly this class of bug.
FOLLOW:
- Does adding -fno-delete-null-pointer-checks change this? => On gcc it disables that specific optimization and restores the check, which is why some kernels build with that flag, but it does not make the original code standard-conforming; it only changes one compiler's willingness to exploit the UB.
- Is this the same issue as the earlier "signed overflow lets the optimizer assume no overflow" story? => Yes, structurally identical: once code takes a path that is only valid in a non-undefined-behavior world, the compiler is free to assume that world, and anything checking for the undefined-behavior case afterward can be optimized away.
PITFALL: Writing defensive null checks after the pointer has already been used, believing the check still protects the caller. Once the dereference happens, the check is not just too late, it can be deleted by the compiler.

@@ 10.09 | Intermediate | Cross-layer | tags=ubsan,wall,static-vs-dynamic,gaps
Q: Concretely, what does gcc's -Wall catch that -fsanitize=undefined does not, and vice versa?
SHORT: -Wall is a static, compile-time pattern matcher; -fsanitize=undefined (UBSan) is a dynamic, runtime instrumentation layer. On this toolchain, -Wall's -Wsequence-point flagged `i = i++;` at compile time while UBSan let it run silently and print `5`. In the other direction, UBSan caught `INT_MAX + 1` overflowing and an out-of-bounds `arr[5]` at the exact runtime moment, neither of which -Wall flagged at all, since both depend on values that are not fixed at compile time.
DEEP:
| Case | -Wall -Wextra (static) | -fsanitize=undefined (runtime) |
|---|---|---|
| `i = i++;` | Warns: `-Wsequence-point` | Ran silently, printed `5`, no diagnostic |
| `int b = INT_MAX + 1;` | No warning | `runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'` |
| `int x; if (x > 0) ...` (uninitialized) | Warns: `-Wuninitialized` | Ran silently, printed `pos`, no diagnostic |
| `arr[idx]` with `arr[5]` and `idx == 5` | No warning (bound not violated syntactically) | `runtime error: index 5 out of bounds for type 'int [5]'` |

All four rows were actually compiled and run on this toolchain (`gcc -std=c11 -Wall -Wextra`, and separately with `-fsanitize=undefined` added) to produce the exact text above; see the other questions in this module for the full listings.
- **Why the split exists:** a compile-time warning can only reason about the program's text and types, not about the values a variable will hold at runtime; a runtime sanitizer sees the actual values but only for the specific inputs a given run happens to exercise. Neither one is a superset of the other.
- **Practical review implication:** treat `-Wall -Wextra` as catching a narrow band of syntactically obvious UB, and `-fsanitize=undefined` as catching whatever UB the current test inputs happen to trigger; a code path UBSan never executes gets no coverage from it either. Fuzzing with sanitizers enabled closes more of that gap than either tool alone.
- **Neither tool catches everything:** the strict-aliasing violation in the earlier type-punning question and the incompatible-function-pointer-type call in Module 12 are both undefined behavior that this gcc's UBSan build does not flag by default (aliasing violations are notoriously hard to instrument generally, and gcc's `-fsanitize=undefined` has no `function`-type check the way clang's does).
FOLLOW:
- Is there a single flag that catches "all" undefined behavior? => No; UBSan's own documentation lists which specific checks it implements (overflow, shifts, bounds with a known size, null and misaligned pointer use, and more), and it is explicit that this is not an exhaustive list of everything the standard leaves undefined.
- Should firmware CI run with -fsanitize=undefined even though the target hardware cannot? => Yes for host-side unit tests and simulators; it finds real bugs before they reach hardware, even though the shipped, cross-compiled firmware binary will not carry the instrumentation.
PITFALL: Concluding "no warnings and no sanitizer errors" means the code has no undefined behavior. It only means the specific checks that were enabled, on the specific inputs that were run, found nothing.

@@ 10.10 | Advanced | Debug | tags=ubsan,array-bounds,report-reading
Q: Read this UBSan report and identify the bug: "q10.c:5:23: runtime error: index 5 out of bounds for type 'int [5]'".
SHORT: This is UndefinedBehaviorSanitizer's array-bounds check, and it names the exact file, line, and column of the offending subscript expression, plus the static array type it violated. It fires here because the compiler can see the full declared type `int [5]` at the access site; it means an index of 5 was used against an array whose valid indices are 0 through 4.
DEEP:
```c
#include <stdio.h>
int main(void) {
    int arr[5] = {0, 1, 2, 3, 4};
    int idx = 5;
    printf("%d\n", arr[idx]);
    return 0;
}
```
Full run with `gcc -std=c11 -Wall -Wextra -fsanitize=undefined`:
```
q10.c:5:23: runtime error: index 5 out of bounds for type 'int [5]'
q10.c:5:5: runtime error: load of address 0x7fffe5011054 with insufficient space for an object of type 'int'
0x7fffe5011054: note: pointer points here
  04 00 00 00 ff 7f 00 00  00 c8 20 d3 d3 75 67 96 ...
              ^
32767
```
1. **First line, the bounds check:** column 23 is the `arr[idx]` expression; the type `int [5]` tells you the declared array size directly from the diagnostic, no need to go find the declaration first.
2. **Second and third lines, a separate address-sanitizer-style check** UBSan's `-fsanitize=undefined` also performs for out-of-bounds loads: it shows the actual bytes at and after the computed address, with a caret marking where the read started, which is directly the byte pattern of whatever memory happened to follow `arr` on the stack.
3. **The plain, non-sanitized run still "succeeds"** and prints `32767` (some indeterminate stack value), which is exactly why this class of bug is dangerous in production: it neither crashes nor looks obviously wrong.
4. **The fix is a bounds check before the access**, `if (idx >= 0 && idx < 5) use(arr[idx]);`, or restructuring so `idx` cannot reach an invalid value in the first place (a `switch` or a lookup table sized to match every valid input).
- **Why plain -Wall does not catch this:** `idx` is a variable, not a compile-time constant, so there is nothing for a purely static pass to disprove; UBSan's bounds check is inserted at compile time but evaluated against the actual runtime value of `idx`.
FOLLOW:
- Would this be caught if `arr` were accessed through a pointer parameter instead of the local array directly? => Usually not by this specific check, since UBSan's array-bounds instrumentation relies on the compiler still knowing the static array type at the access site; once the array has decayed to a plain pointer passed into another function, that type information is typically gone and AddressSanitizer (a different tool, `-fsanitize=address`) is what catches the out-of-bounds memory access instead.
- Is `idx` itself required to be undefined before the subscript runs? => No, computing `idx = 5` is completely fine; the undefined behavior is specifically in using it as a subscript into a 5-element array, per the pointer-arithmetic rule in 6.5.6p8 (array subscripting `arr[idx]` is defined as `*(arr + idx)`).
PITFALL: Reading only the first line of a multi-part sanitizer report and missing that a single bad access can trigger more than one check.
VERIFY: The specific set of checks bundled under gcc's -fsanitize=undefined (`array-bounds` is one of several sub-checks; the exact sub-check list is a gcc-documentation fact, not a language-standard one).

@@ 10.11 | Advanced | Concept | tags=indeterminate-value,trap-representation,uninitialized
Q: What does the standard actually say about reading an uninitialized automatic variable, and is it always undefined behavior?
SHORT: C11 6.3.2.1p2 says that if an automatic-storage object that could have been declared `register` (address never taken) is read before being initialized or assigned, the behavior is undefined. Separately, 6.2.6.1p5 says that if the object's stored bits form a trap representation for its type and are read through a non-character lvalue, that is also undefined. So "indeterminate value" is not a safe placeholder; reading it can be undefined outright, not merely unpredictable.
DEEP:
```c
#include <stdio.h>
int main(void) {
    int x;
    if (x > 0) printf("pos\n"); else printf("nonpos\n");
    return 0;
}
```
Compiled with `gcc -std=c11 -Wall -Wextra`:
```
q11.c: In function 'main':
q11.c:4:8: warning: 'x' is used uninitialized [-Wuninitialized]
    4 |     int x;
      |         ^
```
Running it printed `pos`. Under `-fsanitize=undefined` it also ran silently and printed `pos` again, with no runtime diagnostic, because gcc's UBSan build does not include an uninitialized-value check by default (that class of detection belongs to MemorySanitizer, a separate, clang-only tool not exercised here).
- **Two distinct standard hooks, easy to conflate:** 6.3.2.1p2 is about *never having given the object a value at all*; 6.2.6.1p5's trap representation is about the bits present (from whatever leftover memory happened to be there) not forming a valid value of the type at all, for example a `_Bool` byte holding something other than 0 or 1 on an implementation that traps on it. Ordinary `int` on common platforms has no trap representations, so the first clause, plain "unspecified-turned-undefined by use," is the one actually in play for `int x;` here; padding-heavy or `_Bool`-like types are where the second clause bites.
- **"Indeterminate value" is the standard's term** (an unspecified value or a trap representation), and 6.3.2.1p2 is explicit that using it is undefined, not merely unspecified, precisely because it might be a trap representation.
- **Static analysis (here, -Wuninitialized) is decent at exactly this pattern** because "declared, then read on some path with no intervening write" is a data-flow property the compiler already computes for other reasons; it is one of the more reliable UB warnings available.
FOLLOW:
- Does zero-initializing static or global variables avoid this? => Yes, objects with static storage duration are zero-initialized by default (6.7.9p10) if not explicitly initialized, so this specific issue is purely about automatic (stack) storage.
- Would `int x = 0;` at the top instead of a later conditional assignment always be safer style? => Generally yes for exactly this reason; default-initializing removes an entire category of undefined behavior for negligible cost, at the price of occasionally masking a "forgot to set this" logic bug that a warning would otherwise have caught.
PITFALL: Assuming an uninitialized read is merely "some garbage value" that is annoying but safe to reason about. The standard allows it to be a trap representation, which can be undefined the instant it is read, not just imprecise.
VERIFY: C11 6.3.2.1p2 (indeterminate value on automatic storage) and 6.2.6.1p5 (trap representations).

@@ 10.12 | Advanced | Scenario | tags=works-on-my-machine,portability,review
Q: A teammate says "this pointer-arithmetic trick works fine on our target, so it is not really a bug." How do you separate a real implementation-defined guarantee from an accidental one before signing off?
SHORT: Check whether the behavior is named in Annex J.3 (implementation-defined behavior) or documented by the vendor's own manual; if so, and the code only ever targets that documented implementation, it is a reviewable, sustainable dependency. If the behavior is undefined per the standard (Annex J.2) and merely happens to be stable on the current compiler and flags, it is not a guarantee at all, and "works fine" only describes today's toolchain, not tomorrow's.
DEEP:
1. **Ask which category it falls into first.** Implementation-defined behavior (3.4.1) requires the vendor to document one fixed choice; that is a real, checkable contract you can cite (a manual page, a `-std=` note, an ABI document). Undefined behavior (3.4.3) has no such obligation from anyone, ever.
2. **Get the exact construct in front of you**, not a paraphrase. "Signed right shift" (6.5.7p5) is implementation-defined on every conforming implementation; "signed integer overflow" (6.5p5) is undefined on all of them. These are easy to blur together in a hallway conversation but the standard treats them completely differently.
3. **Check whether the confirmed guarantee is actually the one being relied on.** A right-shift trick might rely on the implementation-defined "arithmetic shift" choice and nothing else; if nearby code also silently assumes no overflow, that second assumption is still undefined even if the shift itself is fine.
4. **Compile the exact function at more than one optimization level** and, where feasible, more than one compiler, specifically looking for a change in output; agreement across `-O0`, `-O2`, and a second compiler is evidence (never proof) that nothing UB-shaped is being exploited, while disagreement is close to proof that something is.
5. **Write down the dependency explicitly** in a comment or design note ("relies on arithmetic right shift, implementation-defined per 6.5.7p5, true for gcc/clang on this target") so the next reviewer, or the next target port, has something concrete to re-check instead of re-litigating "works fine" from scratch.
- **The core distinction to hold onto:** implementation-defined behavior is a promise from one vendor for one implementation; it is portable across your team's builds on that toolchain but not across toolchains. Undefined behavior is not a promise from anyone, on any toolchain, ever, even if every build you have tried agrees.
FOLLOW:
- Does "our target never changes compilers" make relying on undefined behavior acceptable? => No; it also never changes optimization flags, library versions, or gets rebuilt after a compiler security update, until one day it does, and undefined behavior gives the new build no obligation to match the old one's accidental output.
- Is Annex J itself normative? => No, Annex J is explicitly informative (a cross-reference list); the normative requirement is always the individual clause it points back to, so cite the clause, not the annex entry, when it matters.
PITFALL: Accepting "it works on our target" as equivalent to "it is implementation-defined." Only a documented vendor guarantee earns that word; an accidental stable result on undefined behavior earns nothing.

@@ 10.13 | Advanced | Concept | tags=implementation-defined,signed-shift,examples
Q: Besides the standard's own example, what are the other classic implementation-defined behaviors worth knowing for a C interview?
SHORT: The standard's textbook example (3.4.1) is right-shifting a negative signed value; 6.5.7p5 confirms it directly, saying that for `E1 >> E2` with a negative `E1`, "the resulting value is implementation-defined." Other common ones: the signed-integer representation choice, two's complement, ones' complement, or sign-magnitude (6.2.6.2p2), converting an out-of-range value to a signed type (6.3.1.3p3), and integer sizes beyond the standard's stated minimums (5.2.4.2.1).
DEEP:
```c
#include <stdio.h>
int main(void) {
    int s = -16;
    unsigned int u = 0xFFFFFFF0u;
    printf("signed >>2 = %d\n", s >> 2);
    printf("unsigned >>2 = %u\n", u >> 2);
    return 0;
}
```
Compiled with `gcc -std=c11 -Wall -Wextra` and run: `signed >>2 = -4`, `unsigned >>2 = 1073741820`. The unsigned line is fully defined by 6.5.7p5's other branch (logical shift, quotient of `E1 / 2^E2`); the signed line's `-4` is this compiler's implementation-defined choice (an arithmetic shift that fills with the sign bit), not a portable guarantee.
| Behavior | Clause | This gcc/x86-64 |
|---|---|---|
| Right shift of a negative signed value | 6.5.7p5 | Arithmetic shift (sign-extends) |
| Signed integer representation | 6.2.6.2p2 | Two's complement |
| Out-of-range conversion to signed type | 6.3.1.3p3 | Result is the low-order bits (wraps) |
| Size of `int` | 5.2.4.2.1 (minimums only) | 32 bits |

- **Why "implementation-defined" is still useful information:** unlike undefined behavior, each of these has one fixed, documented answer for a given compiler and target, so code that depends on "arithmetic right shift" is non-portable but not unsafe on a toolchain where that is the documented choice; the risk is entirely in porting to a different one, not in the current build misbehaving.
- **C17/C23:** the core wording for these clauses is essentially unchanged from C11; C23 does add a normative requirement that signed integers be two's complement (removing the other two historical choices as conforming options going forward), which turns 6.2.6.2p2's implementation-defined list into a fixed rule for any C23-conforming implementation.
FOLLOW:
- Is `-8 >> 1` guaranteed to equal `-4` on every C11 implementation? => No; it is guaranteed to be one implementation-defined value chosen and documented by that vendor, and arithmetic shift (giving `-4`) merely happens to be what essentially every mainstream implementation documents, gcc and clang included.
- Does implementation-defined behavior ever get caught by -fsanitize=undefined? => No; by definition it is not undefined behavior, so UBSan has nothing to report there, which is exactly why the earlier question's table showed a clean UBSan run for the signed-shift line.
PITFALL: Calling every "surprising but consistent" result implementation-defined without checking the actual clause. Some surprising-but-consistent results (like the earlier `x + 1 > x` fold) are undefined behavior that merely happened to be stable on one build, not a documented guarantee.
VERIFY: C11 6.5.7p5 (shift semantics), 6.2.6.2p2 (signed representation choices), 6.3.1.3p3 (out-of-range signed conversion).

@@ 10.14 | Advanced | Trap | tags=pointer-comparison,relational,different-objects
Q: Is comparing two pointers into unrelated arrays with `<` well-defined, if the comparison compiles and runs without crashing?
SHORT: No. C11 6.5.8p5 defines pointer relational comparison only for pointers into the same array object (or one past its end) or the same aggregate; it closes with "In all other cases, the behavior is undefined." Equality (`==`, 6.5.9) is defined for any two pointers, but `<`, `>`, `<=`, and `>=` between pointers to two separately declared objects are undefined behavior even though the comparison will produce some `0` or `1` on essentially every real machine.
DEEP:
- **What is actually guaranteed by 6.5.8p5:** pointers into the same array compare according to subscript order; pointers to members of the same struct compare in declaration order; all pointers to members of the same union compare equal; a pointer one past the end of an array compares greater than a pointer to its last element. Nothing else is covered.
- **What is not guaranteed:** given `int a[4], b[4];`, the expression `&a[0] < &b[0]` has no defined result. On most real stack or static layouts it will return something consistent for a given build, but nothing in the standard obligates that, and address space layout randomization, reordering by the linker, or a different optimization level can all change which object ends up at the lower address.
- **Why `==` is different and safe:** 6.5.9 defines pointer equality unconditionally (they compare equal exactly when they point to the same object, or are both null, or one is one-past-the-end matching the other under the rule in 6.5.6p9); there is no "unrelated objects" exception the way there is for the ordering operators.
- **Where this actually bites in real code:** a bounds check like `if (ptr >= buffer_a && ptr < buffer_a + len)` is fine (same array), but code that tries to establish a total order between two independently allocated buffers, or between a stack variable's address and a heap pointer, to decide "which one is higher in memory" is relying on undefined behavior, not a portable layout fact.
- **The standard-conforming alternative** when a total order across unrelated objects is actually needed (rare, and usually a sign the design should not need it) is to convert both pointers to `uintptr_t` (7.20.1.4) first; the pointer-to-integer conversion itself is implementation-defined but at least well-defined enough to compare as integers, unlike the raw pointer comparison.
FOLLOW:
- Is subtracting (not comparing) two pointers into different arrays any better? => No, it is the matching undefined case in 6.5.6p9, for the same reason: the standard only defines pointer subtraction within one array object.
- Does this affect qsort-style comparators, which receive pointers into elements of the same array being sorted? => No, that is exactly the safe case (same array object), which is why qsort comparators comparing `*(const int *)a` against `*(const int *)b` (comparing the pointed-to values, not the addresses) or even the addresses themselves within one array are both fine.
PITFALL: Trusting that "it returned 0 or 1 consistently across many test runs" proves the comparison is defined. Consistency under one build's memory layout is not the same as a standard guarantee.
VERIFY: C11 6.5.8p5 (relational operators, pointer comparison rules) and 6.5.9 (equality operators).

@@ 10.15 | Principal | Cross-layer | tags=optimizer,overflow-assumption,x-plus-one
Q: A junior engineer is confused that `if (x + 1 > x) return 1;` returned `1` even when called with `x == INT_MAX`, where `x + 1` overflows. Walk through why, and what it reveals about how optimizers use undefined behavior.
SHORT: Because signed overflow is undefined, the compiler may assume `x + 1 > x` is always true for every `int x`, since the only way it could be false is an overflow the standard says cannot legally happen. On this gcc/x86-64 toolchain, the comparison is constant-folded to `1` at both `-O0` and `-O2`, so the function always returns `1` for `INT_MAX` too, even though a naive two's-complement model says `INT_MAX + 1` wraps to `INT_MIN`, which is not greater than `INT_MAX`.
DEEP:
```c
#include <stdio.h>
#include <limits.h>
int check(int x) {
    if (x + 1 > x) return 1;
    return 0;
}
int main(void) {
    printf("%d\n", check(INT_MAX));
    return 0;
}
```
Compiled with `gcc -std=c11 -Wall -Wextra` at both `-O0` and `-O2`: both printed `1`. Looking at the `-O0` generated assembly for `check` confirms the whole comparison was folded away in the front end, before any optimization pass even ran:
```
check:
        movl    %edi, -4(%rbp)
        movl    $1, %eax
        ret
```
1. **The reasoning chain the compiler is entitled to make:** "the standard says `x + 1` for a signed `int` may not overflow (6.5p5 makes overflow undefined); therefore, for every value of `x` the standard permits, `x + 1 > x` holds; therefore the whole `if` can be replaced by the constant `1`." This is a completely legal transformation under the standard, not a bug in gcc.
2. **This is not an -O2-only effect here**, which surprises people expecting "optimizations only kick in at higher levels." Some UB-based constant folding happens as part of basic front-end simplification even at `-O0`; the aggressive whole-loop transformations most people associate with "the optimizer assumed no overflow" (for example turning `for (i = 0; i <= n; i++)` into something that behaves as if it cannot terminate abnormally) are the higher-optimization-level version of the same underlying license.
3. **The mental model to replace:** "the compiler will do the two's-complement thing I expect" is only true for unsigned types, which have a defined wraparound (6.3.1.3p2). For signed types, the correct mental model is "the compiler is allowed to assume this line of code, as written, never overflows," and will use that assumption anywhere it helps, including deleting the very check meant to catch the overflow.
4. **The fix**, if overflow must be detected rather than assumed away, is to check before the addition using the type's limits (`if (x == INT_MAX) return 0; return 1;` here), or to perform the arithmetic in a wider or unsigned type and then range-check the result, never to test for overflow after the fact on the signed operation itself.
- **Interview framing:** this example (or the closely related infinite-loop-from-overflow-assumption story) is the standard way interviewers probe whether a candidate understands that "undefined behavior" is not a synonym for "probably fine in practice," but an active license the optimizer is written to exploit.
FOLLOW:
- Would `unsigned int check_u(unsigned int x) { return (x + 1 > x); }` behave the same way at `x == UINT_MAX`? => No, and that is the whole point of the contrast: unsigned wraparound is defined (6.3.1.3p2), so `UINT_MAX + 1` really is `0`, `0 > UINT_MAX` is false, and the function correctly returns `0`; the compiler cannot fold this one to a constant because the false case is a real, reachable outcome.
- Is this specific to gcc, or would clang do the same fold? => The standard permits any conforming compiler to perform this fold, since it follows directly from signed overflow being undefined; which specific compilers actually implement it, and at which point in their pipeline, is a toolchain fact, not a language one, so always verify on the actual compiler in use rather than assuming.
PITFALL: Debugging this by staring at the "wrong" runtime value and looking for a hardware or memory-corruption explanation. The value is not wrong by any hardware fault; the whole comparison was removed at compile time.
VERIFY: C11 6.5p5 (undefined on overflow) and 6.3.1.3p2 (defined unsigned wraparound), to confirm the asymmetry that makes this fold legal only for the signed version.

Q: You are reviewing a firmware driver's C file for undefined behavior before a safety-relevant release. What is your concrete method, beyond "read it carefully"?
SHORT: Run a layered pipeline rather than relying on inspection alone: compiler warnings at their strictest, a UB sanitizer build exercised against the real test suite and a fuzzer where inputs are attacker- or environment-controlled, then a targeted manual pass over the specific constructs sanitizers cannot see (strict aliasing, incompatible function-pointer calls, and pointer comparisons across unrelated objects), each mapped to a specific standard clause so the finding is falsifiable, not a feeling.
DEEP:
1. **Static pass:** build with `-std=c11 -Wall -Wextra -Wpedantic` (and a stricter project-specific set, such as `-Wconversion`, `-Wcast-align`, `-Wshadow`) and clear every warning; treat this as necessary, not sufficient, per the earlier question in this module.
2. **Dynamic pass:** build a host-side test binary with `-fsanitize=undefined,address` and run the full existing test suite through it, then run a fuzzer (or at minimum a targeted set of boundary-value inputs: `0`, negative, `INT_MAX`/`INT_MIN`-adjacent, maximum buffer sizes) against any function that parses external or hardware-derived data, since sanitizers only report what actually executes.
3. **Manual audit for sanitizer blind spots**, specifically:
   - Any pointer cast that reinterprets an object's type (strict aliasing, 6.5p6-7): confirm every one goes through `memcpy` or a union, not a raw pointer cast.
   - Any function pointer called after being cast to or from a different function type (6.3.2.3p8): confirm the call site's assumed signature matches the pointed-to function's real signature.
   - Any pointer comparison or subtraction between two objects (6.5.8p5, 6.5.6p9): confirm both operands are always into the same array or aggregate.
   - Any signed arithmetic on values derived from hardware registers or untrusted input, where overflow is reachable: confirm range checks happen before, not after, the arithmetic.
4. **Cross-reference every unsigned computation that is expected to wrap** (tick counters, ring-buffer indices) against 6.3.1.3p2 explicitly, to confirm the code is relying on documented wraparound rather than an accidental two's-complement assumption smuggled in through a signed type.
5. **Record findings against clause numbers**, not vague descriptions, so a re-reviewer (or a future toolchain upgrade that changes what gets exploited) can re-check the same specific claim quickly.
- **Why this order:** static analysis is cheapest and catches the syntactically obvious cases first; dynamic analysis catches value-dependent bugs the static pass structurally cannot; the manual pass exists specifically for the handful of UB categories current sanitizers do not instrument well (aliasing and incompatible function-pointer calls chief among them, per the earlier module questions).
FOLLOW:
- Does passing every step of this pipeline prove the file has no undefined behavior? => No; it raises confidence substantially but sanitizers only see executed paths and gcc's UBSan build has known gaps (no aliasing or function-type check), so the manual pass is load-bearing, not optional, for the categories it targets.
- Should this pipeline run on every commit or only before release? => The static and dynamic passes belong in ordinary CI on every commit, since they are cheap and automatic; the manual audit is realistically a release-gate activity, focused on the diff since the last audit rather than the whole file every time.
PITFALL: Treating a clean sanitizer run on the existing test suite as a release gate by itself. It only reflects the inputs the suite happens to exercise, not the full input space a shipped driver will see.

@@ 10.18 | Principal | Concept | tags=defensive-coding,misra,portable-idioms,c17-c23
Q: Given that undefined behavior cannot be caught by any single tool, what is a realistic, layered defensive strategy for a firmware team that must ship reliable C?
SHORT: No single practice closes the gap; combine strict compiler warnings, a UB/address sanitizer build in the host test matrix, a coding standard that forbids the highest-risk idioms (raw type-punning casts, overflow-prone signed arithmetic on untrusted ranges), and a few standard-conforming replacements (memcpy for reinterpretation, unsigned types for anything expected to wrap, range checks before arithmetic) applied consistently enough that reviewers can spot violations quickly.

  - Reinterpreting bytes: `memcpy` into a same-sized object of the target type, never a pointer cast.
  - A value expected to wrap (counters, ring-buffer indices, checksums): declare it unsigned and rely on 6.3.1.3p2's defined modulo behavior.
