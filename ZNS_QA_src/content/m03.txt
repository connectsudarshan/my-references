# Module 3: Zones, States & the Write Pointer

@@ 3.01 | Basic | Concept | tags=zone,sequential-write-required,zone-type,lba-space
Q: What is a zone in a Zoned Namespace, and which zone types does ZNS define?
SHORT: A zone is a fixed-size, contiguous, non-overlapping range of LBAs. The namespace is carved into equal zones, laid out back to back from LBA 0, each Zone Size LBAs long. ZNS defines one zone type, Sequential Write Required (Zone Type 2h): the host writes each zone strictly sequentially at its write pointer, may read anywhere, and gets space back only by resetting the whole zone.
DEEP:
- **Layout:** zone n starts at ZSLBA = n x Zone Size. Zone Size (ZSZE) is per namespace and lives in the ZNS Identify Namespace data, so every zone has the same address span.
- **Sequential Write Required:** a write must begin exactly at the zone's write pointer, otherwise the controller aborts it with Zone Invalid Write. There is no overwrite in place. The only host-visible "erase" is Reset Zone, which empties the entire zone.
- **Zone Append:** the exception in addressing. The host names the zone and the device chooses the LBA (module 5).
- **Only type 2h:** ZBC/ZAC SMR drives also have Conventional and Sequential Write Preferred zones. A ZNS zone descriptor carries the type in byte 0, and the Linux NVMe driver rejects any zone whose type is not 2h.
- **Zone is logical:** a zone is an address-space contract, not an erase block. How firmware maps a zone to NAND is module 8.
FOLLOW:
- Can one namespace mix conventional and zoned regions? => No. A zoned namespace (Command Set Identifier 2h) contains only zones. Conventional and zoned namespaces coexist as separate namespaces (module 2).
- Must Zone Size be a power of two? => Not that I could confirm in the spec text (see VERIFY), but the Linux NVMe driver source I checked rejects non-power-of-two zone sizes, so real hosts effectively assume it.
PITFALL: Equating a zone with a NAND erase block. Zone Size and capacity are host-facing numbers and firmware is free to stripe a zone over many blocks and dies.
VERIFY: Whether the ZNS spec requires uniform Zone Size and a namespace size that is a multiple of it, and the reserved Zone Type codes.

@@ 3.02 | Basic | Concept | tags=write-pointer,wp,sequential,invalid-write
Q: What is the write pointer, and how does it move?
SHORT: The write pointer (WP) is the LBA where the next write to the zone must start. It equals ZSLBA in an Empty zone and advances by the number of blocks written after every successful write. A write that does not start exactly at the WP fails with Zone Invalid Write. The WP is valid only in Empty, Implicitly Opened, Explicitly Opened and Closed zones; in Full, Read Only and Offline zones the field is invalid.
DEEP:
1. Empty zone: WP = ZSLBA.
2. A successful write of N blocks at the WP moves it to WP + N.
3. When the write reaches ZSLBA + ZCAP the zone becomes Full (see 3.05).
4. Reset Zone puts the WP back to ZSLBA.

While the WP is valid it satisfies ZSLBA <= WP < ZSLBA + ZCAP. Once a write reaches ZSLBA + ZCAP the zone is Full and the WP field stops being meaningful.
- **Where the host reads it:** only Report Zones returns the WP. A normal Write completion does not carry it, so hosts keep their own shadow copy. Zone Append is the exception, because its completion returns the LBA where data landed (module 5).
- **Related statuses:** Zone Invalid Write (SCT 1, SC BCh), Zone Boundary Error (B8h) and Zone Is Full (B9h). Linux names them NVME_SC_ZONE_INVALID_WRITE and so on, with the 0x1xx values. Module 7 covers the full set.
- **Queue depth caveat:** with several writes in flight to one zone, the host must submit them in WP order and the device must process them in order, or the second write hits Zone Invalid Write. This is why Zone Append exists.
FOLLOW:
- Can the WP move backward? => Only via Reset Zone in normal operation. After unexpected power loss it may come back lower than the host last saw if the data was not durable (see 3.15).
- Does a Flush or FUA change the WP? => No. The WP advances on successful write completion. Durability of that data follows the usual Flush and FUA rules.
PITFALL: Expecting the WP in the write completion. Only Zone Append returns an LBA, so a host that does not track the WP must call Report Zones.
VERIFY: The exact durability guarantee the spec gives for WP and data after unexpected power loss.

@@ 3.03 | Basic | Concept | tags=zone-size,zone-capacity,zsze,zcap,vzc
Q: What is the difference between Zone Size and Zone Capacity?
SHORT: Zone Size (ZSZE) is the address span of every zone in the namespace. Zone Capacity (ZCAP) is the number of usable LBAs in a zone, counted from ZSLBA, and is less than or equal to Zone Size. LBAs from ZSLBA + ZCAP to the end of the zone exist in the address map but cannot be written. The gap lets Zone Size stay a clean power of two while capacity matches the NAND geometry.
DEEP:
- **Where they live:** ZSZE is per LBA format in the ZNS Identify Namespace data (the LBA Format Extension entry), ZCAP is per zone in bytes 8 to 15 of each zone descriptor.
- **Why they differ:** capacity follows what the media can hold after bad blocks, parity and firmware reserves. Zone Size is chosen for fast address arithmetic on the host (shift instead of divide).
- **Variable Zone Capacity:** the Zone Operation Characteristics field has a bit (VZC) that says capacity may differ from zone to zone. If it is 0, all zones have the same capacity. The Linux NVMe driver source I checked refuses namespaces with any Zone Operation Characteristics bit set.
- **Writes past capacity:** a write that would cross ZSLBA + ZCAP is aborted (Zone Boundary Error in the QEMU model), and the zone is Full when the WP reaches ZSLBA + ZCAP.
- **Reads in the gap:** handled like reads of unwritten blocks, not as an error (zonedstorage.io).
- **Capacity accounting:** usable space is the sum of ZCAP, not NSZE (worked in 3.08).
FOLLOW:
- Why not just make capacity equal to size? => Zone Size is a power of two for host math, while capacity tracks superblock geometry, which rarely is.
- Which value decides when a zone is Full? => Capacity. Reaching ZSLBA + ZCAP fills the zone even though ZSZE more addresses exist.
PITFALL: Filling to Zone Size in a test. The last ZSZE - ZCAP LBAs are not writable, so a host or test that plans on ZSZE hits a boundary error.
VERIFY: Whether Zone Capacity can change after Reset Zone when VZC is 1, and the exact status for a write that starts inside the gap.

@@ 3.04 | Intermediate | Concept | tags=zone-descriptor,report-zones,zone-attributes,extension
Q: What is inside a zone descriptor, and how is a Report Zones buffer laid out?
SHORT: The Report Zones buffer starts with a 64-byte header whose first 8 bytes are the number of zones, then one 64-byte descriptor per zone. Byte 0 holds the Zone Type in bits 3:0, byte 1 holds the Zone State in bits 7:4, byte 2 is Zone Attributes, byte 3 is Zone Attributes Information, bytes 8-15 are ZCAP, 16-23 ZSLBA and 24-31 the WP. In an extended report each descriptor is followed by its zone descriptor extension.
DEEP:
| Byte | Field | Notes |
|---|---|---|
| 0 | Zone Type (bits 3:0) | 2h = Sequential Write Required |
| 1 | Zone State (bits 7:4) | 1h Empty, 2h Implicit Open, 3h Explicit Open, 4h Closed, Dh Read Only, Eh Full, Fh Offline |
| 2 | Zone Attributes | bit 0 ZFC, bit 1 FZR, bit 2 RZR, bit 3 ZRWAV (newer revisions), bit 7 ZDEV |
| 3 | Zone Attributes Information | finish/reset recommended limit selectors (newer revisions) |
| 8-15 | Zone Capacity | LBAs |
| 16-23 | Zone Start LBA | lowest LBA of the zone |
| 24-31 | Write Pointer | valid only in Empty, Open, Closed |
| 32-63 | Reserved | |

- **Descriptor n:** at offset 64 + 64 x n in a plain report. With extensions the stride is 64 + ZDES x 64 bytes, where ZDES (in 64-byte units) comes from the LBA Format Extension in the ZNS Identify Namespace data. ZDES = 0 means no extension. nvme-cli computes it as `zdes << 6`.
- **Extension:** host-defined bytes attached to a zone, valid only when the ZDEV attribute bit is 1. Reset Zone clears them (see 3.10).
- **Raw-byte trap:** the state is the high nibble of byte 1. A raw byte of 20h means Implicitly Opened, and the kernel decodes it as `zs >> 4`.
- **Full report size:** 64 + 64 x zones bytes, for example 16,448 bytes for 256 zones.
FOLLOW:
- Do the Report Zones filter codes equal the state codes? => No. The Zone Receive Action Specific Field uses 0 all, 1 Empty, 2 Implicit Open, 3 Explicit Open, 4 Closed, 5 Full, 6 Read Only, 7 Offline, so Full, Read Only and Offline are 5, 6, 7 in the filter but Eh, Dh, Fh in the state field. Linux nvme.h swaps 5 and 6 (see 4.08).
- How does the host pick extended or plain? => The Zone Receive Action: 0 is a normal report, 1 is an extended report (libnvme, SPDK and QEMU; Linux nvme.h defines only 0).
PITFALL: Reading the state from the low nibble of byte 1, or decoding the filter code as a state code.
VERIFY: Zone Attributes Information bit layout (added in a later ZNS revision than 1.0) and which bytes are reserved in your target revision. Filter codes 5 = Full, 6 = Read Only: see the VERIFY line in 4.08.

@@ 3.05 | Intermediate | Concept | fig=zstates | tags=zone-states,state-machine,open,active
Q: What are the seven zone states, and what can be done in each?
SHORT: Empty, Implicitly Opened, Explicitly Opened, Closed, Full, Read Only and Offline. Empty has WP = ZSLBA. The two Open states accept writes and hold an open resource. Closed keeps data and the WP but releases the open resource, while still counting as active. Full accepts no more writes. Read Only and Offline are controller-entered degraded states, and Offline is terminal.
DEEP:
| State | Code | Writes | Reads | WP field |
|---|---|---|---|---|
| Empty | 1h | yes | yes | valid, = ZSLBA |
| Implicitly Opened | 2h | yes | yes | valid |
| Explicitly Opened | 3h | yes | yes | valid |
| Closed | 4h | yes (reopens implicitly) | yes | valid |
| Read Only | Dh | Zone Is Read Only | yes | invalid |
| Full | Eh | Zone Is Full | yes | invalid |
| Offline | Fh | Zone Is Offline | Zone Is Offline | invalid |

- **Open zones:** Implicitly Opened plus Explicitly Opened, limited by MOR.
- **Active zones:** open zones plus Closed, limited by MAR. Empty and Full zones use neither (module 6).
- **Reserved codes:** 0h and 5h to Ch are not defined states (per the Linux and SPDK headers), so a validator should flag them.
- **Ordering trap:** the codes are 1 to 4 for the normal states, then Dh Read Only, Eh Full, Fh Offline.
- **Offline is terminal:** the spec has no transition out of Offline.
FOLLOW:
- Which states count toward the active limit? => Implicitly Opened, Explicitly Opened and Closed.
- Can an Empty zone become Full without any writes? => Yes, through Finish Zone, or through a controller action.
PITFALL: Treating Closed as unusable. A Closed zone keeps its WP and data, still counts as active, and a write reopens it (needing an open resource).
VERIFY: Code assignments 1h to 4h and Dh to Fh (they match SPDK and the Linux headers) and that 0h and 5h to Ch are reserved, in the ZNS Zone Descriptor figure.

@@ 3.06 | Intermediate | Concept | tags=transitions,write,open,close,finish,reset,offline
Q: Walk through the host-driven state transitions: what does each command do in each state?
SHORT: A write moves Empty or Closed to Implicitly Opened and Full when it reaches capacity. Open Zone moves Empty, Implicitly Opened or Closed to Explicitly Opened. Close Zone moves an open zone to Closed. Finish Zone moves Empty, open and Closed zones to Full. Reset Zone moves open, Closed and Full zones to Empty and sets WP = ZSLBA. Offline Zone moves Read Only to Offline. Everything else is rejected or a no-op.
DEEP:
| State | Write | Open | Close | Finish | Reset | Offline |
|---|---|---|---|---|---|---|
| Empty | Imp Open | Exp Open | err* | Full | no change | err* |
| Imp Open | stays, Full at ZCAP | Exp Open | Closed | Full | Empty | err* |
| Exp Open | stays, Full at ZCAP | no change* | Closed | Full | Empty | err* |
| Closed | Imp Open | Exp Open | no change | Full | Empty | err* |
| Full | Zone Is Full | err* | err* | no change* | Empty | err* |
| Read Only | Zone Is Read Only | err* | err* | err* | err | Offline |
| Offline | Zone Is Offline | err* | err* | err* | err | no change* |

"err" is Invalid Zone State Transition (SCT 1, SC BFh). Cells marked * are expected behavior that must be confirmed against the spec text.
- **Resources:** Empty to Imp Open needs one open and one active resource, Closed to Imp Open needs one open. Failure gives Too Many Open Zones (BEh) or Too Many Active Zones (BDh), unless the controller closes another implicitly open zone to make room (module 6).
- **Reset side effects:** WP becomes ZSLBA and the attribute bits ZDEV, FZR, RZR and ZFC are cleared.
- **Select All:** the Zone Management Send Select All flag applies an action to every zone it is valid for (module 4).
FOLLOW:
- Which transition frees an open resource but keeps the active one? => Close Zone (open to Closed).
- Does Reset Zone on a Read Only zone recover the space? => No. It fails with Invalid Zone State Transition, and only Offline Zone is allowed from Read Only.
PITFALL: Assuming every wrong-state action fails. Reset on Empty, Close on Closed and Offline on Offline succeed as no-ops, so the oracle needs an exact expected result per cell, including "state and WP unchanged" for rejected ones.
VERIFY: The starred cells, especially Finish on Full, Open on Explicitly Opened, and Close on Empty or Full, in the Zone Management Send section.

@@ 3.07 | Intermediate | Concept | tags=implicit-open,explicit-open,resources,eviction
Q: What is the difference between an implicitly and an explicitly opened zone, and why does it matter?
SHORT: A zone is implicitly opened when a write reaches an Empty or Closed zone, and explicitly opened when the host sends Open Zone. Both use an open and an active resource. The difference is who may end it: the controller may implicitly close an Implicitly Opened zone to free an open resource, but never closes an Explicitly Opened one. Only the host or a fault does that.
DEEP:
- **Why open explicitly:** Open Zone reserves the resource up front. If the limits are hit, the failure is at the Open command (Too Many Open Zones or Too Many Active Zones) instead of in the middle of a data stream.
- **Eviction:** when a write needs an open resource and all are used, the controller may move one Implicitly Opened zone to Closed. Which one is up to the device (the QEMU model closes the oldest).
- **Visibility:** the host sees an eviction only by reading the zone state again (2h became 4h). No completion reports it, so a host that tracks state itself must resync.
- **One-way:** Implicit to Explicit exists (Open Zone on an implicitly open zone). Explicit to Implicit does not. An Explicitly Opened zone leaves only through Close, Finish, Reset or a controller fault.
- **Validation test:** with the open limit at N, open N zones explicitly and write to a fresh Empty zone. Expect Too Many Open Zones, since nothing can be evicted. Repeat with N-1 explicit and the rest implicit and expect success with one zone quietly Closed.
FOLLOW:
- Can the host tell that the controller closed a zone? => Only through Report Zones state.
- Does Close Zone release the active resource? => No. Only Finish, Reset, or a transition to Read Only or Offline take the zone out of the active count.
PITFALL: Assuming the device will always make room. Explicit opens pin their resources, so a host that opens MOR zones explicitly has no headroom for another.
VERIFY: Whether the spec obliges the controller to close an implicitly open zone before returning Too Many Open Zones (may versus shall).

@@ 3.08 | Intermediate | Numeric | tags=zone-count,zslba,wp,capacity,arithmetic
Q: A 64 GiB zoned namespace uses 4 KiB LBAs, Zone Size 0x10000 and Zone Capacity 0xDC00. How many zones are there, where does zone 100 start, and where is its WP after 40 writes of 1 MiB plus three writes of 4 KiB?
SHORT: NSZE is 0x1000000 LBAs, so there are 0x1000000 / 0x10000 = 256 zones. Zone 100 starts at ZSLBA = 100 x 65,536 = 0x640000. Each 1 MiB write is 256 LBAs, so the WP is 0x640000 + 40 x 256 + 3 = 0x642803. Usable capacity is 256 x 0xDC00 LBAs, which is 55 GiB, or 85.9 percent of the address space.
DEEP:
1. NSZE: 64 GiB / 4 KiB = 16,777,216 = 0x1000000 LBAs.
2. Zone Size: 0x10000 = 65,536 LBAs x 4 KiB = 256 MiB. Zones = 16,777,216 / 65,536 = 256.
3. Zone Capacity: 0xDC00 = 56,320 LBAs = 220 MiB. Gap per zone = 65,536 - 56,320 = 9,216 LBAs = 36 MiB.
4. ZSLBA of zone 100 = 100 x 65,536 = 6,553,600 = 0x640000 (also 0x64 << 16, since Zone Size is a power of two).
5. Written: 40 x 256 + 3 = 10,243 LBAs. WP = 6,553,600 + 10,243 = 6,563,843 = 0x642803.
6. Remaining capacity in zone 100: 56,320 - 10,243 = 46,077 LBAs, so the zone becomes Full when WP = 0x64DC00.
7. Usable space: 256 x 56,320 = 14,417,920 LBAs = 55 GiB, which is 55 / 64 = 85.9 percent.
8. Lookup: LBA 0x64A000 is zone 0x64 = 100, offset 0xA000 = 40,960 < ZCAP, so it is writable range. LBA 0x65E000 is zone 101 with offset 0xE000 = 57,344 > ZCAP, so it falls in the gap.
9. Fill count: 56,320 / 32 = 1,760 writes of 128 KiB (32 LBAs) fills a zone exactly.
FOLLOW:
- How does the zone lookup change if Zone Size is not a power of two? => The host divides instead of shifting: zone = LBA / ZSZE, and offset = LBA mod ZSZE.
- What does the state look like after write number 1,760 of 128 KiB? => Full, and Report Zones shows state Eh.
PITFALL: Sizing the dataset from NSZE. A 64 GiB namespace stores 55 GiB, and a host GC or capacity plan that ignores the gap runs out of zones early.
VERIFY: That the namespace size must be an exact multiple of Zone Size in the spec (the example assumes it).

@@ 3.09 | Advanced | Concept | tags=controller-transitions,power-cycle,reset,initial-state
Q: Which transitions does the controller make on its own, and what happens to open zones across a power cycle or controller reset?
SHORT: The controller may close an Implicitly Opened zone for resource management, and may move a zone to Read Only or Offline for media reasons. With Zone Active Excursions it can finish an active zone (ZFC set). After an NVM Subsystem Reset or power cycle, open zones come back Closed if the WP is past ZSLBA or an extension is valid, otherwise Empty. Full, Read Only and Offline stay, and a zone may also come back Full. Whether a controller-only reset does the same is unconfirmed (VERIFY).
DEEP:
| Zone before reset | State after reset |
|---|---|
| Empty | Empty |
| Open or Closed, WP > ZSLBA | Closed |
| Open or Closed, WP = ZSLBA, ZDEV = 0 | Empty |
| Any of these with ZDEV = 1 | Closed |
| Full, Read Only, Offline | unchanged |
| Any zone the controller could not recover | may come back Full (the spec allows Full as a result of the reset) |

- **Explicit opens are lost:** an Explicitly Opened zone returns as Closed, so the host must open it again before relying on reserved resources.
- **Resource count after reset:** open count is 0, and the active count equals the number of Closed zones, which must fit within MAR.
- **Read Only to Offline:** happens only by host command (Offline Zone). No Zone Management action returns a Read Only zone to writable.
- **Format and creation:** on a Format or a new namespace, each zone starts Empty or Offline, so a device may ship with some Offline zones.
- **What to test:** after every reset or power cycle, read the full zone report and compare it with the table applied to your pre-reset model. The WP itself must also be checked (see 3.15).
FOLLOW:
- Why does ZDEV = 1 force Closed even when WP = ZSLBA? => Because the zone carries host data in its descriptor extension, so it is not "nothing written" and must not be silently emptied.
- Which resets apply? => As I read the spec, the initial state is set by an NVM Subsystem Reset or when all controllers report shutdown processing complete. A Controller Level Reset (CC.EN 1 to 0) is not in that list, and QEMU closes zones only on shutdown, so record what the drive does on CC.EN and on CC.SHN separately.
PITFALL: Expecting Explicitly Opened zones to survive as Explicitly Opened. A test that reserves resources and then power cycles must re-open afterwards.
VERIFY: The exact list of events that trigger the initial-state rules (NVM Subsystem Reset, shutdown complete on all controllers, and whether a Controller Level Reset counts), and the Full-after-NVM-Subsystem-Reset condition, in the ZNS state-machine section.

@@ 3.10 | Advanced | Concept | tags=zone-attributes,zfc,fzr,rzr,zdev,excursion
Q: What do the zone attribute bits ZFC, FZR, RZR and ZDEV mean, and how should a host and a validator treat them?
SHORT: ZFC (bit 0) says the controller finished the zone itself. FZR (bit 1) and RZR (bit 2) mean the controller recommends the host Finish or Reset the zone. ZDEV (bit 7) says a zone descriptor extension is valid. FZR and RZR are advisory hints tied to media health or data-retention limits, not errors, and they clear when the host acts (Reset Zone clears all four bits).
DEEP:
- **ZFC:** set when the controller moved an active zone to Full without a host command, a Zone Active Excursion. Data below the old WP is intact and the zone takes no more writes. The device must advertise this in Zone Operation Characteristics (ZAE), and the host should be told through a zone-information-changed event (module 6).
- **FZR:** the controller would like the zone filled or Finished, for example because a partly written zone has been open too long for its NAND. The Identify Namespace data holds finish recommended limits (FRL and further limits).
- **RZR:** the controller would like the zone reset, for example because stored data has aged or degraded. Reset limits (RRL and further limits) live in Identify Namespace data.
- **Zone Attributes Information (newer revisions):** selects which of the limit fields applies to this zone.
- **ZDEV:** cleared by Reset Zone, and it changes the post-reset state to Closed (3.09).
- **Linux angle:** the kernel NVMe driver source I checked refuses a namespace with any Zone Operation Characteristics bit, so excursion-capable ZNS devices are not usable there without patches. That constrains where ZFC can be tested.
FOLLOW:
- Does FZR change the zone state? => No. The zone stays in its state until the host acts, though the controller may escalate per its limits (for example by finishing it and setting ZFC).
- How do you test FZR? => Leave a zone partly written for longer than the advertised finish limit and check the bit appears. It is device-specific, so report it as informational unless the vendor defines the trigger.
PITFALL: Failing a test on FZR or RZR being set. These are advisory, and a validator should log them and check only that Reset or Finish clears them.
VERIFY: Bit positions, units of FRL and RRL and the exact clearing rules in the ZNS Zone Descriptor and Identify Namespace sections.

@@ 3.11 | Advanced | Trap | tags=read,unwritten,dlfeat,dulbe,boundary,offline
Q: What does a Read return in each zone state and above the write pointer? Does reading above the WP fail?
SHORT: No, reads above the WP do not fail. Reads work in every state except Offline, and LBAs at or above the WP (and in the gap above ZCAP) count as unwritten blocks. The device returns the value advertised in DLFEAT (zeros or ones) or, if the host enabled DULBE, may return Deallocated or Unwritten Logical Block. Offline zones and reads that cross a zone boundary without support fail.
DEEP:
| Zone state | Read result |
|---|---|
| Empty | success, all LBAs unwritten |
| Open or Closed | success, data below WP, unwritten value at and above WP |
| Full, Read Only | success |
| Offline | fails with Zone Is Offline (BBh) |

- **Read across zone boundaries:** allowed only if the Read Across Zone Boundaries bit (Optional Zoned Command Support field) is 1. If it is 0, a read that spans two zones is aborted with Zone Boundary Error (B8h). When it is set, every zone the read touches has to be readable.
- **DLFEAT:** the Read Value field in Identify Namespace is 001b for all-00h, 010b for all-FFh, 000b for not reported. Read it and do not hardcode zeros.
- **Reads that span the WP:** legal, the written part matches, the rest is the unwritten value.
- **After Reset Zone:** old data must no longer be returned. A test should read back and check for the unwritten value, which doubles as a data-leak check.
- **Boundary reads to include:** WP - 1, WP, WP + 1, ZCAP - 1, ZCAP, last LBA of the zone, and a read straddling into the next zone.
FOLLOW:
- Which status does DULBE return? => Deallocated or Unwritten Logical Block (SCT 2, SC 87h; NVME_SC_UNWRITTEN_BLOCK in Linux), only if the feature is enabled and supported.
- Why might a device return stale data above the WP? => It is a firmware bug when a Reset did not invalidate the mapping. Reads there must give the unwritten value.
PITFALL: Writing "read above WP must fail" into an oracle. That is a different drive class's rule and it flags a compliant ZNS device.
VERIFY: Whether ZNS requires or merely allows Unwritten Block errors above the WP, the OZCS bit position (bit 0), and behavior when a cross-zone read includes an Offline zone.

@@ 3.12 | Advanced | Cross-layer | tags=wp-invalid,full,linux,blkzone,units,report
Q: Report Zones on the device shows a Full zone with WP = 0x4DC00, but blkzone shows a different write pointer for the same zone. Which one is right, and what is the second difference to watch for?
SHORT: Both are right. The spec makes the WP field invalid in Full, Read Only and Offline zones, so the device may put any value there. The Linux NVMe driver ignores it for Full zones and reports WP as zone start plus zone length. Also, blkzone prints sectors of 512 bytes regardless of the LBA size, so every LBA number is scaled by the LBA size divided by 512.
DEEP:
- **Spec rule:** WP is valid in Empty, Implicit Open, Explicit Open and Closed, and invalid in Full, Read Only and Offline.
- **Kernel code path:** in `nvme_zone_parse_entry` the driver takes the state from `zs >> 4`, and for Full it sets `wp = start + len` where len is Zone Size, not capacity. For other states it passes the raw value through.
- **Units:** the block layer uses 512-byte sector units for start, len, wp and capacity. With 4 KiB LBAs, LBA 0x4DC00 would be sector 0x26E000 (multiply by 8), but for this Full zone (start LBA 0x40000, ZSZE 0x10000) the driver reports wp = 0x280000 sectors, the zone end.
- **Validator rule:** assert the state, not the WP, for Full, Read Only and Offline zones. Keep a logical model value (ZSLBA + ZCAP for a Full zone) and skip raw comparison.
- **Cross-checks:** convert units before comparing `nvme zns report-zones` with `blkzone report`, and treat the Full-zone WP override as expected.
- **What Full still means:** the zone has no writable space left. LBAs between the last written LBA and ZCAP (for a Finished zone) read as unwritten.
FOLLOW:
- Is the WP of an Empty zone always ZSLBA? => Yes, valid and equal to ZSLBA, so a mismatch there is a device bug.
- What does the block layer report for Read Only and Offline WP? => The source I checked passes the raw device value, so it is undefined by the spec and must be ignored.
PITFALL: Writing "Full means WP = ZSLBA + ZCAP" as a hard invariant. A zone is Full when its state says so, and a Finished or controller-finished zone can be Full with a partly written span.
VERIFY: Kernel behavior for Read Only and Offline WP on the version you test, and whether blkzone output units differ across util-linux versions.

@@ 3.13 | Advanced | Debug | tags=report-zones,dump,invariants,triage,violation
Q: You get the report-zones dump below (4 KiB LBAs, ZSZE 0x10000, ZCAP 0xDC00, MOR 4, MAR 8, ZOC = 0). Which zones violate the spec, and how would you confirm each?

DEEP:
| Zone | ZSLBA | ZCAP | WP | ZS byte | ZA |
|---|---|---|---|---|---|
| 0 | 0x00000 | 0xDC00 | 0x00000 | 10h | 00h |
| 1 | 0x10000 | 0xDC00 | 0x10200 | 20h | 00h |
| 2 | 0x20000 | 0xDC00 | 0x2DC00 | 20h | 00h |
| 3 | 0x30000 | 0xDC00 | 0x30000 | 40h | 00h |
| 4 | 0x40000 | 0xDC00 | 0x4DC00 | E0h | 01h |
| 5 | 0x50000 | 0xDC00 | 0x50000 | D0h | 00h |
| 6 | 0x60000 | 0xDC00 | 0x60000 | F0h | 00h |
| 7 | 0x70000 | 0xDC00 | 0x7F000 | 40h | 00h |
| 8 | 0x80000 | 0xDC00 | 0x80100 | 10h | 00h |

1. Decode the state as the high nibble: 1h Empty, 2h Implicit Open, 4h Closed, Eh Full, Dh Read Only, Fh Offline.
2. Zone 1: WP - ZSLBA = 0x200 = 512 LBAs (2 MiB). Fine.
3. **Zone 2 (violation):** WP = ZSLBA + ZCAP = 0x2DC00 in an open state. Reaching capacity must make the zone Full.
4. **Zone 3 (legal):** Closed with WP = ZSLBA arises from Open then Close with no data. It still counts as active, and after a reset it would return as Empty (ZDEV = 0).
5. **Zone 4 (suspect):** ZFC = 1 means the controller finished the zone, which needs the Zone Active Excursions bit, and ZOC = 0 here. WP is invalid in Full and is ignored.
6. **Zones 5 and 6:** WP is invalid, so ignore it. Read Only rejects writes and Reset. Offline rejects reads and writes.
7. **Zone 7 (violation):** WP 0x7F000 exceeds ZSLBA + ZCAP = 0x7DC00 by 0x1400 = 5,120 LBAs, into the unmapped gap.
8. **Zone 8 (violation):** Empty demands WP = ZSLBA, but WP is 0x100 (256 LBAs) higher.
9. Resource check: open = zones 1 and 2 = 2 (limit MOR 4), active = 2 open + Closed zones 3 and 7 = 4 (limit MAR 8). Fine.
FOLLOW:
- How do you tell if zone 2 is a stale report or a real internal state? => Send a 1-block write at the WP. Zone Is Full means state was Full and the report is stale, Zone Boundary Error means the state is open with WP at the end (a state-update bug), success means data past capacity was accepted (severe).
- Zone 8 shows Empty with a WP off by 256 LBAs. What would you read? => The LBAs at ZSLBA and ZSLBA + 0x100, plus the trace of the preceding Reset. Suspect a Reset that cleared state but not the WP, or a stale cache in report generation.
PITFALL: Treating zone 3 as a bug. Closed with no data is reachable and legal, but it consumes an active resource, which is why resource tests must count it.
VERIFY: Whether ZFC may ever be set when ZOC does not advertise Zone Active Excursions, in the Zone Attributes definition.

@@ 3.14 | Principal | Concept | tags=shadow-model,invariants,oracle,automation,coverage
Q: How would you design a zone-state model and invariant checker for a ZNS validation framework?
SHORT: Keep a per-zone shadow of state, WP, attributes and resource counts, updated only from command completions and the spec's transition rules, never from the device report. After each drained batch and on a timer, run Report Zones and diff against the shadow. Assert geometry, WP range, transition legality, resource limits and WP monotonicity, and encode the legitimate nondeterminism explicitly.
DEEP:
1. **Geometry:** ZSLBA(n) = n x ZSZE, ZCAP <= ZSZE, type = 2h, state is one of the seven, reserved bytes zero.
2. **WP range:** in Empty, Open and Closed states ZSLBA <= WP < ZSLBA + ZCAP. Empty implies WP = ZSLBA, but WP = ZSLBA does not imply Empty, since an open or Closed zone with no data sits there too. Ignore WP in Full, Read Only, Offline.
3. **Monotonic WP:** between Resets, WP never decreases, and after each completed write it equals the old WP plus blocks written (for Append, returned LBA plus length).
4. **Transition legality:** only the table in 3.06 plus declared controller moves. Offline is terminal. Read Only never returns to writable.
5. **Resources:** open count <= open limit and active count <= active limit (MOR and MAR are zero-based in Identify, and the kernel uses MOR + 1, so 0xFFFFFFFF means no limit).
6. **Rejected commands:** a failed command must leave state and WP unchanged. Check by reporting the zone right after.

- **Declared nondeterminism:** the controller may close any Implicitly Opened zone when resources run out, may move zones to Read Only or Offline, and after power loss the WP may lie between last durable and last submitted. The model holds an allowed set, not one value.
- **Race handling:** compare after draining the queues, since a report can race in-flight writes.
- **Failure output:** dump the model, the report, and the last 20 commands with completion status so the trace reproduces.
FOLLOW:
- Why not seed the model from the device report? => A device that consistently lies (state and WP both wrong the same way) would never be caught. The oracle must come from the spec and completions.
- How do you handle an unexpected but legal Closed zone? => Record it as an informational eviction, resync the shadow to Closed, and check resource counts.
PITFALL: Asserting exact equality where the spec allows a set of outcomes, which produces flaky failures that get ignored and hide real bugs.
VERIFY: Zero-based MAR and MOR encoding and the "no limit" value in the ZNS Identify Namespace section.

@@ 3.15 | Principal | Scenario | tags=power-loss,wp,durability,flush,fua,triage
Q: After a sudden power cut in the middle of a sequential write stream, Report Zones shows a zone Closed with a WP lower than the host last saw. Is that a bug, and how do you triage it?
SHORT: Not automatically. After power loss the controller rebuilds zone state from what it persisted: open zones return Closed, and WP reflects recoverable data. It is a bug if the WP is lower than the last point the host made durable (FUA or Flush completion, or any completion when there is no volatile write cache), or if data below the WP is missing or wrong. Bound the WP between the durable end and the submitted end and read back everything.
DEEP:
1. **Record per zone before the cut:** last submitted end LBA, last completed end LBA, last durable end (FUA write or Flush completion), and whether a volatile write cache is enabled (Identify Controller VWC, Get Features Volatile Write Cache).
2. **After power on:** Report Zones. Expect state per 3.09 and WP_new with durable_end <= WP_new <= submitted_end.
3. **Read back every LBA below WP_new** and compare with the written pattern. Read LBAs at and above WP_new and expect the unwritten value.
4. **Classify failures:**
   - WP_new > durable and holes or wrong data below WP: firmware persisted the WP before the data.
   - WP_new < durable_end: flushed data lost, a journal or metadata bug.
   - Zone Empty though data was durable: lost zone mapping.
   - Zone Full without Finish or capacity reached: bad recovery rule.
5. **Repeat** at many cut points (random, at zone boundaries, at Finish, at Reset) and plot WP_loss = submitted_end - WP_new.
- **With PLP:** power-loss protection should flush volatile data, so completed writes are expected to survive. Any loss is a bug, and the rollback window shrinks to in-flight commands.
FOLLOW:
- How do you make the cut reproducible? => Use a programmable power switch or the drive's power-fail injection and trigger on a command count or timer, logging exact command IDs and submit times. Use FUA on marker writes so the durable lower bound is known.
- What if WP_new is below durable_end on only one zone? => Check whether that zone was mid-Finish or mid-Reset at the cut, which are metadata-heavy operations, and reproduce that specific sequence.
PITFALL: Comparing WP_new to the last completed write instead of the last durable point. Completed does not mean durable when a volatile cache is on.
VERIFY: The durability and WP-rollback rules the ZNS spec and NVM Command Set give for unexpected power loss, and how PLP is declared.

@@ 3.16 | Principal | Scenario | tags=read-only,offline,media-fault,fault-injection,triage
Q: During an endurance run a few zones go Read Only. How do you root-cause it, and how do you design a test for that behavior?
SHORT: Read Only means the controller stopped accepting writes to the zone, typically after NAND program or erase failures or lost redundancy, while data stays readable. Record when each zone changed, correlate with the SMART and health log and vendor logs, copy the data out, then send Offline Zone. For validation, inject NAND faults on chosen blocks and assert the exact state, status and resource behavior.
DEEP:
1. **Detect:** a write failing with Zone Is Read Only (BAh), a zone-information-changed event (module 6), or periodic reports. The host cannot trust the WP field, so use its own record of the last completed write.
2. **Evidence:** timestamp of first appearance, Percentage Used and Available Spare, Media and Data Integrity Errors, Critical Warning bit 3 (media in read-only mode, namespace-wide, a related but different signal), and the vendor NAND log (bad blocks, die, program-fail counts).
3. **Causes:** program or erase failure with no spare left for the zone's stripe, wear-out, an injected fault left active, or a firmware bug that latched the state wrongly.
4. **Validate the behavior:**
   - Only zones mapped to the faulted block change state.
   - Writes fail with Zone Is Read Only, Reset fails with Invalid Zone State Transition, reads below the last completed write still match.
   - The open and active counts drop, since Read Only zones are neither.
   - Offline Zone moves it to Offline, then reads fail with Zone Is Offline.
5. **Host side:** evacuate valid data, mark the zone dead in the allocator and adjust capacity accounting.
FOLLOW:
- Can Reset Zone bring the space back? => No, it fails with Invalid Zone State Transition. Only a vendor mechanism or reformat may recover the space (check the spec and vendor documents).
- How do you know how much valid data a Read Only zone holds when WP is invalid? => From the host's own record (the shadow model's last completed write), and by reading until the device returns the unwritten value.
PITFALL: Expecting the WP field to say how much survives in a Read Only zone. It is invalid there, so the host must keep its own bookkeeping.
VERIFY: Critical Warning bit 3 meaning in the NVMe Base Specification, and which log (Changed Zone List or asynchronous event) reports the change on your device.

@@ 3.17 | Principal | Concept | tags=coverage,state-machine,test-plan,fault-injection,automation
Q: How would you build a coverage plan for the zone state machine, and how do you reach the states that cannot be entered by commands alone?
SHORT: Enumerate (state x action) cells with an expected status and post-state for each: 7 states and 9 actions (Write, Append, Open, Close, Finish, Reset, Offline, Set Descriptor Extension, Read) give 63 cells, and about 190 test points once you add resource-limit variants. Reach the ordinary states with commands. Reach Read Only, Offline and controller-finished Full only with fault injection or vendor hooks, and record them as gaps if unavailable.
DEEP:
| Target state | How to reach it |
|---|---|
| Empty | Reset Zone, or a fresh Format |
| Implicit Open | write one block to an Empty zone |
| Explicit Open | Open Zone |
| Closed with data | write, then Close Zone |
| Closed, WP = ZSLBA | Open Zone, then Close Zone |
| Full | write to ZCAP, or Finish Zone |
| Read Only, Offline, Full by ZFC | fault injection or vendor command only |

- **Size:** 7 x 9 = 63 cells. Repeating each under three resource conditions (below limits, at open limit, at active limit) gives 189 test points. Generate them from a table.
- **Sequences:** cover single transitions first (0-switch), then consecutive pairs (1-switch), for example Closed to Implicit Open to Full.
- **Edge writes:** end a write exactly at ZCAP, one block short, and one block over.
- **Random walks:** run the shadow model (3.14) with seeded random commands, biased toward edges and limits, and log the seed.
- **Metric:** count distinct (state, action, result) tuples hit. Publish the holes, and mark Read Only and Offline cells as "needs injection" instead of dropping them.
- **Tooling:** nvme-cli `nvme zns` subcommands with JSON output, or SPDK and xNVMe for high queue depth.
FOLLOW:
- The drive ships with no Offline zones. How do you cover Offline? => Use a vendor fault or a factory-offline namespace. If neither exists, record it as an explicit coverage gap with an owner, not a silent skip.
- What is 1-switch coverage? => Coverage of every sequence of two consecutive transitions, not only each single transition.
PITFALL: Covering success paths only. Roughly half the matrix is rejected actions, and each must be checked for exact status and no side effects.
VERIFY: The complete list of Zone Management Send actions in your ZNS revision, since the action count changes the matrix size.
